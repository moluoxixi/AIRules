# Skill 内容标准

## 适用时机

本标准用于约束 AIRules 第一方 `skills/<name>/SKILL.md` 的内容质量。它不是默认安装到 AI 宿主里的 skill，也不是普通业务任务的运行规则。

仅在以下场景使用：

- 新增 first-party skill。
- 修改 first-party skill 的 `description`、触发条件、流程、输出位置、用户确认策略或脚本命令。
- 评审 skill 是否值得保留、合并、删除或默认分发。
- 发布、同步或提交前，用户明确要求校验 skill 内容。
- CI 或维护脚本需要抽检 skill 内容约束。

不在以下场景触发：

- 普通代码实现、文档编写、测试修复或业务问答。
- 只读取 third-party/vendor skill 作为参考。
- 用户没有要求修改 skill，且当前任务不会影响 skill 分发或执行行为。

## 核心原则

- Skill 是可复用的工作流能力，不是一次任务的复盘记录。
- Skill 必须有清晰触发边界；没有独立触发场景的内容应写入 README、docs、脚本帮助或现有 skill 的小节。
- Skill 不应把项目治理、候选记录、校验脚本包装成会自动触发的代理能力。
- Skill 中的事实、命令、输出路径和用户确认要求必须可执行、可验证、不过度承诺。

## Frontmatter 约束

- `name` 必须存在，且等于 skill 目录名。
- `description` 必须存在。
- `description` 是给 AI 判断“是否加载/触发该 skill”的触发条件，不是给人看的能力摘要。
- `description` 必须说明适用时机或场景，例如“用于……时触发”“当……时使用”。
- `description` 不得只写泛泛能力，例如“生成文档”“提高质量”“校验 skill”。
- `SKILL.md` 不超过 500 行；超过时优先拆到 `references/`、脚本或普通 docs。

## 正文结构约束

每个 first-party skill 应至少说明：

- 触发条件：什么时候用。
- 不适合场景：什么时候不要用。
- 输入来源：读取哪些文件、用户信息或脚本输出。
- 输出边界：会写入哪些路径，哪些路径不得写入。
- 用户确认策略：哪些动作需要先询问用户。
- 验证方式：可选校验命令或测试方式；不得默认强制运行，除非这是 CI/发布流程或用户明确要求。

## 示例与模板约束

Skill 正文可以包含示例、模板、候选格式和命令片段，但必须明确其性质：

- 示例必须标注为“示例”，不得伪装成固定事实。
- 模板必须使用占位符或说明字段含义，不得让 AI 把示例内容当真实业务数据。
- 候选格式必须说明是否需要用户确认、是否待审、是否会直接写入正式知识库。
- 命令片段必须说明运行前提、目标路径和失败处理方式。
- 如果一段内容只是参考口径、可选流程或人工评审材料，必须写明“仅供参考”“用户确认后执行”或“不得自动应用”。

## 禁止内容

- 不得要求 AI 在用户未确认时自动写入长期记忆、正式知识库、rules、skills、vendor 或宿主目录。
- 不得把 third-party/vendor skill 当作可直接修改的资产。
- 不得把临时任务经验、单次修复日志或猜测写成长期规则。
- 不得写“失败可降级为 warning”来掩盖校验失败。
- 不得在 skill 中保留占位说明，例如“这里写协议路径”“TODO 后续补充”。
- 不得声明工具已经存在、测试已经通过或路径一定可写，除非 skill 同时要求实际验证。

## 推荐去向

当内容不适合作为独立 skill 时，优先放到：

- `docs/`：设计标准、内容规范、架构说明、长期维护说明。
- `scripts/`：可执行校验、同步、转换工具。
- `tests/`：可自动验证的内容合同。
- 现有 skill 的小节：只是某个工作流的补充步骤。
- README/README-zh：用户安装、使用和维护说明。

## 校验命令

用户确认后，可对单个 skill 根目录运行：

```bash
node scripts/verify-skill-frontmatter.mjs --root skills/<skill-name>
```

该命令检查 frontmatter、行数、description 触发语义，以及正文中示例/模板/候选内容是否有边界说明。它只接受直接包含 `SKILL.md` 的单个 skill 根目录，不接受 `skills/` 总目录。
