# O-03 · 计数器责任主体在 agent 契约层完全缺失（P2）

## 现状（核验通过，比原描述更严重）

agent 输出契约中**既无**声明性字段（`current_loop_id` / `current_iteration`），**也无**建议性字段（`recommended_loop` / `recommended_next_action`）。计数器写入责任完全悬空。

核验证据：

- `agents/consistency-reviewer.md` 全文（1-39 行）：输出契约只规定状态用 `PASS`/`FAIL`/`MISSING`/`N/A`、可写 `docs/consistency/*-implementation-review.md`、不符项指出对应需求条目。**无任何与回路/迭代/计数相关的字段。**
- `agents/code-reviewer.md`（1-42 行）：输出契约规定结论分级 `Critical`/`Improvement`/`Nitpick`、`escalation_type` ∈ {`code_quality`, `requirement_mismatch`}、回传由主代理裁决。**无 `current_loop_id` / `current_iteration` / `recommended_loop` 字段。**
- `agents/debugger.md`（1-40 行）：输出契约规定回传"根因 + 证据 + 建议修复点 + 回归测试设计"、状态用 `MISSING` 兜底未复现。**无 `current_loop_id` / `current_iteration` / `recommended_loop` 字段。**
- 全仓 Grep `recommended_loop` / `recommended_reinject` / `recommended_next_action` / `stage_evidence`：**仅在历史 issue 文档中出现**，是问题登记里的预设示例或修复方案草稿，**不是 agent 当前契约的真实字段**。

## 与原 P2 描述的差异

历史 issue 描述"agents 输出 `recommended_loop` 这类建议性字段"——但子代理逐字核验后发现：

- 这些 `recommended_*` 字段**在 agent 契约中根本不存在**
- 它们只在 `issue/` 历史登记里作为修复方案草稿出现过

因此现状**比原描述更糟**：不是"建议性字段责任悬空"，而是"完全没有任何字段承载循环身份信息"。

## 学术对照（简）

LangGraph / OpenAI Agents SDK / AutoGen 通用模式都是**编排层传入 + 子 agent 回执 + 编排层据回执持久化计数**，而非建议性表达。

## 修复建议

在 `agents/consistency-reviewer.md`、`agents/code-reviewer.md`、`agents/debugger.md` 的输出契约段补两类字段，明确职责分层：

### 声明性字段（由主代理派发时**传入**，子代理在 evidence 中**回执**）

```yaml
current_loop_id: <Consist→Code | Test→Debug→Code | Review→Code | Review→Req>
current_iteration: <integer，由主代理写入>
```

子代理只读取与回执，不修改。这样计数器的写入责任主体明确是主代理。

### 建议性字段（由子代理**产出**给主代理）

```yaml
recommended_next_action:
  reroute_target: <Code | Req | none>
  escalation_type: <code_quality | requirement_mismatch | n/a>  # 仅 code-reviewer 适用
  should_increment_mismatch_loop: <boolean>  # 仅 code-reviewer 适用
```

主代理读取建议字段后据自身计数器决定是 reroute 还是 BLOCKED。同步在 `skills/consistency-check`、`skills/requesting-code-review`、`skills/systematic-debugging` 的输出格式段补这两类字段的位置与样例。

## 与 O-01 / O-02 的关系

- **O-01** 在主代理侧建机制（账本 + hook）维护 `iteration`
- **O-03** 在子代理侧建契约（输入接受 / 输出回执）让机制可观测、可审计
- **O-02** 复用相同基础设施承载 `blocked_id`

三者应作为同一轮变更落地，避免分阶段返工。

## 回归测试设计

```yaml
- id: TC-LoopId-001
  name: consistency-reviewer evidence 必含 current_loop_id 与 current_iteration
  given: 主代理派发时传入 current_loop_id=Consist→Code, current_iteration=2
  when: consistency-reviewer 回传 evidence
  then: evidence 包含 current_loop_id=Consist→Code 与 current_iteration=2（回执一致）

- id: TC-LoopId-002
  name: code-reviewer 输出 should_increment_mismatch_loop 字段
  given: code-reviewer 判定方向性错误
  when: 输出 evidence
  then: evidence 含 escalation_type=requirement_mismatch 且 should_increment_mismatch_loop=true
```

## 影响范围

- `agents/consistency-reviewer.md`、`agents/code-reviewer.md`、`agents/debugger.md`（输出契约段加两类字段）
- `skills/consistency-check/SKILL.md`、`skills/requesting-code-review/SKILL.md`、`skills/systematic-debugging/SKILL.md`（同步样例）
- `__test__/workflow-contract.test.ts` 增加文本锚点断言（`current_loop_id`、`current_iteration` 字段在 agent 文件中存在）
