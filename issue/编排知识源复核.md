# 编码生命周期编排独立复核

## 复核结论

当前编码生命周期编排的主方向是成立的：默认编码路径保持轻量，复杂变更才进入规格持久化层；需求分析、计划、实现、一致性评审、测试验证、代码评审之间的顺序也基本符合可验证交付的要求。上一版中容易导致硬错误的时序问题已经修正，一致性评审现在位于编码后、测试验证前，能够先拦截“实现不符合需求/计划/验收用例”的问题，再投入实际测试成本。

当前仍有问题，但主要是边界表达问题，不是架构性推倒重来。最需要修的是：普通编码路径里混入了 `spec-workflow apply` 的语义，spec 触发条件在流程图上表达偏宽，`--allow-empty` 例外容易被误解为普通文档/流程变更也应走 spec，archive 前置条件没有明确区分流程证据门禁和脚本内容门禁。

## 一、主流程是否有问题

主流程整体没有大问题。它现在表达的是一条标准编码任务流水线：先把需求转成事实源和验收标准，再冻结实现计划和测试用例清单，然后编码实现，随后做一致性评审，再运行测试/构建/lint，最后做独立代码评审。这个顺序是合理的。

一致性评审放在测试运行之前是正确的。它评的是“最终 diff 是否符合需求、计划、验收用例”，不是代码质量，也不是测试结果。如果实现方向已经偏了，先跑测试没有意义；测试最多证明代码满足当前测试，但不能证明它满足原始需求。因此当前 `Code -> Consist -> Test -> Review` 的顺序比 `Code -> Test -> Consist -> Review` 更合理。

代码评审放在测试之后也是合理的。代码评审需要看到最终 diff 和测试证据，否则 reviewer 只能做静态判断，无法确认变更是否经过实际验证。当前规则要求 reviewer 与 coder 是不同实例，也符合反自评要求。

阶段证据 schema 是有效补强。它要求每个阶段记录状态、输入资产、命令或证据来源、关键输出、失败原因、下游依赖和是否阻断，可以减少代理用自然语言把 `FAIL`、`MISSING`、`NOT RUN` 包装成“基本完成”的风险。

## 二、当前最明显的问题：普通路径混入 spec apply

当前流程图里普通路径写成：

```mermaid
Plan -->|普通路径| Code["实现(spec-workflow · apply): coder 按栈写测试(红) + 代码(绿)，勾选 tasks"]
```

这里有明确问题。普通路径按定义是不走规格持久化层的路径，不应该出现 `spec-workflow · apply`。同时，“勾选 tasks”也只适用于 spec 路径下的 `.airules/changes/<change-id>/tasks.md`，不应该成为普通编码任务的默认要求。

这个问题会造成两个误导。第一，代理可能以为所有编码任务都必须创建或维护 spec tasks，导致小改、局部 bugfix、内部重构被过度流程化。第二，spec-workflow 的职责会被扩大，从“把值得长期保存的行为契约固化为规格”变成“所有实现任务的执行器”，这会破坏方法论层和规格持久化层的分工。

建议把普通路径改成：

```mermaid
Plan -->|普通路径| Code["实现：coder 按计划写测试(红) + 代码(绿)"]
```

如果是规格路径，再单独表达：

```mermaid
Spec --> Apply["spec-workflow · apply：按 tasks.md 落地并勾选任务"]
Apply --> Code
```

或者保持单个 Code 节点，但在正文中明确：只有规格路径需要执行 `spec-workflow apply` 和勾选 `tasks.md`，普通路径只按计划和验收用例实现。

## 三、spec 和 plan 应该分开

spec 和 plan 不应该合并。它们解决的问题不同。

plan 是一次任务的执行路线，回答“这次怎么做”。它关注文件范围、实现步骤、测试顺序、验收命令、风险和不做什么。plan 的生命周期通常跟随一次任务，任务结束后不一定继续维护。

spec 是系统长期行为契约，回答“系统应该长期承诺什么”。它关注外部可观察行为、接口语义、状态机、权限规则、数据一致性、兼容性和破坏性变化。spec 归档后会进入 `.airules/specs/`，成为后续任务、评审、测试设计可以引用的长期事实源。

因此，正确关系应该是：需求事实源定义为什么做和要满足什么；spec 定义系统长期承诺什么行为；plan 定义这次如何实现这些行为；tests 证明实现满足需求、plan 和 spec。不是每个 plan 都需要 spec，但进入 spec 路径的任务一定需要 plan，因为 spec 只定义契约，不替代执行拆解。

## 四、spec 触发条件是否合理

当前 spec 触发条件总体合理，但表达需要收紧。

`spec-workflow` 中写“变更涉及系统行为契约（接口/状态机/数据一致性等），值得沉淀为长期事实源”，这个方向是对的。关键限定是“行为契约”和“值得沉淀为长期事实源”。但流程图 Gate 写的是“系统行为/接口/状态机/数据一致性”，这个短表达容易被误读为只要碰到接口、状态机、数据一致性，就必须立 spec。

这会导致触发面偏宽。一个局部 bugfix 可能涉及接口返回、状态判断或数据一致性，但如果它只是修复实现错误，不改变系统长期契约，就不应该强制走 spec。反过来，一个看似很小的改动，如果改变了公共 API、权限规则、订单状态流转、数据落库语义或兼容性承诺，就应该触发 spec。

建议把触发条件从“技术对象类型”改成“契约变化属性”。更推荐的表达是：

```md
触发 spec-workflow 当且仅当：

- 用户显式要求正式立项、沉淀为可追溯规格契约；或
- 变更会新增、修改或废弃外部可观察的系统行为契约，并且该契约需要作为长期事实源维护，例如公共 API、跨模块协议、状态机、权限规则、数据一致性规则、持久化数据模型、兼容性/破坏性变化；或
- 后续多 agent、多模块、多团队会依赖该行为契约，缺少书面 spec 会导致实现、评审或回归验证无法稳定判定正确性。
```

对应的不触发条件应写清楚：

```md
不触发 spec-workflow：

- 纯内部实现重构且行为等价；
- 小改、L0/L1、局部 bugfix，且不改变长期契约；
- 纯探索、纯格式、普通文档更新；
- 只需要一次性实现计划，不需要归档为长期事实源的任务。
```

这样能避免把 spec-workflow 变成所有复杂代码任务的默认负担，同时保留它在系统行为契约变化中的价值。

## 五、`--allow-empty` 例外需要明确边界

当前规则里一方面说纯探索、纯文档、纯格式调整不需要 spec；另一方面 archive 支持纯文档/纯流程变更加 `--allow-empty` 跳过 delta 要求。这两者并非冲突，但需要明确层级。

默认规则应该是：普通纯文档、纯流程、纯格式变更不触发 spec-workflow。例外规则应该是：只有当用户显式要求把治理决策、流程规则或文档变更作为可追溯 change 归档时，才允许使用 `--allow-empty`。并且 `--allow-empty` 只能跳过 delta spec 要求，不能跳过 proposal 和 tasks 的内容门禁。

如果不写清楚，后续代理可能把 `--allow-empty` 当成“无行为契约也可以常规归档”的入口，导致 spec 目录变成普通变更日志或文档历史。这会降低 `.airules/specs/` 作为长期行为事实源的信噪比。

## 六、archive 前置条件要拆成两类门禁

当前 archive 前置条件包含两类东西：一类是流程证据，如实现完成、验证 PASS、一致性评审 PASS 或 N/A、代码评审无阻塞项；另一类是脚本可检查内容，如 proposal 非空、tasks 全部完成、存在 delta spec、delta 合并无冲突。

这两类门禁应该分开写。脚本只能可靠检查文件内容和合并冲突，不能知道测试是否真的跑过，也不能知道一致性评审和代码评审是否真的通过。测试、评审和一致性状态必须由主流程 evidence schema 负责。

建议写成：

```md
流程门禁（主代理基于阶段证据负责）：实现完成、验证 PASS、一致性评审 PASS 或 N/A、代码评审无阻塞项。

脚本门禁（`spec-archive.mjs` 强制检查）：proposal 的 Why/What Changes 非空、tasks 默认全部 `[x]`、默认至少一个 delta spec、delta 合并无冲突。
```

这样可以防止代理误以为只要 `spec-archive.mjs` 成功，就代表整条编码流水线已经满足归档条件。

## 七、建议补充的回归测试

现有 workflow contract 已经覆盖了关键负例，包括空 delta、空 proposal、未完成 tasks 和一致性评审时序。建议再补一组 flag 语义测试，锁定例外参数不会变成绕过门禁的通道。

建议补充：

```md
- `spec-archive --allow-empty` 只跳过 delta spec 要求，proposal 空或 tasks 缺失仍 FAIL。
- `spec-archive --allow-incomplete` 只跳过 tasks 全完成要求，proposal 空或 delta 缺失仍 FAIL。
- `spec-validate --allow-empty` 只跳过 delta spec 数量要求，不跳过 proposal/tasks 基本校验。
```

这类测试成本很低，但能防止后续维护时把“显式例外”扩大成“全面绕过”。

## 八、建议修正优先级

优先级最高的是修正普通路径 Code 节点，移除 `spec-workflow · apply` 和“勾选 tasks”。这是当前最容易造成执行路径误判的问题。

第二优先级是收紧 spec Gate 文案，把“系统行为/接口/状态机/数据一致性”改成“外部可观察行为契约变化 + 值得长期沉淀”。接口、状态机、数据一致性可以作为例子保留，但不应作为充分触发条件。

第三优先级是明确 `--allow-empty` 只是用户显式要求归档纯治理/流程类 change 时的例外，不是普通文档变更的默认路径。

第四优先级是拆分 archive 的流程门禁和脚本门禁，避免把脚本成功等同于整条流程完成。

第五优先级是补 flag 语义回归测试，防止例外参数在未来演化成绕过机制。

## 最终判断

当前编排可以继续沿用，不需要重做。它已经具备编码任务所需的基本闭环：需求事实源、计划、测试设计、TDD 实现、一致性评审、实际验证、独立代码评审和按需规格归档。真正需要调整的是 spec-workflow 的边界表达。

spec 不应该替代 plan，也不应该成为所有编码任务的默认前置物。spec 的价值在于沉淀长期行为契约；plan 的价值在于指导本次实现。只要把这条边界写清楚，并修掉普通路径里的 `spec-workflow apply` 混入问题，当前编排会更轻、更稳，也更不容易被代理误执行。
