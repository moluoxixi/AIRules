# 编排知识源复核与当前剩余问题

## 结论

`issue/编排.md` 的主判断基本成立：可靠 coding agent 编排应强调可验证任务、清晰 handoff、真实工具/测试反馈、独立评审、可观测轨迹和可审查长期上下文。这个方向能被 ReAct / ReWOO / LLMCompiler、SWE-agent / SWE-bench、OpenAI Agents SDK、Anthropic Agent Skills、OpenSpec / Spec Kit、context engineering 与 GraphRAG / memory 类资料共同支撑。

但 `编排.md` 不能再作为当前仓库现状报告使用。它记录的是修复前状态：多个 P0/P1 已在当前项目中修复或部分修复；同时又出现了新的剩余问题，包括 CI 未实际跑 `rules:check`、`lint:check` 当前失败、workflow-contract fixtures 覆盖不足。

## 知识源复核

| 论点 | 知识源支撑 | 复核结论 |
|---|---|---|
| agent 需要 reasoning 与 tool observation 闭环，不能只靠模型自述 | [ReAct](https://arxiv.org/abs/2210.03629)、[SWE-agent](https://arxiv.org/abs/2405.15793) | 成立。支撑“读 diff / 读测试输出 / 读日志 / 失败回环”的门禁。 |
| 复杂任务可先规划依赖，再并行执行独立子任务 | [ReWOO](https://arxiv.org/abs/2305.18323)、[LLMCompiler](https://arxiv.org/abs/2312.04511) | 成立。支撑“并行必须依赖清晰、产物边界明确、不写同一文件”。 |
| 多 agent 的价值来自中间产物、检查点、失败回退，不是角色数量 | [MetaGPT](https://arxiv.org/abs/2308.00352)、[ChatDev](https://arxiv.org/abs/2307.07924)、SWE-agent | 成立。支撑从旧 9-agent 收敛到 5-agent + 按需多实例。 |
| coding-agent 评估应绑定真实任务、环境和可判定结果 | [SWE-bench](https://www.swebench.com/)、[SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)、[AgentBench](https://openreview.net/forum?id=zAdUB0aCTQ) | 成立。支撑“最小 workflow fixtures”而不是只做文案自检。 |
| 工具使用能力需要看参数选择、结果利用、失败恢复和轨迹质量 | ToolBench / API-Bank 类评估、AgentBench | 方向成立，但 `编排.md` 参考资料没有为 ToolBench / API-Bank 单独列出主来源链接，证据链应补齐。 |
| handoff / guardrails / tracing 是 agent 编排的关键工程能力 | [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/)、[Anthropic Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) | 成立。支撑“输入上下文包、输出证据 schema、不可伪装 PASS”。 |
| spec-driven development 应把意图固化为 proposal / tasks / delta / archive | [OpenSpec](https://intent-driven.dev/knowledge/openspec/)、[GitHub Spec Kit](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) | 成立。支撑 `spec-workflow` 的 propose / apply / archive 和 proposal/tasks/delta 内容门禁。 |
| context / memory 不只是有无知识源，还要定义检索顺序、冲突优先级和证据状态 | [Sourcegraph context engineering](https://sourcegraph.com/blog/context-engineering)、[GraphRAG](https://memgraph.com/docs/ai-ecosystem/graph-rag)、[MemGraphRAG](https://arxiv.org/html/2606.00610v1) | 成立。支撑 ADR-0004 的普通文件 / CodeGraph / 项目 memory / 全局 memory / MCP 顺序。 |

## `编排.md` 自身需要修订的点

1. **现状判断已过期**：文中仍把 `rules:check` 缺失、ADR 仍停留旧 9-agent、spec-archive 可无 delta 归档等写成当前问题；这些在当前仓库里已不再完全成立。
2. **结论段有时序表述冲突**：开头把主线概括为“实现/TDD → 验证 → 调试回环 → 一致性评审 → 独立代码评审”，但正文又建议 `Code → Consistency-review → Test → Code-review`。当前项目已采用后者，文档结论段应同步。
3. **知识源参考列表不够对齐正文**：正文提到 ToolBench / API-Bank、RAGAS、CRAG、DSPy、MemGPT、Cursor rules、Aider、OpenHands、GitHub Copilot coding agent、Gemini CLI 等，但参考列表没有逐项给出主来源。若这些概念继续作为论据，应补 primary source 链接或删去不承重的名称。
4. **“当前问题”与“建议后续增强”混在一起**：例如 workflow fixtures 和 evidence schema 是正确的后续增强；但当前 `rules/AGENTS.md` 已有阶段证据 schema，不能再简单写成完全缺失。

## 当前项目已完成的修复

1. **一致性评审时序已对齐**：`rules/AGENTS.md` 当前为 `Code → Consist → Test → Review`，并且文字说明也写成编码后、测试验证前。
2. **5-agent 架构已落地**：ADR-0001 / ADR-0002 已在索引中标记为 superseded，ADR-0003 / ADR-0004 分别承接 5-agent 收敛和知识检索协议。
3. **轻量自洽检查已恢复**：`package.json` 已有 `rules:check`，脚本 `scripts/check-rules-consistency.ts` 检查固定 agent、agent 引用 skill、分发清单 skill、旧 agent 活引用、overview 引用不存在 npm script、Mermaid 旧时序。
4. **spec-workflow 内容门禁已补上**：`spec-validate.mjs` 校验 proposal/tasks/delta；`spec-archive.mjs` 默认要求 proposal 有效、tasks 全部完成、至少一个 delta spec，除非显式 `--allow-empty` / `--allow-incomplete`。
5. **知识源机制已裁决**：ADR-0004 废弃 registry，改为普通文件检索 / CodeGraph / 项目 memory / 全局 memory / MCP 外部资料的顺序与冲突优先级。
6. **handoff context packet 已写入 agent 文件**：planner、coder、debugger、consistency-reviewer、code-reviewer 均有“输入上下文包”和缺关键输入 `MISSING blocked` 规则。
7. **重型治理词汇回流已基本处理**：`executing-plans` 与 `finishing-a-development-branch` 已使用“变更范围/风险摘要”，不再保留 `编排.md` 所说的“变更分级”收尾模板。

## 当前仍未完全收口的问题

### P1：`lint:check` 当前失败

本次验证中 `npm run lint:check` 失败，49 个 Markdown lint 错误，集中在已跟踪的 `.ruletest-output/full-run/inputs/**` 测试输入和根 `AGENTS.md` 的多 H1。既然 `ci.yml` 会跑 `lint:check`，当前项目不能声明全量验证通过。

建议：

- 明确 `.ruletest-output` 是测试 fixture 还是生成物；如果是 fixture，就在 ESLint 配置中按规则豁免或修正 fixture；如果是生成物，就不应跟踪或不应被 lint 扫描。
- 根 `AGENTS.md` 若必须多 H1，应在 Markdown lint 规则中对该文件做专门例外；否则调整标题层级。

### P1：CI 文档与工作流仍漂移

`docs/architecture/overview.md` 说 PR 阶段 `ci.yml` 跑 `lint:check / typecheck / test / rules:check`，但当前 `.github/workflows/ci.yml` 实际只跑 `lint:check`、`typecheck`、`npm test`，没有 `npm run rules:check`。

建议：在 CI 中补 `npm run rules:check`，或把 overview 改成真实 CI 状态。更推荐补 CI，因为 `rules:check` 正是这次编排修复的低成本核心门禁。

### P1：workflow-contract fixtures 仍不足

当前已有 `rules:check` 和 spec-workflow 脚本测试，但尚未形成 `workflow-contract.test.ts` 或等价测试集合，覆盖 `编排.md` 明确要求的四类负例：

- 缺上游事实源时 planner/coder 应 `MISSING blocked`
- 未运行验证时不得报告 `PASS`
- reviewer 与 coder 未隔离应失败
- spec archive 空 delta 默认应失败

建议新增文本级/脚本级 workflow contract 测试，不调用真实 LLM，只验证规则资产是否包含并维持这些关键断言。

### P2：spec-workflow 负例测试还不够直观

脚本已经实现 proposal/tasks/delta 门禁，但现有 `spec-workflow-scripts.test.ts` 没有单独覆盖“无 delta 默认失败”“proposal 空失败”“tasks 未完成失败”这几个最直接的负例。当前只是在代码层能看到门禁，测试层表达还不够贴近 `编排.md` 的验收标准。

建议补三条测试：

- `spec-validate` 对无 delta change 默认失败
- `spec-archive` 对 proposal 空 / tasks 未完成失败且不移动 change
- `spec-archive --allow-empty` 只跳过 delta 要求，不跳过 proposal/tasks 要求

### P2：`rules:check` 还不能发现 CI 漂移

`rules:check` 能检查 overview 是否引用不存在的 npm script，但不能检查 overview 声称的脚本是否真的出现在 `.github/workflows/ci.yml`。这就是本次 CI 漂移能留下来的原因。

建议扩展 `check-rules-consistency.ts`：当 overview 声称 PR 阶段跑 `rules:check` 时，必须在 `.github/workflows/ci.yml` 中找到 `npm run rules:check`。

## 建议落地顺序

1. 先修 `lint:check`，否则 CI 当前必失败。
2. 给 CI 补 `npm run rules:check`，并扩展 `rules:check` 检查 CI/overview 一致性。
3. 补 workflow-contract fixtures，至少覆盖四类负例。
4. 补 spec-workflow 最小内容门禁的负例测试。
5. 更新或重写 `issue/编排.md`：把“修复前问题清单”转成“历史审计 + 当前状态”，并补齐正文提到但参考列表缺失的知识源链接。
