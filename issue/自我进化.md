# 自我进化机制再评估（2026-06-28）

## 结论

对照 2025-2026 年最新论文（EvolveMem、Agent-Native Memory Survey、Agent Skill Evaluation Survey、Safety Risks in Self-Evolving Agents、Externalization in LLM Agents、Xinming Tu 3×3 Framework）与工程实践（Mem0 2026 Report、AGENTS.md spec、Claude Code memory），逐条验证代码库实际实现后判定：

**AIRules 自我进化闭环在 prose/设计层已无架构级缺陷。** 原 issue 提出的所有关键建议（boundary 类型、recall 比例平衡、安全边界侵蚀归因、created_at/status 生命周期、按 type 分流检索、库级淘汰/合并）均已落地到 `rules/AGENTS.md`、`recall-memory`、`remember`、`reflect`、`distill-candidates` 五处。设计方向与学术共识高度一致，且在"人工审核门禁"这一点上比多数开源项目更保守、更安全。

**真正的遗留差距不在设计层，在 enforcement/实证层。** 具体见下。

## Prose 已约束 vs 实际执行的落差（真正的 gap）

### Gap 1：既有 memory 条目未迁移到新 schema（P1）

`remember` skill 定义的 schema 已包含 `created_at` 和 `status: active|superseded`，但实际存在的 memory 文件（`.airules/memory/memory-needs-review-like-skills.md`）frontmatter 只有 `type: decision`，**未补 `created_at` 和 `status`**。

这意味着 `recall-memory` 的 status 过滤在当前唯一的 memory 条目上不会生效——不是因为设计缺，而是因为存量数据没跟上 schema 演进。

**建议**：补一次存量 migration——为已有条目补全 `created_at`（按 git blame 时间）和 `status: active`。后续 `remember` 写入时严格校验 schema 完整性。

### Gap 2：Phase 4 自动化 fixture 仍为零覆盖（P1）

`scripts/check-rules-consistency.ts` + `__test__/workflow-contract.test.ts` 当前**零覆盖**自我进化约束。以下规则只有 prose 约束，没有机器门禁：

- `vendor/` 不作为源资产
- 全局 skill 必须登记 `constants/skills.ts`
- superseded memory 不进 active 召回
- 自动 distill 不能直接写正式库
- 项目 skill 不盲创宿主目录

规则漂移风险：当前全靠 LLM 阅读 skill 文本后自我遵守，无客观信号拦截违规。一旦 skill 文本被误改或 LLM 未加载完整指令，约束可能静默失效。

**建议**：Phase 4 优先补 3-5 条负例 fixture，每条对应一个可判定的文件系统或文本断言。不需要模拟完整 LLM 行为，只需验证"结构不变式"（如 vendor 下无 `.md` 源文件、skills 目录名都出现在 constants/skills.ts 等）。

### Gap 3：纵向评测无运行时度量（P2，长期方向）

`distill-candidates` 的"库级健康复核"用启发式扫描沉淀素材（sessions/changes）来判断"长期不触发"或"屡被覆盖"。这是合理的无运行时方案，但有两个局限：

1. 启发式依赖 session-capture 的覆盖率——如果用户不定期运行 capture，淘汰信号就没有数据来源
2. "触发但被覆盖"的判断只能基于事后文本分析，无法精确计数

这不是当前的 P0/P1 问题（项目是纯 prompt 元项目，没有运行时自增机制），但在 Phase 5 考虑更强评测时需要明确：精确度量需要宿主 runtime 支持（如 QoderWork awareness 提供 recall/override 事件），AIRules 仓库内只能做启发式近似。

**建议**：Phase 5 明确分工——AIRules 内定义"什么信号意味着 skill 退化"的判据规则；宿主 runtime 负责采集信号并传入 distill-candidates 的输入；不在 AIRules 内伪造运行时能力。

### Gap 4：检索策略进化无反馈闭环（P2，长期方向）

`recall-memory` 已有按 type 分流（decision 时序倒排、gotcha 文件匹配、constraint/boundary 全量扫），但这是静态启发——策略本身不会随使用而优化。EvolveMem 论文证明检索策略自适应能带来 78% 的提升，但那需要：per-query 评估、根因诊断、配置调整、回退保护。

对 AIRules 当前规模（memory 条目极少）这不是紧迫问题。但如果未来项目 memory 增长到 50+ 条目，静态启发的检索质量会下降。

**建议**：作为 Phase 5 的远期方向记录，不在当前路线图中加权。

## 对照最新论文的设计验证

| 论文/项目 | 核心主张 | AIRules 对齐情况 |
|-----------|----------|-----------------|
| Safety Risks (arXiv:2604.16968) | 良性经验累积侵蚀安全；需拒绝类经验平衡 | 已有 `boundary` type + recall 最低比例 + reflect 归因 |
| EvolveMem (arXiv:2605.13941) | 检索策略不应冻结 | 已有按 type 分流（启发式），无自适应进化 |
| Agent-Native Memory (arXiv:2606.24775) | memory 需完整生命周期；staleness 是首要风险 | 已有 created_at/status/superseded 机制 |
| Skill Evaluation Survey (arXiv:2606.11435) | 需纵向评测 + 库级压缩 | 已有库级健康复核（启发式），无精确度量 |
| Externalization (arXiv:2604.08224) | memory 是 context 非 enforcement；skill 需淘汰 | 明确声明 memory ≠ enforcement；已有淘汰候选流程 |
| Xinming Tu 3×3 | 区分 what evolves × when persists | scope 五类判定对齐 across-sessions/across-users 分离 |
| Mem0 Report 2026 | async writes; multi-scope tags; staleness最危险 | scope 标签对齐；staleness 机制已落地 |

## 最终建议：当前唯一应做的事

**Phase 4 负例 fixture**是当前投入产出比最高的动作。prose 设计已完备，但没有机器拦截意味着规则漂移是时间问题。建议的最小 fixture 清单：

1. `vendor/skills/` 下不存在非生成来源的 `.md` 文件
2. `skills/` 下每个目录名都出现在 `constants/skills.ts` 的某个 vendor 配置中
3. `rules/AGENTS.md` 中"记忆与持续进化闭环"段落包含关键文本锚点（`boundary`、`superseded`、`安全边界侵蚀`、`库级健康复核`）
4. `.airules/memory/*.md` 中所有正式 memory 文件的 frontmatter 包含 `created_at` 和 `status` 字段

其余 Phase 5 内容属于远期方向，不构成当前阻塞。
