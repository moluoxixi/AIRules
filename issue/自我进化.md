# 自我进化闭环：负反馈通路缺失

## 结论

当前自我进化闭环（`capture → distill → 审核转正 → recall → reflect → 再沉淀`）的正向积累路径设计合理，与 2026 年学术共识高度一致。但闭环**只有正向积累，没有负向反馈**——缺少"记忆过时了"、"skill 无效了"、"经验累积侵蚀了安全边界"的系统性检测与修正机制。这不是概念缺失（`issue/自我进化.md` 部分涉及），而是**现有路线图低估了负反馈的紧迫性**，且有三个 2026 年新论文揭示的风险点未被覆盖。

本 issue 聚焦"原 issue 未覆盖或严重度低估"的增量问题，已确认正确的设计不重复论证。

## 与原 `issue/自我进化.md` 的关系

原 issue 的 Phase 1-5 路线图仍然有效。本 issue 是对其的**增量补充**——识别三个新风险、升级两个已知问题的严重度、给出负反馈通路的具体设计建议。建议将本 issue 的结论并入原路线图的对应 Phase。

## 新发现的问题

### P0-new：良性经验累积导致安全退化

**来源**：On Safety Risks in Experience-Driven Self-Evolving Agents (arXiv:2604.16968, 2026-04)

**核心发现**：不需要对抗性注入，纯良性任务经验累积就能系统性侵蚀 agent 安全行为。7 个 LLM backbone 上复现了攻击成功率上升 48.6% 的结果，且一旦启动无自然恢复。机制归因（Integrated Gradients）表明检索到的经验在高层 attention 中持续覆盖安全指令，效果不同于简单的上下文延长。

**与 AIRules 的关联**：`recall-memory` 在每次任务起始读回 decision/gotcha/constraint，这些本质都是"执行偏见"（execution bias）——教 agent "如何做"，但从不教"何时拒绝做"。论文中的三类失败模式（Sensitive Execution、Standard Execution、Format Recovery）都可能在 AIRules 场景复现：被召回的过程模式覆盖了应当谨慎/拒绝的判断。

**当前设计缺口**：
1. memory type 只有 `decision`/`gotcha`/`constraint`/`reference`，没有"边界/拒绝"类型
2. recall 没有执行类记忆与拒绝类记忆的比例平衡机制
3. reflect 归因维度没有"安全退化"这一类别

**建议动作**：
1. 扩展 memory type 新增 `boundary`（何时不做/何时拒绝），或在 `constraint` 写入指南中强制要求包含负面边界
2. `recall-memory` 流程中保证边界类记忆的最低召回比例——每次 recall 结果中至少包含一条相关的 constraint/boundary
3. `reflect` 归因维度增加"安全边界侵蚀"类别，当产物越权/违反限制时可定位到经验积累导致的行为漂移

### P1-new：检索基础设施冻结

**来源**：EvolveMem: Self-Evolving Memory Architecture via AutoResearch (arXiv:2605.13941, 2026-05)

**核心发现**：存储内容持续进化但检索策略保持冻结时，检索质量必然退化。EvolveMem 通过 Evaluate→Diagnose→Propose→Guard 循环让检索配置自适应演化，在 LoCoMo 上实现 78% 的相对提升。不同类型的查询（事实查找、时序推理、多跳推断）需要根本不同的检索策略。

**与 AIRules 的关联**：当前 `recall-memory` 的检索策略是硬编码的——读 `MEMORY.md` 索引 → 按标题匹配 → 深读 topic。随着 memory 条目增长：
- 标题不总能反映内容与当前任务的语义关联（title 检索退化）
- 不同 `metadata.type` 的查询需要不同策略（`decision` 需时序倒排，`gotcha` 需文件关联匹配，`constraint` 需全量 scan）
- 无法知道"检索质量是否在下降"（无反馈信号）

**当前设计缺口**：原路线图 Phase 2 的 schema 扩展解决"数据维度"，但不解决"检索路由"。

**建议动作**：
1. Phase 2 中为 `recall-memory` 预留按 `metadata.type` 分流检索策略的接口（不同类型不同排序/过滤规则）
2. Phase 5 考虑引入最小检索质量反馈：recall 后如果用户明显忽略/覆盖了召回内容，记录为负信号


### P1-new：缺少纵向评测（skill 转正后是否真的有用）

**来源**：Agent Skill Evaluation and Evolution: Frameworks and Benchmarks (arXiv:2606.11435, 2026-06)

**核心发现**：该综述明确指出当前 skill evaluation 领域最大盲区是**没有任何基准测试能跨多轮反馈纵向追踪 skill 质量变化**。所有评测都是快照式的——转正时测一次就完事。推荐方向：skill 库应从静态仓库转变为"活的、被监控的基础设施"，evolution 和 evaluation 应是同一个持续学习过程的两面。

**与 AIRules 的关联**：闭环可以 capture→distill→转正，但没有回路测量"转正后的 skill 被 recall 了多少次？实际帮到了几次？被跳过/覆盖了几次？"这意味着：
- skill 库会退化为"未经验证的 prompt 片段堆积"
- 错误转正无法被自动检测和回退
- 无法回答"这个 skill 值得保留吗？"

**当前设计缺口**：原路线图 Phase 3 的转正门禁只管"入口质量"，不管"存续价值"。Phase 5 提到了评测，但缺具体最小可行度量。

**建议动作**：
1. Phase 3 转正时为每个 skill/memory 条目埋入最小度量字段：`metrics.recall_count`、`metrics.last_recall`、`metrics.override_count`（被用户覆盖/跳过的次数）
2. Phase 5 定义淘汰信号：如果 `override_count / recall_count > threshold`（如 70%），标记为 suspect 并触发复核
3. `distill-candidates` 增加"library-level"视角：扫描既有 skill 的度量数据，识别重复/过时/无效候选进行合并或淘汰建议

## 已知问题严重度升级

### Memory staleness：P1 → P0

**来源**：
- Are We Ready For An Agent-Native Memory System? (arXiv:2606.24775, 2026-06)
- State of AI Agent Memory 2026 (Mem0 Report, 2026-04)

**升级理由**：两篇独立来源均指出——高置信度但已过时的记忆比低相关性记忆**危害大得多**。它们是"confidently wrong"的，会以高权重被召回并误导决策。Agent-native memory 论文进一步证明没有生命周期管理的系统必然产出"过去的幻觉"（hallucinations of the past），且随时间推移检索准确率可从 37.1% 下降到 7.4%。

当前 3 字段 schema（`name`/`description`/`metadata.type`）下，已入库的记忆**没有任何衰减或过期信号**。一旦写入就永久 active。随着项目使用时间增长，错误记忆污染是确定性事件。

**建议动作**：将原 Phase 2 的最小 schema 扩展**提前到 Phase 1.5**——至少先加 `created_at` 和 `status`（active/superseded/archived），让 recall 有条件过滤。不需要一步到位补全 12 个字段。最小变更：
- `remember` 写入时自动填 `created_at`
- `remember` 更新时如果 supersedes 旧记忆，标旧记忆 `status: superseded`
- `recall-memory` 默认只读 `status: active`，superseded 不进召回

### Skill 库只增不减：P1 → P1（保持，但补淘汰路径）

**来源**：Agent Skill Evaluation and Evolution 综述识别四种演化范式：Execution Feedback、Trajectory Distillation、**Compression & Augmentation**、Reinforcement Learning。AIRules 当前只覆盖第二种（Trajectory Distillation），完全缺失第三种——库级结构优化（去重、合并、精简、淘汰）。Externalization 论文也指出 skill 需要"live signals such as retrieval frequency and runtime failure rates"驱动压缩决策。

**建议动作**：
1. Phase 3 或 Phase 4 补"skill 淘汰/合并"流程
2. 淘汰信号基于 retrieval frequency（长期不被触发）和 override rate（触发但被跳过）
3. `distill-candidates` 或新的 `skill-maintenance` 流程负责周期性扫描库级健康度

## 设计方向确认正确（无需改动）

以下经最新文献复核后确认设计正确：
- 人工审核门禁（安全退化论文进一步验证了"自动化只写候选区"的必要性）
- Memory 不是 enforcement（Externalization 论文和 AGENTS.md spec 共同确认）
- 双层 scope 分离（与 Xinming Tu 3×3 框架中 across-sessions / across-users 分离一致）
- capture 时打流标签 declarative/procedural（与 Externalization 论文 memory→skill promotion 路径一致）
- 冲突优先级 code > rules > memory（与 AGENTS.md "closest file wins" 一致）

## 总结：缺失的负反馈通路全景

```
当前闭环（只有正向）：
  capture → distill → 审核转正 → recall → reflect → 再沉淀
                                                      ↑ 循环

需要补充的负向通路：
  recall → 使用/跳过/覆盖 → 度量回写 ─┐
                                       ├→ staleness 检测 → supersede/archive
  memory 存续 → 时间衰减 + 事实复核 ──┘

  skill 存续 → recall_count / override_rate → 淘汰/合并建议

  经验累积 → 安全边界检测 → boundary 类记忆补充 → recall 比例平衡
```

## 建议路线图调整

| Phase | 原计划 | 建议增补 |
|-------|--------|----------|
| 1.5（新增）| — | 最小 schema：`created_at` + `status`，recall 过滤 superseded |
| 2 | schema 与索引 | 增加检索策略分流接口（按 type 路由） |
| 3 | 转正门禁 | 转正时埋度量字段；memory type 扩展 `boundary` |
| 4 | 最小自动化 | 增加淘汰信号 fixture（override_rate 超阈值 → suspect） |
| 5 | 评测闭环 | 纵向评测 + 检索质量反馈 + 安全边界监控 |

## 落地状态（2026-06-28）

本 issue 的建议已落地到规则资产，其中与 baseline「不搞无客观信号的重型治理」（`rules/AGENTS.md` 核心门禁取舍原则）冲突的项按 baseline 精神改为**轻量/启发式**形式，而非机械引入运行时计数器：

- **已落地（直接采纳）**：
  - `created_at` + `status: active|superseded` 写入 `remember` schema，`recall-memory` 默认只召回 `active`（对应 Phase 1.5）。
  - `boundary` memory type 加入 `remember` / `distill-candidates` schema；`recall-memory` 保证边界类最低召回比例。
  - `reflect` 归因维度新增「安全边界侵蚀」。
  - `recall-memory` 增按 `metadata.type` 的轻量分流检索（启发，非硬路由）。
- **已落地（按 baseline 精神改轻量）**：
  - 纵向 skill 度量（`recall_count`/`override_count`）**未引入精确计数器字段**——AIRules 是纯 prompt 项目、无运行时自增机制，改由 `distill-candidates` 的「库级健康复核」用扫描沉淀素材的启发式信号（长期不触发 / 触发屡被覆盖 / 已 superseded / 重复碎片）产出淘汰·合并候选，人工审核后执行。Phase 4 的「override_rate 阈值 fixture」相应改为启发式判断，不强求数值字段。

落地文件：`skills/remember`、`skills/recall-memory`、`skills/reflect`、`skills/distill-candidates`、`rules/AGENTS.md`（记忆与持续进化闭环段、reflect/distill/recall 条目）。
