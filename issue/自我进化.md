# AIRules 自我进化与记忆机制扩大知识源复核

## 结论

扩大知识源后，原先对 AIRules 自我进化闭环的主判断仍然成立，但需要把问题从“是否应该有记忆和 skill 自演化”推进到“如何防止长期上下文污染、如何评测 skill 是否真的有用、如何区分全局与项目资产、如何把自动化限制在候选区”。

AIRules 当前的方向是合理的：`capture → distill candidates → 人工审核转正 → recall → reflect → 再沉淀`，并把 procedural knowledge 路由到 skill，把 declarative knowledge 路由到 memory。这与 Reflexion、SAGE、ExpeL、Voyager、MemGPT/Letta、Claude Code memory、AGENTS.md、多数 self-evolving agents survey 的共同方向一致。关键差异在于，AIRules 是一个 rules/skills 元项目，不是单个 agent 私有运行时。因此它必须比论文原型和产品 auto memory 更保守：自动化只能生成候选、报告或待审清单，不能直接修改正式 `rules/`、根 `skills/`、正式项目 memory 或 `vendor/`。

二次评估后的核心结论是：AIRules 不缺“自我进化闭环”的概念，缺的是四类硬边界。第一，源资产层与投影产物层必须分离，`vendor/skills` 只能是生成物。第二，全局 skill、项目 skill、全局 memory、项目 memory 必须有 scope 判定和读取规则。第三，正式 memory 必须有生命周期和审计字段，否则错误记忆会被 recall 反复放大。第四，skill 候选转正必须引入评测或最小验证证据，否则 skill library 会退化成未经验证的 prompt 片段堆积。

## 扩大后的知识源覆盖

这次复核覆盖四类知识源。论文与综述侧包括 Reflexion、Voyager、ExpeL、SAGE、Self-Refine、MemGPT、MemoryBank、A-MEM、Toolformer、LATS、Agent-Pro，以及 Awesome Self-Evolving Agents 中整理的 memory architecture evolution、dynamic experience evolution、skill augmented evolution、agentic topology evolution 等分类。新增重点是 SAGE 对 checker、STM/LTM、reflection、MemorySyntax 的组合，以及 Agent Skill Evaluation and Evolution / SkillsBench 方向对 skill 定义、skill benchmark、skill evolution system design 的强调。

开源项目侧包括 Hermes Agent / hermes-agent-self-evolution、Letta/MemGPT、OpenHands、AutoGPT、DeerFlow 相关 self-evolution issue/RFC。这里最有价值的不是照搬某个项目目录，而是抽取机制边界：Letta 把 agent state 和 memory blocks 结构化管理；AutoGPT 把 workflow 拆为 blocks，并用 agbenchmark 做客观评估；OpenHands 强调 project workspace、filesystem 权限边界和多 agent 后端；Hermes 类项目强调从 execution traces 中发现失败模式，再沉淀技能或改写 harness。

产品与工程实践侧包括 QoderWork Awareness/Memory、Skills、Scheduled Tasks、Hooks、Dynamic Workflows，Claude Code memory / CLAUDE.md，AGENTS.md 规范，以及 Cursor rules 方向。新增关键事实是 Claude Code 明确区分 CLAUDE.md 与 auto memory：两者都会加载为上下文，但不是强制配置；强制行为应交给 hooks 或 settings。Claude Code auto memory 使用 `MEMORY.md` 作为入口索引，只加载前 200 行或 25KB，并按需读取 topic 文件。这与 AIRules 的“轻索引 + 命中深读”非常一致，也支持当前项目把 memory 视为 context 而非 enforcement。

行业机制侧包括 AGENTS.md 的“closest file wins”、多层项目上下文、工具尝试运行检查、跨工具共享项目指令，以及 agent benchmark 对真实任务、可判定结果、轨迹质量和失败恢复的要求。这些机制共同说明：自我进化资产不能只靠自然语言约定，需要层级、作用域、冲突优先级、评测门禁和可观测证据。

## 对 AIRules 当前设计的再评估

AIRules 的最大优点是已经把“自动产生经验”和“正式生效资产”分开。`distill-candidates` 生成候选，`remember` 负责显式记忆写入或审核后转正，`recall-memory` 只把 memory 当背景证据，`reflect` 做归因与路由。这比 Reflexion / SAGE 中把 reflection 直接写入长期记忆更适合工程仓库，因为仓库级记忆一旦错误，会污染后续所有维护任务。

但当前设计仍有一个危险倾向：文档里已经承认候选区和正式库分离，却没有把 scope 判定、分发登记、读取优先级、生命周期字段、评测证据做成足够硬的契约。外部资料反复说明，长期记忆与技能库的价值来自检索质量、适用条件、失败边界和验证反馈；如果只把会话总结成 Markdown 并放进长期目录，短期看像“会进化”，长期会变成不可验证的上下文垃圾。

从 SAGE 看，AIRules 应保留 checker 思想，但不应让 checker 只是另一个自评文本。SAGE 的 checker 用于质量门禁，Assistant 根据反馈迭代，直到 checker 接受或达到上限。对应到 AIRules，checker 应落成一致性评审、代码评审、测试输出、rules:check、workflow fixtures、候选转正 checklist，而不是再写一段“我认为这个候选有用”。

从 Letta/MemGPT 看，AIRules 应把 memory 当成有结构的 agent state，而不是无限追加日志。正式 memory 需要 `status`、`source`、`created_at`、`updated_at`、`reviewed_at`、`reviewed_by`、`related_files`、`supersedes`、`confidence`、`expiry_condition`。`MEMORY.md` 应是轻索引，不是事实全集；topic 文件才承载详细事实。索引必须小、稳定、可筛选；深读必须按任务相关性触发。

从 Claude Code memory 看，AIRules 当前“项目 memory 不是强制规则”的方向正确。CLAUDE.md / auto memory 都是上下文，不能替代 hooks/settings；同理，AIRules 中真正的强制约束应进入 `rules/AGENTS.md`、宿主项目 AGENTS/CLAUDE、脚本测试、hooks 或 CI。memory 只能提供背景和偏好，不能覆盖代码、当前项目文档或用户明确指令。

从 AGENTS.md 看，AIRules 需要吸收“nearest scope wins”的规则。全局规则、用户偏好、项目规则、子目录规则、项目 memory、全局 memory 都可能冲突。建议固定为：用户本轮明确要求 > 代码与当前项目文档 > 最近的项目规则文件 > 项目 memory > 全局 memory > 通用 skill 建议。memory 与规则冲突时，memory 应退让；全局偏好与项目事实冲突时，全局偏好应退让。

从 skill evaluation 方向看，AIRules 需要明确 skill 不是“写得像教程的 Markdown”，而是可复用、可触发、可验证的过程资产。一个 skill 候选要转正，至少要说明触发条件、反例、依赖、输入输出、失败模式、验证方法、与现有 skill/rules 的冲突检查；如果进入全局分发，还必须登记到 `constants/skills.ts` 并通过投影/安装相关检查。

## 关键风险重新分级

### P0：`vendor/` 仍可能被误用为源资产目录

`vendor/skills` 在当前安装与投影链路中是生成物或同步中间层，不是长期源资产。扩大知识源后，这个判断更强：无论是 Claude Code memory、Letta memory blocks，还是 AGENTS.md 项目规则，都把长期上下文放在明确的源位置或运行时状态里，而不是放在 build output。若把候选 skill、正式 skill 或 memory 写入 `vendor/`，会破坏 Git 审计、人审转正、生命周期管理和投影幂等性。

建议硬规则保持不变：`vendor/` 只允许由投影/安装脚本生成或同步；任何 `session-capture`、`distill-candidates`、`remember`、人工候选转正流程都不得写 `vendor/`；需要分发的全局 skill 必须从唯一源目录生成 `vendor/skills`，再从 `vendor/skills` 安装到宿主目录。

### P0：全局/项目 scope 不判定会导致资产污染

外部资料普遍区分用户级、项目级、路径级、运行时状态级上下文。Claude Code 有组织级、用户级、项目级、本地个人项目级、rules path scope；AGENTS.md 有 closest AGENTS wins；Letta 有 human/persona memory blocks。AIRules 如果不先判定 scope，就会把项目事实误写成全局偏好，把用户偏好误写进仓库，把局部 skill 误分发给所有项目。

建议候选转正前强制判定五类 scope：全局可分发 skill、项目局部 skill、项目 memory、用户运行时全局 memory、规则资产。只有第一类进入根 `skills/` 并考虑登记分发；第二类进入 `.airules/project-skills/` 或项目宿主 shared resources；第三类进入项目 `.airules/memory/`；第四类交给运行时 awareness/memory；第五类升级到 `rules/AGENTS.md`、项目 AGENTS/CLAUDE 或 hooks/CI。

**受众边界（关键）**：第一类的「写根 `skills/` + 登记 `constants/skills.ts` + 经 `vendor/skills` 投影」是 **AIRules 仓库维护者**才有的机制——用户项目里没有根 `skills/`，也不该有。因此 baseline 与闭环 skill 分发到用户项目后，「判出全局可复用洞见」的正确动作不是在用户仓库内写「全局」资产，而是把它作为**上游贡献候选**交人工决定是否回流 AIRules。这条边界必须在 prose 里写死，否则分发出去的 skill 会在用户项目里尝试执行一套根本不存在的目录机制。

### P0：自动反思直接转正会放大错误

Reflexion、SAGE、ExpeL 证明 reflection 有价值，但它们多数是实验系统或 agent 私有经验库。AIRules 的正式 rules/skills/memory 会影响未来仓库维护和用户项目分发，风险更高。错误 reflection 如果直接进入正式 memory，就会在每次 recall 时作为背景事实反复出现；错误 skill 如果进入全局分发，会改变多个宿主 agent 的行为。

建议自动化边界固定为：自动任务只能写 `.airules/sessions/`、`.airules/*-candidates/`、issue 报告、过期检查清单或评测报告；不得直接写正式 `rules/`、根 `skills/`、正式 `.airules/memory/`、`vendor/`。用户当场明确说“记住这条”是例外，因为这相当于人工审核。
### P1：memory schema 太薄，不足以支撑长期治理

当前正式 memory 如果只有 `name`、`description`、`metadata.type`，无法表达来源、审核、过期、替代、置信度和关联文件。Letta/MemGPT 的启示是记忆应是结构化 state；Claude Code auto memory 的启示是入口索引应轻量，详细 topic 文件按需加载；A-MEM、MemoryBank、MemGPT 等论文也都强调长期记忆需要检索、合并、遗忘和冲突管理。

建议正式 memory frontmatter 至少扩展为：`name`、`description`、`metadata.type`、`metadata.scope`、`metadata.status`、`metadata.source`、`metadata.created_at`、`metadata.updated_at`、`metadata.reviewed_at`、`metadata.reviewed_by`、`metadata.related_files`、`metadata.supersedes`、`metadata.confidence`、`metadata.expiry_condition`。`MEMORY.md` 只索引 active 记忆，superseded/archived 记忆不参与默认 recall。

### P1：skill 候选缺少评测门禁

Skill evaluation 相关资料显示，agent skill 需要定义、benchmark、评测、路由、组合和演化机制。Voyager 的 skill library 也依赖可执行验证和适用条件。AIRules 当前的 skill 候选如果只靠文本质量转正，会出现两个问题：一是重复 skill 越积越多；二是失败模式没有被真实任务验证。

建议 skill 候选转正最少需要四类证据：来源证据，说明来自哪次任务、哪段失败或哪类重复操作；适用证据，说明触发条件和不适用场景；验证证据，至少有一次真实任务、fixture、脚本检查或独立 reviewer 复核；冲突证据，说明与既有 rules/skills/agents 是否重叠或矛盾。进入全局分发的 skill 还必须有投影检查和宿主兼容性说明。

### P1：项目级 skill 分发缺少宿主探测协议

项目级 skill 不应像全局安装一样写入所有宿主目录。Claude Code、AGENTS.md、Cursor rules、OpenHands 等实践都说明项目上下文应跟实际项目结构和宿主能力绑定。若 AIRules 在项目里盲目创建 `.qoder/`、`.claude/`、`.cursor/`、`.agents/`、`.codex/`，会造成“幽灵启用”：目录存在本身可能改变宿主行为，但用户并没有选择启用该宿主。

建议项目级 skill 分发流程为：先检测项目根实际存在的宿主目录或显式 host 参数；再读取 `constants/hosts.ts` 的 `projectSharedResources`、`skillsDirName`、`agentFormat`、`excludedSkills` 等能力配置；只向命中的宿主投影；未命中时保留在 `.airules/project-skills/` 或输出待安装提示，不主动创建宿主目录。

## 已约束 vs 待强制（落差对照）

上节风险按「严重度」分级，但落地需要的是另一个维度：每条约束**当前是否已在 prose 写明、是否已有机器门禁强制**。三种状态决定它该进路线图哪一阶段——已约束、缺 fixture 的只需补负例；prose 缺的需先补写 skill/rule 表述；设计缺的需先定 schema/协议。混淆这三类会把「补一条断言」误判成「重写闭环」。

| 约束 | prose 现状 | fixture 现状 | 落差类型 | 阶段 |
|---|---|---|---|---|
| 自动 distill 只写候选区、不写正式库 | 已约束（`distill-candidates` 写入边界） | 无负例 | prose 已约束、缺 fixture | Phase 4 |
| `session-capture`/`remember` 禁写 `vendor/` | 已约束（各自写入边界） | 无负例 | prose 已约束、缺 fixture | Phase 4 |
| reflect 教训只路由、不自行固化 | 已约束（`reflect` 纪律末条） | 无负例 | prose 已约束、缺 fixture | Phase 4 |
| 记忆候选与 skill 候选同等待审 | 已约束（闭环各 skill + 项目 memory 决策记录） | 无负例 | prose 已约束、缺 fixture | Phase 4 |
| 候选转正前判 5 类 scope | prose 缺 → 本轮补写 | 无 | prose 缺、需补写 | Phase 1（本轮）/4 |
| 全局-项目两层 memory 读取 + 冲突优先级 | prose 缺 → 本轮补写 | 无 | prose 缺、需补写 | Phase 1（本轮）/4 |
| 全局 skill 必登记 `constants/skills.ts` 才算分发 | 部分（投影链路隐含） | 无负例 | prose 半缺 + 缺 fixture | Phase 3/4 |
| 项目 skill 不盲目创建宿主目录 | prose 缺 | 无 | prose 缺、需补写 | Phase 3/4 |
| 正式 memory 带状态/来源/审核/过期字段 | 设计缺（schema 仅 3 字段） | N/A | 设计缺、需新增 | Phase 2 |
| superseded memory 不进 active 召回 | 设计缺（无 status 字段） | 无负例 | 设计缺 + 缺 fixture | Phase 2/4 |

要点：多数 P0「红线」其实 **prose 已约束、只缺 fixture**——它们的真实风险是「规则漂移时无机器拦截」，而非「闭环没说」。真正的 prose/设计缺口集中在 scope 判定、两层 memory 协议（Phase 1 本轮补）与 memory schema（Phase 2）。路线图应据此分配工作量，不把补断言与补设计混谈。

## 推荐架构修正

第一，明确目录分层。全局可分发 skill 的唯一源目录可以继续是根 `skills/`，也可以后续迁移到 `resources/global-skills/` 或 `.airules/global-skills/`，但必须只有一个事实源。`vendor/skills` 是由该源目录投影出的 build output。项目局部 skill 使用 `.airules/project-skills/` 或候选区。项目 memory 使用 `.airules/memory/`。运行时全局 memory 不落在仓库里，而由 QoderWork/Claude Code/宿主 awareness 系统承载。

第二，明确 memory 读取协议。推荐顺序为：先读取运行时全局 memory 轻索引，用于用户偏好、跨项目习惯和通用 gotcha；再读取当前项目 `.airules/memory/MEMORY.md`，用于项目事实、项目约束、仓库决策和局部踩坑；最后按相关性深读 topic 文件。冲突优先级为：代码和当前项目文档 > 最近项目规则文件 > 项目 memory > 全局 memory。若项目 memory 与代码/文档冲突，应采用代码/文档，并标记该 memory 可能过期；若全局 memory 与项目 memory 冲突，应采用项目 memory。

第三，明确 enforcement 与 context 的边界。memory、session capture、候选报告都只是 context。真正的 enforcement 应写入 `rules/AGENTS.md`、项目 AGENTS/CLAUDE、宿主 rules、hooks、CI、脚本测试或 permission policy。这个边界与 Claude Code 的说明一致：CLAUDE.md 和 auto memory 都不是强制配置，强制阻断要靠 hooks/settings。

第四，给候选转正增加事务模型。skill 候选转正事务包括 scope 判定、frontmatter 校验、重复检查、冲突检查、验证证据、目标目录移动、必要时登记 `constants/skills.ts`、投影检查、review 记录。memory 候选转正事务包括 scope 判定、来源复核、当前事实复核、schema 补齐、重复/冲突检查、supersedes 关系处理、索引更新、review 记录。

第五，引入最小评测闭环。不要一开始做大而全的 self-evolution benchmark；先做小型 workflow fixtures 和候选转正 checklist。例如：错误 memory 不应默认召回；superseded memory 不应出现在 active 索引；未登记的全局 skill 不应被认为已分发；项目级 skill 在没有宿主目录时不应创建 `.claude` 或 `.qoder`；vendor 中的文件不应被识别为候选源资产。

第六，把 Scheduled Tasks / Dynamic Workflows 限制为维护助手。它们可以周期性扫描 sessions/changes，生成候选清单、过期 memory 清单、skill 失败模式清单和 issue 报告；也可以运行只读评测并输出复核结果。但它们不应自动修改正式规则资产。若未来要自动提交正式修改，也必须走 PR、人审、测试和独立评审。

## 分阶段实现路线

第一阶段只改文档契约，不改安装行为。更新 `session-capture`、`distill-candidates`、`remember`、`recall-memory`、`reflect` 和 `rules/AGENTS.md` 中关于候选区、正式库、scope、vendor、全局/项目 memory 读取协议的表述。目标是让所有参与闭环的 skill 对职责边界说法一致。

第二阶段补 schema 与索引。扩展正式 memory frontmatter；明确 `MEMORY.md` 索引格式，只索引 active 条目；定义 superseded/archive 的处理；补充缺失目录按需创建规则；修正 recall 初筛只能基于索引标题、钩子和少量 metadata，深读后才使用完整 description 的表述。

第三阶段补候选转正门禁。给 skill 候选和 memory 候选分别写转正 checklist；全局 skill 转正时要求检查 `constants/skills.ts`；项目 skill 转正时要求检查项目宿主目录或显式 host；memory 转正时要求检查 scope 与冲突优先级；vendor 写入作为硬失败。

第四阶段补最小自动化。新增或扩展 `rules:check` / workflow contract fixtures，覆盖 vendor 不作为源、全局 skill 必须登记、项目 skill 不盲目创建宿主、superseded memory 不默认召回、自动 distill 不能直接写正式库等负例。这个阶段的目标是防止规则漂移，不是模拟完整 LLM 行为。

第五阶段再考虑更强自演化。参考 SAGE checker、Hermes execution trace、SkillBench/Agent Skill Evaluation、AutoGPT agbenchmark 的方向，把成功/失败任务沉淀成可评测样例。但任何“自动生成 skill 并转正”的能力都应先在候选区运行一段时间，积累误报、重复、冲突和失败数据后再决定是否提高自动化程度。

## 验收标准

修复后应满足以下条件（每条均在上文有权威说明，此处只作可逐条核对的清单，不重述论证）：

- **自动化只写候选区**：任意自动提炼路径只能写 `sessions` / `candidates` / issue 报告，不能直接写正式 `rules/`、根 `skills/`、正式 `.airules/memory/` 或 `vendor/`。
- **转正前判 scope**：候选转正前必须判定 scope，且只落入全局 skill / 项目 skill / 项目 memory / 运行时全局 memory / 规则资产之一。
- **全局 skill 唯一源 + 投影**：全局 skill 必须来自唯一源目录，经 `vendor/skills` 投影到宿主；`vendor/skills` 不得人工维护（仓库内机制；用户项目内对应「上游贡献候选」）。
- **项目 skill 不盲建宿主目录**：只投影到已检测到的宿主目录或显式 host，不得盲目创建 `.qoder` / `.claude` / `.cursor` / `.agents` / `.codex`。
- **memory schema 完整**：正式 memory 带状态、来源、审核、时间、关联文件、替代关系、过期条件。
- **召回只读 active**：默认 recall 只读 active 索引与命中 topic，不读 superseded/archived。
- **memory 冲突优先级**：代码/项目文档 > 项目 memory > 全局 memory。
- **强制约束进规则资产**：enforcement 必须进 rules / AGENTS / CLAUDE / hooks / CI / 脚本测试，不能只写 memory。
- **skill 候选转正需验证证据**：至少一种验证证据，不能只凭文本完整性通过。
