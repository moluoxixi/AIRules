# 编排健壮性复核

## 结论

对照 2025–2026 多代理编排领域主要论文（Anthropic "Building Effective Agents"、OpenAI Agents SDK、Self-Evolving Agents Survey / Xinming Tu et al.、NemoClaw / NVIDIA、GEPA/Hermes governance）与开源实践（LangGraph、AutoGen、CrewAI），AIRules 编码流水线的核心架构（阶段契约、skill/agent 正交分层、reviewer≠coder 隔离红线、证据驱动完成判定、spec-workflow 按需三态持久化）稳健且符合工业界共识。

但存在 6 个结构性问题，按严重程度分级如下。

---

## P1：应尽快解决

### 1. 编排层缺少全局回路熔断（No Escalation Budget）

**现象**：流水线中存在两个主要回路——`Test FAIL → debugger → coder → Consist → Test` 以及 `Review FAIL → coder → ...`。`systematic-debugging` 内部有"同一方法失败两次则换方向"的铁律，但这仅约束 debugger 自身的诊断策略，**主编排层没有对应的全局重试上限或升级路径**。

**风险**：一个隐蔽的架构级 bug 可能让 debugger→coder→test 循环无限迭代，耗尽 token/budget 而无产出；对于分发到不同宿主（Claude 200k vs Cursor 32k）的场景，token 耗尽时机不可预测。

**学术对照**：
- Anthropic "Building Effective Agents" 的 evaluator-optimizer loop 明确建议设置 `max_iterations`，超限后将控制权交还人类或切换策略。
- NemoClaw (NVIDIA 2025) 的 ReAct 循环有 token-budget 和 step-budget 双约束。
- AutoGen 最新版本引入 `budget_manager` 组件做全局资源管控。

**建议修复**：
1. 在 `rules/AGENTS.md` 流水线 flowchart 的 `Test → Debug → Code` 回路和 `Review → Code` 回路各加一个计数器门（如 `max_loop: 3`）。
2. 超限后标 `BLOCKED`，生成 blocked summary（含已尝试路径与失败证据），升级给用户决策。
3. 可选：在阶段证据 schema 中增加 `loop_iteration` 字段，使回路次数可观测。

**影响范围**：`rules/AGENTS.md` 核心门禁节、流水线 Mermaid 图、`agents/debugger.md`、`skills/systematic-debugging/SKILL.md`。

---

### 2. 一致性评审的输入缺乏可机器比对的结构化锚点

**现象**：`consistency-reviewer` 的契约要求输入"最终 diff + 需求/计划/验收用例"，但验收用例由 `test-design` 以自然语言矩阵形式产出，一致性评审本质上是纯 LLM 语义推理，没有客观结构化锚点。reviewer 需要逐条人工对照自然语言表述是否覆盖，容易遗漏或误判。

**学术对照**：
- Google Vertex AI Agent Builder 和 LangGraph 的 structured output 模式强调"可机器验证的中间产物"。
- SAGE 的 checker 机制用结构化 checklist 做门禁判定，而非纯自然语言自评。

**建议修复**：
1. `test-design` 产出验收用例矩阵时，同时输出一份机器可解析格式（如 YAML checklist），每条包含 `id`、`description`、`acceptance_condition`。
2. `consistency-check` 加载该 checklist 后逐条打勾（`COVERED` / `NOT_COVERED` / `PARTIAL`），使评审结论可结构化追溯。
3. 不改变流水线拓扑，仅增强阶段间产物格式。

**影响范围**：`skills/test-design/SKILL.md` 输出契约、`skills/consistency-check/SKILL.md` 输入契约、`agents/consistency-reviewer.md`。

---

### 3. 并行 coder 实例缺少运行时冲突保障

**现象**：`dispatching-parallel-agents` 的触发条件是"互不写同一文件"，但该判定是 LLM 在派发前做的静态推理，没有运行时隔离保障。如果两个 coder 实例意外修改了同一文件的不同区域（共享 type 文件、barrel export、共享 util），合并时才发现冲突，需要人工介入。

**学术对照**：
- OpenAI Agents SDK 的 handoff 模型通过串行避免冲突（一次只有一个 agent 活跃）。
- Git worktree 隔离（项目已有 `using-git-worktrees` skill）是正确方向，但目前在 `dispatching-parallel-agents` 中未强制要求。

**建议修复**：
1. 把 worktree 隔离从"可选 skill"提升为并行 coder 的**默认模式**，写入 `dispatching-parallel-agents` 的前置条件。
2. 合并阶段增加 `git diff --check` + `git merge --no-commit` 冲突检测步骤，冲突时标 `BLOCKED` 并输出冲突文件列表。
3. 在 `subagent-driven-development` 的 implementer dispatch 流程中，显式声明"并行实例 MUST 使用 worktree 隔离"。

**影响范围**：`skills/dispatching-parallel-agents/SKILL.md`、`skills/subagent-driven-development/SKILL.md`、`skills/using-git-worktrees/SKILL.md`（可能需补充"并行场景"使用指引）。

## P2：设计改进空间

### 4. 代码评审路由缺少升级分类

**现象**：`Review FAIL` 统一路由回 `coder` 修复。但代码评审发现的问题可能属于两类完全不同的根因：A) 纯代码质量问题（命名、结构、性能），coder 可直接修；B) 需求理解偏差导致的实现方向错误，本质上应回溯到需求分析。当前流程把 B 类也路由给 coder，coder 只能在错误方向上继续修补。

**建议修复**：
1. 在 `code-reviewer` 的输出契约中增加 `escalation_type` 字段：`code_quality`（回 coder）vs `requirement_mismatch`（回溯到 brainstorming/planning）。
2. 主编排根据该字段决定路由目标，避免在错误基础上反复修补。
3. 可在 Mermaid 图中从 `Review` 节点拉出两条出边：`Review -->|code_quality FAIL| Code` 和 `Review -->|requirement_mismatch| Req`。

**影响范围**：`rules/AGENTS.md` 流水线图与阶段契约、`agents/code-reviewer.md` 输出格式、`skills/requesting-code-review/SKILL.md`。

---

### 5. 编排层对 token/cost 无感知

**现象**：编排完全基于逻辑阶段，没有 token 预算分配机制。一个大型任务如果在 brainstorming 阶段消耗了 60% context window，后续 plan→code→review 会被压缩或截断，但编排层不会主动干预。分发到不同宿主时（Claude 200k vs Cursor 32k vs Codex 128k），同一编排策略的可行性差异很大。

**学术对照**：
- AutoGen `budget_manager` 组件做全局资源管控。
- Claude Code 的 agent loop 有隐式 token 预算感知（`/compact` 自动触发）。
- NemoClaw 在 orchestrator 层分配每轮 step budget。

**建议修复**：
1. 在阶段契约中增加可选的 `budget_hint` 字段（百分比分配，如"requirements ≤ 15%, plan ≤ 15%, implementation ≤ 50%, review ≤ 20%"）。
2. 子代理在接近预算时主动精简输出或请求 handoff（触发 `handoff` skill），而非等到截断。
3. 这是软约束，不需硬编码数字；作为 guidelines 写入编排方法论即可。

**影响范围**：`rules/AGENTS.md` 阶段契约表、各 agent 文件（加"预算感知"指引段落）。

---

### 6. `MISSING blocked` 缺少结构化传播追踪

**现象**：多个阶段都可能报 `MISSING blocked`，但目前没有集中的 blocked-item ledger。如果 brainstorming 产出的需求事实源中某字段标了 `MISSING`，下游的 plan、test-design、code 都会各自独立报 blocked，主代理需要自行追踪哪些 MISSING 是同源的、解除一个 MISSING 后哪些下游可以解锁。

**建议修复**：
1. 在编排层引入轻量 `blocked_registry` 概念（可以是内存中的 list 或文件），记录每个 MISSING 的：源头阶段、原始标识、影响的下游阶段、解除条件。
2. 当用户澄清解除某个 MISSING 时，主代理据此批量解锁下游，而非逐阶段重新发现。
3. 这可以作为 `subagent-driven-development` 的 progress ledger 的扩展字段。

**影响范围**：`rules/AGENTS.md` 阶段证据 schema、`skills/subagent-driven-development/SKILL.md` progress ledger 设计。

## 已知限制（记录但不要求修复）

### spec-workflow archive 语义冲突

`spec-archive.mjs` 的合并顺序（RENAMED→REMOVED→MODIFIED→ADDED）只处理文本冲突（硬失败），语义冲突（如一个 MODIFIED 改变了某个 ADDED 依赖的前提条件）无法被脚本检测。当前硬失败策略是合理的保守选择，记录为已知限制。

## 建议优先级

1. **P1-1 全局回路熔断** — 唯一可能导致任务卡死或资源耗尽的结构性风险，应最先修复。
2. **P1-3 并行冲突保障** — 并行是性能关键路径，冲突会导致返工，投入产出比高。
3. **P1-2 结构化验收锚点** — 提升一致性评审质量上限，但不阻塞当前流程。
4. **P2-4/5/6** — 按迭代节奏逐步落地，可与 `issue/自我进化.md` Phase 2-5 协调。

## 落地状态（2026-06-28）

6 个问题均已落地到规则资产，与 baseline「不搞无客观信号的重型治理」冲突的项按 baseline 精神改为软约束/可选形式：

- **P1-1 全局回路熔断**：`rules/AGENTS.md` 流水线图加回路计数与 `BLOCKED` 升级边；核心门禁新增第 9 条「回路熔断」（`max_loop` 默认 3）；`agents/debugger.md`、`skills/systematic-debugging` 明确区分「编排层全局熔断」与「debugger 局部两次换向」两层。
- **P1-2 结构化验收锚点**：`skills/test-design` 增产机器可解析 YAML 验收清单（`id`/`description`/`acceptance_condition`）；`skills/consistency-check`、`agents/consistency-reviewer` 按 `id` 逐条标 `COVERED`/`NOT_COVERED`/`PARTIAL`。
- **P1-3 并行冲突保障**：`skills/dispatching-parallel-agents` 把 worktree 隔离提升为并行**写**代码子代理的默认，合并前做 `git diff --check` + `git merge --no-commit` 冲突预演；`skills/subagent-driven-development` 声明并行实例 MUST worktree；`skills/using-git-worktrees` 补并行场景指引。
- **P2-4 升级路由**：`agents/code-reviewer`、`skills/requesting-code-review` 输出加 `escalation_type`（`code_quality` 回 coder / `requirement_mismatch` 回溯需求）；流水线图 `Review` 拉出两条出边。
- **P2-5 token 感知（改软约束）**：阶段证据 schema 加**可选** `budget_hint`（百分比软分配，不硬编码数字）；`agents/coder` 加预算感知段，接近预算时主动精简或触发 `handoff`。
- **P2-6 blocked 传播（改可选）**：阶段证据 schema 加可选 `blocked_id`；实现挂 `skills/subagent-driven-development` 进度账本扩展，仅多任务同源阻塞时启用，不另立强制登记表。
