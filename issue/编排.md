# 评估：当前 AIRules 编码生命周期流程编排的设计问题与改进建议

## 背景

本 issue 评估当前 AIRules 编码生命周期编排是否存在结构性问题。评估对象包括 `rules/AGENTS.md` 中的全局 baseline、`agents/*.md` 子代理定义、`skills/spec-workflow` 及测试/计划/评审相关 skills、架构文档与历史计划文件。外部参考包括 ReAct、Reflexion、Tree of Thoughts、ReWOO、LLMCompiler、SWE-agent、MetaGPT、ChatDev、Self-Refine、Constitutional AI、Voyager、Toolformer、Generative Agents 等论文，以及 OpenSpec / spec-driven development、Anthropic Agent Skills / slash commands、Superpowers、OpenAI Agents SDK、context engineering 等工程实践。二次扩大知识源后，又补充对 agentic software engineering benchmark、tool-use benchmark、RAG/context/memory 评估与主流 coding-agent 工程实践的检索，覆盖 SWE-bench / SWE-bench Verified、AgentBench、ToolBench / API-Bank 类工具使用评估、OpenHands / CodeAct、Agentless、AutoCodeRover、LiveCodeBench、GraphRAG / RAGAS / CRAG / DSPy / MemGPT 类上下文与记忆系统，以及 Cursor rules / AGENTS、Aider、OpenHands、SWE-agent、GitHub Copilot coding agent、Gemini CLI、Claude Code 和 Superpowers 等实践。

结论先行：当前主线方向整体正确。它把软件工程 SOP 显式化为“需求事实源 → 计划/验收 → 实现/TDD → 验证 → 调试回环 → 一致性评审 → 独立代码评审 → 规格归档/记忆沉淀”，与主流 agent 论文和 OpenSpec / Superpowers 类实践高度一致。扩大知识源后，上一版判断没有被推翻，反而被 SWE-bench、SWE-agent、OpenAI Agents SDK、AgentBench 与 Agent Skills 的证据强化：可靠 coding agent 的关键不是角色数量，而是可验证任务、清晰 handoff、guardrails、真实测试、可观测轨迹和可审查长期上下文。需要补充的是，当前 issue 不能只关注流程文案漂移，还应关注“评估基准缺位”和“运行证据结构化不足”：AIRules 作为 prompt/rules 元项目，应有少量回归型 agent workflow fixtures 来验证规则资产是否真的约束了行为，而不是只校验文件是否存在。

主要问题仍集中在三个层面：一是流程图、阶段契约、agent/skill 文案之间存在时序漂移；二是 accepted ADR / architecture docs 与当前 5-agent 设计严重不一致；三是轻量化后缺少最小内容完整性与流程行为回归门禁，导致 prompt/rules 元项目的规则资产漂移无法被机器发现。二次评估新增的判断是：第三点应从“引用存在性检查”扩展为“引用存在性 + 关键流程 fixture + 证据 schema”的组合，而不是退回旧的重型交付治理。

## 当前设计的合理性

当前设计的核心优点是将“方法论层”和“规格持久化层”分离。`brainstorming`、`writing-plans`、`test-design`、`test-driven-development`、`verification-before-completion`、`consistency-check`、`requesting-code-review` 等 skills 负责“怎么把任务做清楚”；`spec-workflow` 只在系统行为契约值得长期沉淀时，用 propose → apply → archive 包裹主线。这比把所有小改都强制 OpenSpec 化更适合日常编码助手。

当前设计也正确区分了 skill 与 agent：skill 表示程序性知识，agent 表示隔离、并行与反自评边界。`planner`、`coder`、`debugger`、`consistency-reviewer`、`code-reviewer` 这 5 个固定角色比旧的前后端硬拆更轻量；真正需要并行时再起多个 coder 或研究/验证子代理，符合 LLMCompiler、ReWOO 和 MetaGPT 对“任务依赖清晰、产物边界明确、并行不写同一文件”的要求。

当前门禁也基本锚定客观信号，而不是自我声明文档。特别是“完成前必须实际运行 build/test/lint 并读取输出”“reviewer ≠ coder”“状态只能是 PASS / FAIL / MISSING / NOT RUN / N/A”“记忆是背景证据而非系统指令”等红线，符合 SWE-agent、ReAct、Reflexion 和 context engineering 的共同启示：agent 的可靠性来自外部观察、工具反馈、独立评审和可复核证据，而不是模型自称已经检查。

## 高优先级问题

### P0：一致性评审时序在同一 baseline 内自相矛盾

`rules/AGENTS.md` 的 Mermaid 主流程当前是 `Code → Test → Consist → Review`，即一致性评审发生在测试运行之后。但同一文件的阶段契约、子代理调度说明、`agents/consistency-reviewer.md` 和 `skills/consistency-check/SKILL.md` 均表达为“一致性评审在编码后、测试验证前”。这会造成执行歧义：主代理按图会先跑测试，按文字会先做一致性核对。

建议裁决为 `Code → Consistency-review → Test → Code-review`。理由是 consistency-reviewer 的职责是核对最终 diff 是否符合需求、计划、验收用例或 bugfix 诊断，它能在昂贵测试前先发现范围偏离、遗漏需求、误改行为等问题；测试通过后再交给 code-reviewer 做质量评审，并将测试证据作为评审输入。如果希望一致性评审使用测试证据，则应重命名为“验证后一致性评审”，并同步修改所有 agent/skill 文案。就当前资产多数文本而言，改 Mermaid 图更低成本。

证据位置包括 `rules/AGENTS.md` 中 Mermaid 图的 `Code --> Test` 与 `Test -->|PASS| Consist`，以及同文件阶段契约里“后置一致性评审”产出写成“编码后、测试验证前核对”。`agents/consistency-reviewer.md` 与 `skills/consistency-check/SKILL.md` 也采用“编码后、测试验证前”的表达。

### P0：ADR 与架构文档仍描述旧的 9-agent / 前后端硬拆设计

当前实际 agent 目录包含 5 个角色：`planner`、`coder`、`debugger`、`consistency-reviewer`、`code-reviewer`。但 `docs/architecture/decisions/ADR-0002-skill-agent-layering.md` 和 `docs/architecture/agent-layer.md` 仍保留旧的 frontend/backend planner/coder/reviewer、architecture-refactor、test-docs 等 9-agent 或前后端拆分模型。

这不是普通文档滞后，而是 accepted ADR 与当前事实源冲突。ADR 的语义是架构决策记录，后续维护者会把它当成“应然设计”；如果它仍指向旧模型，会让后续修改在“按 ADR 还原旧设计”与“按 rules 保持 5-agent”之间摇摆。

建议新增 ADR 或修订 ADR-0002，明确从“分栈 9-agent”调整为“5-agent + 按需多实例 + skill/agent 两层解耦”的决策，并同步更新 `docs/architecture/agent-layer.md`。如果保留 ADR 历史不改，应至少把状态标记为 Superseded，并指向新 ADR。

### P0：轻量化后缺少最小内容完整性与流程行为回归门禁

`.claude/plans/gate-lightweight.md` 记录了删除与分发/安装无关的 skills/agents 内容校验。当前 `package.json` 中也没有 `rules:check`、`verify:skills`、`delivery:verify`、`verify:knowledge-sources` 等脚本，`.husky/pre-push` 只跑 typecheck。删除重型治理是合理的，但当前状态把 prompt/rules 元项目最需要的自洽性检查也一起删除了。

这直接导致本次评估发现的漂移无法被机器发现：流程图和文字时序冲突、ADR 仍引用旧 agent、architecture overview 仍引用已删除 verify 脚本、spec-workflow 文案与 archive 脚本行为不一致。对于一个专门维护 AI rules / skills / agents 的元项目，最小内容门禁不是“额外治理”，而是防止规则资产自相矛盾的基础设施。

二次扩大知识源后，这个问题需要升级表述：不只是“引用存在性检查缺失”，还包括“流程行为回归样例缺失”和“运行证据 schema 缺失”。SWE-bench / SWE-bench Verified 的关键启示是，coding agent 评估必须绑定真实 issue、可复现环境和可判定结果；AgentBench / ToolBench / API-Bank 类评估说明，agent 能力应按任务完成、工具使用、失败恢复和轨迹质量衡量；OpenAI Agents SDK 的 guardrails / tracing 也说明，流程编排需要输入校验、输出校验和可观测执行轨迹。对应到 AIRules，不能只检查 `agents/*.md` 是否存在，还应至少用小型 fixtures 验证“缺计划时 coder 应阻断”“未运行测试时不能报告 PASS”“reviewer 与 coder 不能同实例”“spec archive 前置条件不满足时不能归档”等关键行为契约。

建议不要恢复旧的重型变更包或全量纯净校验，而是新增最小自洽性与流程回归检查：`rules/AGENTS.md` 中引用的固定 agent 必须存在；agent frontmatter 中引用的 skill 必须存在；`constants/skills.ts` 分发清单中的 skill 目录必须存在；架构文档不得引用已删除的一方 agent 名；spec-workflow 文案中的关键前置条件必须与脚本支持的行为一致；docs/architecture/overview.md 不得列出 package.json 中不存在的质量脚本；同时新增少量文本级或脚本级 workflow fixtures，用于验证关键门禁的期望状态枚举和阻断语义。这里的目标不是模拟完整 LLM，而是把 AIRules 自己声明的 SOP 转成可回归的最小契约。

## 中优先级问题

### P1：spec-workflow 的 archive 前置条件与主流程不一致

`rules/AGENTS.md` 的主流程要求代码评审 PASS 后才进入 spec archive。但 `skills/spec-workflow/SKILL.md` 对 archive 的描述更像“实现完成、测试通过后即可归档”，没有显式要求 consistency-reviewer 与 code-reviewer 通过。

这会造成一个危险路径：执行者如果只按 spec-workflow skill 操作，可能在没有完成独立评审的情况下，把 delta 合并进长期 `.airules/specs/`。一旦归档过早，错误规格会进入长期事实源，并影响后续 recall / planning / implementation。

建议统一 archive 前置条件为：实现完成、验证 PASS、一致性评审 PASS 或 N/A、代码评审无阻塞项。该条件应同时写入 `rules/AGENTS.md`、`skills/spec-workflow/SKILL.md`，并由脚本或最小校验机制尽可能验证。

### P1：spec-archive 允许“无 delta spec”归档，削弱规格契约语义

当前 spec-workflow 文案要求规格路径产出 `proposal.md + specs/<capability>/spec.md(delta) + tasks.md`，并进行 `spec-validate`。但 `skills/init-project/scripts/spec-archive.mjs` 在没有 delta spec 的情况下仍可移动 change 到 archive，并输出“无 delta spec”。这使“走了规格契约路径”与“长期规格事实源发生变化”之间脱钩。

建议默认禁止无 delta 归档。如果确有纯文档或纯流程 change 需要归档，应显式提供 `--allow-empty`，并在 skill 中限定使用场景。`spec-validate.mjs` 在指定 change-id 时也应校验 proposal、tasks、至少一个 delta spec 的存在性，除非显式允许空变更。

### P1：proposal.md / tasks.md 只有模板，没有确定性校验

`spec-new-change.mjs` 会创建 proposal 和 tasks 模板，但模板里包含占位符与空 bullet；`spec-validate.mjs` 只校验 delta spec 格式，不校验 proposal 的 Why / What Changes 是否非空，也不校验 tasks 是否包含实际任务、archive 前是否全部 `[x]`。

这会使 propose 阶段看起来完成，但关键动机、范围与执行闭环可能仍是空的。OpenSpec / Spec Kit 类实践的核心价值正是把聊天意图固化为可审查的文件，如果这些文件没有最小内容检查，spec-workflow 会退化为目录搬运。

建议把最小校验加入 `spec-validate` 或新增专门脚本：proposal 必须存在；Why 和 What Changes 去掉注释后非空；tasks 至少包含一个复选框任务；archive 前 tasks 必须全部完成，除非显式 `--allow-incomplete`。

### P1：知识源 ADR 与当前仓库状态漂移

`docs/architecture/decisions/ADR-0001-knowledge-source-registry.md` 仍描述 `airules.knowledge.json`、`knowledge-search` skill 和 `verify-knowledge-sources.mjs`，但当前工作区中这些资产已删除或不再作为当前机制存在。与此同时，`brainstorming` / `writing-plans` 仍提到先读代码、文档、知识源补齐事实。

建议裁决知识源机制是否废弃。若废弃，应新增 ADR 说明从 registry 模式改为普通文件检索、CodeGraph、recall-memory 或宿主 MCP 检索，并把 ADR-0001 标记为 Superseded。若保留，则恢复最小 registry 和校验，并同步 package scripts。

### P1：docs/architecture/overview.md 描述已删除的质量脚本

`docs/architecture/overview.md` 仍列出 `scripts/verify-*.mjs`，并描述 PR 阶段执行 `delivery:verify`、`verify:rules:self-sufficiency`、`verify:skills`、`verify:knowledge-sources` 等门禁。但 `package.json` 当前没有这些命令。

建议同步 architecture overview 到当前真实状态。若要恢复最小内容门禁，应先在 package scripts 和脚本目录落地，再让 overview 描述它们；否则 overview 应明确当前只保留 build/lint/test/typecheck/install 相关校验。

### P1：缺少统一的执行证据 schema，导致 PASS / FAIL / MISSING 难以审计

当前 baseline 已要求状态只能使用 PASS、FAIL、MISSING、NOT RUN、N/A，并要求实际运行 build/test/lint 后读取输出。但它没有定义每个阶段交付给下游的证据最小字段。SWE-agent、OpenAI Agents SDK tracing、AgentBench / ToolBench 类评估共同说明，agent workflow 的质量不仅取决于最终答案，还取决于可追踪的工具调用、失败恢复、输出校验和状态转换。

建议在 rules 或 verification skill 中定义轻量 evidence schema，而不是恢复冗长交付模板。最小字段可以包括：阶段名、状态枚举、输入资产、执行命令或只读证据来源、关键输出摘要、失败原因、下游依赖、是否阻断。测试验证阶段必须记录实际命令与退出状态；一致性评审必须记录比对对象和结论；代码评审必须记录 reviewer 与 coder 的实例隔离；spec archive 必须记录 change-id、校验命令、归档目标和是否有 delta。这样可以让“诚实状态报告”从自然语言约定变成可审计结构。

### P1：缺少 workflow fixture，无法验证规则资产是否真的约束 agent 行为

扩大 benchmark 知识源后，上一版“补最小内容完整性校验”的建议需要进一步具体化。SWE-bench 的核心价值不是题目数量，而是将真实 issue、仓库状态、测试结果与评分规则绑定；SWE-bench Verified 进一步强调样本质量和人类验证。AIRules 不需要构建大型 benchmark，但应有少量小型 fixtures 来验证自身规则是否可执行。

建议新增 `__test__/workflow-contract.test.ts` 或类似脚本，覆盖最小正反例：缺少需求事实源时 planner/coder 应输出 MISSING blocked；未运行验证时不得出现 PASS；spec change 没有 delta 时 validate/archive 应失败；架构文档引用不存在脚本时检查失败；agent frontmatter 或 rules 引用不存在 skill 时检查失败；同一实例自评应被规则文本显式禁止。这类 fixture 可以是文本规则断言、脚本行为断言和少量模拟 change 目录，不需要调用真实 LLM。

### P1：子代理 handoff 上下文包没有标准化

当前 `rules/AGENTS.md` 只要求“每次委派必须自包含；子代理回传必须由主代理用 diff、命令输出、日志或 URL 复核”。这个方向正确，但仍偏抽象。OpenAI Agents SDK 的 handoffs、Anthropic Agent Skills 的 progressive disclosure、ReWOO / LLMCompiler 的计划变量依赖都指向同一个工程结论：handoff 必须携带稳定输入包，否则子代理会在缺失上下文时自行补全事实。

建议为固定 agent 定义最小 context packet：planner 需要需求事实源、相关代码/文档证据、验收目标和未知项；coder 需要冻结计划、验收用例、目标文件范围、禁止事项和测试优先级；debugger 需要失败命令、完整错误摘要、相关 diff、已排除假设和只读边界；consistency-reviewer 需要最终 diff、需求/计划/验收用例、允许的 N/A 条件；code-reviewer 需要最终 diff、测试证据、需求摘要和 review rubric。该标准不必成为新文档模板，可以直接放入各 agent 文件或一个共享 skill reference。

## 低优先级问题

### P2：planner 是否必须派发的语义略有冲突

`rules/AGENTS.md` 的核心门禁说“计划默认是一个阶段，不强制拆成独立 agent”，但子代理调度索引又把“计划 → planner”写成固定路径。建议补一句：planner 是可派发角色；简单任务可由主代理在当前上下文按 `writing-plans` 与 `test-design` 完成，只有命中隔离、并行或独立性时才派 planner。

### P2：Superpowers 第一方化后仍有少量重型治理词汇回流

`rules/AGENTS.md` 明确将强制变更分级视为重型治理，不属于普通编码任务；但 `skills/executing-plans/SKILL.md` 与 `skills/finishing-a-development-branch/SKILL.md` 的收尾模板仍含“变更分级”。建议替换为“风险/范围摘要”或“变更范围”，避免 L0/L1/L2 式治理概念通过 skill 回流。


## 外部资料对当前流程的映射

ReAct 证明 agent 需要在 reasoning 与 tool observation 之间循环，支持 AIRules 在需求分析、调试、资料检索中采用“先读代码/查资料补事实，再计划”的模式。Reflexion、Self-Refine 与 Constitutional AI 支持 critique / reflection 的价值，但也说明自评不能替代外部反馈；这正好支持 AIRules 保留测试输出、独立评审和状态枚举，而不是依赖模型自称已检查。Tree of Thoughts 支持复杂设计先生成多个候选方案再筛选，但不应对小改强制启用，否则会变成过度治理。

ReWOO 与 LLMCompiler 支持将依赖清晰的任务先规划为 DAG，再并行执行工具或子任务；这与 AIRules 的“多源只读调研、跨模块扫描、批量验证可派临时子代理”一致，也支持继续限制“写同一文件或强耦合修改不并行”。SWE-agent 强调 agent-computer interface 决定软件工程能力上限，因此 AIRules 里“读 diff、读测试输出、读日志、debugger 只读诊断、reviewer 基于最终 diff”都是高价值规则。

MetaGPT 与 ChatDev 支持将软件工程 SOP 编码为多智能体流程，但它们也提醒多 agent 的收益来自中间产物、检查点和失败回退，而不是角色数量本身。因此当前从 9-agent / 前后端硬拆收敛到 5-agent + 按需多实例是正确方向。Voyager、Generative Agents 与 Reflexion 支持长期 memory / skill library，但也暴露污染风险；AIRules 的 capture → distill candidates → 人工审核 → recall → reflect 闭环比自动写入更适合 rules 元项目。

OpenSpec / spec-driven development 对 AIRules 的启示是：规格路径应该显式包含 propose、apply、verify、archive，并把 delta 合并进长期 source-of-truth spec。AIRules 当前已经同构，但需要补强 verify/archive 前置条件和 proposal/tasks/delta 的最小确定性校验。Anthropic Agent Skills 与 Superpowers 的启示是：skill 应采用渐进披露，常驻 baseline 只保留红线和调度，具体流程放入按需 skill；但 Superpowers 的“任何可能适用都必须先调用 skill”不宜完全照搬，否则会损害小改低摩擦原则。

二次扩大知识源后，benchmark 类资料带来的主要校准是：AIRules 不能只声明 SOP，还要有极小规模的回归评估资产。SWE-bench / SWE-bench Verified 说明 coding-agent 评估应绑定真实仓库状态、可执行测试和可判定结果；AgentBench 说明通用 agent 评估应覆盖多环境任务完成，而不是单轮回答；ToolBench / API-Bank 类资料说明工具调用质量需要看参数选择、结果利用和失败恢复。对应到本仓库，合理的落点不是引入大型 benchmark，而是建立 workflow-contract fixtures 和 evidence schema，把“缺事实源阻断、未验证不得 PASS、评审实例独立、spec archive 不可空归档”等规则转成可回归断言。

context engineering、GraphRAG / RAGAS / CRAG / DSPy / MemGPT 类资料对上一版结论的修正是：记忆与知识源不能只讨论是否存在，还要讨论检索边界、优先级、冲突规则和评价方式。当前 issue 已指出 ADR-0001 与知识源机制漂移；二次评估后应补充：如果知识源 registry 被废弃，替代方案必须说明普通文件检索、CodeGraph、项目 memory、全局 memory、MCP 外部资料之间的读取顺序和冲突处理，否则“先读代码、文档、知识源补齐事实”的门禁会变成不可执行口号。

主流 coding-agent 实践带来的校准是：OpenAI Agents SDK 的 handoffs / guardrails / tracing、Claude Agent Skills 的 progressive disclosure、Cursor / AGENTS 的项目规则、Aider / OpenHands / SWE-agent 的仓库内编辑与测试闭环，都支持 AIRules 的“常驻 baseline 只放红线，细节按需 skill，子代理按隔离/并行/独立性拆分”。但它们也共同要求更明确的上下文包和权限边界。AIRules 已经规定 debugger 只读、reviewer 独立、子代理回传需复核；下一步应把这些要求落实到每个 agent 的最小输入包和 evidence schema，而不是只写在总规则里。

## 建议修复范围

建议拆成六个后续实现 issue 或 PR。

第一个修复应统一编码生命周期时序与 agent/skill 文案，主要涉及 `rules/AGENTS.md`、`agents/consistency-reviewer.md`、`skills/consistency-check/SKILL.md`、`skills/spec-workflow/SKILL.md`。目标是明确一致性评审到底在测试前还是测试后，并统一 archive 的前置条件。

第二个修复应同步架构文档和 ADR，主要涉及 `docs/architecture/decisions/ADR-0002-skill-agent-layering.md`、`docs/architecture/agent-layer.md`、`docs/architecture/overview.md`，必要时新增 ADR 取代旧 9-agent 决策。

第三个修复应补 spec-workflow 的最小确定性门禁，主要涉及 `skills/init-project/scripts/spec-validate.mjs`、`skills/init-project/scripts/spec-archive.mjs` 及相应测试。目标是禁止默认无 delta 归档，校验 proposal/tasks 的最小内容，并在 archive 前确认 tasks 完成。

第四个修复应恢复轻量内容完整性校验，主要涉及新增或恢复一个小脚本和 package script。该脚本不做重型治理，只检查 agent/skill/rules/docs 的引用存在性与明显漂移，例如旧 agent 名残留、分发清单目录不存在、overview 引用不存在的 npm scripts。

第五个修复应新增 workflow-contract fixtures 和 evidence schema。fixtures 用于验证关键门禁的最小正反例，不调用真实 LLM；evidence schema 用于约束阶段输出的最小审计字段，避免 PASS / FAIL / MISSING 只停留在自然语言约定。

第六个修复应明确知识源读取协议和子代理 handoff context packet。知识源协议需要裁决 ADR-0001 的去留，并说明普通文件、CodeGraph、项目 memory、全局 memory、MCP 外部资料之间的读取顺序和冲突规则；handoff context packet 需要给 planner、coder、debugger、consistency-reviewer、code-reviewer 定义最小输入包与回传证据。

## 验收标准

修复完成后，`rules/AGENTS.md` 的流程图、阶段契约、子代理触发说明、agent 文件和 skill 文件应对一致性评审时序给出同一答案。架构文档应只描述当前 5-agent + 按需多实例模型，或明确旧模型已被 supersede。spec-workflow 应不能在默认模式下把没有有效 delta、没有有效 proposal、没有有效 tasks 的 change 归档。package scripts 应包含一个低成本内容自洽性检查，并能在本仓库发现旧 agent 名、缺失 skill 引用、缺失 npm script 引用这类问题。workflow-contract fixtures 应覆盖至少四类负例：缺上游事实源、未运行验证却报告 PASS、reviewer 与 coder 未隔离、spec archive 空 delta。阶段输出应有轻量 evidence schema，能记录状态、输入资产、命令或证据来源、失败原因和阻断关系。知识源读取协议应说明 registry 废弃或保留后的替代链路，并定义项目 memory、全局 memory、代码/文档和外部资料的冲突优先级。固定 agent 的 handoff context packet 应能让子代理在缺少关键输入时报告 MISSING blocked，而不是自行补事实。所有状态报告继续使用 PASS、FAIL、MISSING、NOT RUN、N/A，不引入重型变更分级作为普通编码任务门禁。
