# 编排健壮性二轮复核

## 结论

二轮复核基于对 `rules/AGENTS.md`、所有 skill/agent 文件、`__test__/workflow-contract.test.ts` 和 `scripts/check-rules-consistency.ts` 的逐字审读，并对照 2025–2026 多代理编排论文（Anthropic "Building Effective Agents"、OpenAI Agents SDK、Self-Evolving Agents Survey、NemoClaw、GEPA/Hermes governance、SAGE）与开源实践（LangGraph、AutoGen、CrewAI）。

上一版 `issue/编排.md` 的 6 个结构性问题（回路熔断、结构化验收锚点、并行隔离、升级路由、token 感知、blocked 传播）**均已落地到当前规则资产中**：Mermaid 图有 `max_loop` 计数边与 `BLOCKED` 升级、核心门禁第 9 条明确回路熔断、`test-design` 已产出 YAML 验收清单、`dispatching-parallel-agents` 已强制 worktree 隔离、`escalation_type` 拆分已在 Review 节点、`budget_hint` 与 `blocked_id` 作为可选字段存在。

但深读后发现 **5 个新的、确实未覆盖的问题**，属于第一轮未触及的盲区。

---

## P1：结构性风险

### 1. `Consist→Code` 回路缺少独立的熔断计数

**现象**：Mermaid 图中 `Consist -->|不符| Code` 形成一个回路：`Code → Consist → (不符) → Code`。核心门禁第 9 条和阶段证据 schema 显式标注了两条回路的 `max_loop`——`Test→Debug→Code` 和 `Review→Code`——但 `Consist→Code` 回路**不在此列**。

如果一致性评审持续判定"不符"，coder 修改后再由 consistency-reviewer 审，这个回路在到达 Test 之前可以无限循环。当前设计隐式依赖"总会通过 Consist 到达 Test，再被 Test 的 max_loop 兜住"，但如果 Consist 始终不通过，流程永远不会到达 Test，Test 的熔断也就永远不会触发。

**学术对照**：Anthropic "Building Effective Agents" 的 evaluator-optimizer pattern 对每个 evaluator 回路都单独设 budget，不依赖下游 evaluator 做兜底。LangGraph 的每条 conditional edge 都可以挂 `max_retries`。

**建议修复**：
1. 在核心门禁第 9 条中显式列出第三条回路：`Consist→Code` 回路也受 `max_loop` 约束（可共享默认值 3，也可独立设为 2）。
2. Mermaid 图的 `Consist -->|不符| Code` 边改为 `Consist -->|"不符 (回路计数 < max_loop)"| Code`，并加一条 `Consist -->|"回路计数 ≥ max_loop"| Blocked`。
3. 或者在文字说明中明确"三条回路"而非当前的"两条"。

**影响范围**：`rules/AGENTS.md` 核心门禁第 9 条、Mermaid 流水线图、`agents/consistency-reviewer.md`（如有执行说明）。

---

### 2. `requirement_mismatch` 外层回路无显式熔断

**现象**：`Review -->|"requirement_mismatch FAIL"| Req` 构成一条外层回路：`Req → Plan → Code → Consist → Test → Review → (mismatch) → Req`。核心门禁第 9 条的 `max_loop` 作用于 `Test→Debug→Code` 和 `Review→Code`（`code_quality` 分支），但 `requirement_mismatch` 分支把控制流路由到 Req 而非 Code，不计入 `Review→Code` 的 loop_iteration。

如果需求始终被误解（例如用户表述模糊、LLM 在 brainstorming 阶段反复产出偏差需求事实源），这条外层回路无上限。每次绕完一圈都是全新的 Plan→Code→Test→Review 周期，token 消耗巨大。

**学术对照**：NemoClaw 对 outer 和 inner loop 都有独立的 step budget。AutoGen 的 `budget_manager` 是全局 token 预算，覆盖所有回路不论层级。

**建议修复**：
1. 为 `requirement_mismatch` 回路设一个独立计数器（如 `mismatch_loop`，默认 2），达到上限即 `BLOCKED`。理由：方向性错误反复出现说明需求本身存在无法自动解决的歧义，应升级用户而非继续尝试。
2. 或在 `budget_hint` 层面用 token 消耗总量做兜底——当总 token 消耗超过某阈值时，无论哪条回路都强制 BLOCKED。
3. 最轻量方案：在核心门禁第 9 条补充一句"requirement_mismatch 回溯 Req 也计入回路计数（与 code_quality 共享或独立计数均可），达到 max_loop 同样标 BLOCKED"。

**影响范围**：`rules/AGENTS.md` 核心门禁第 9 条、Mermaid 图（可选：`Review -->|"requirement_mismatch FAIL (mismatch_loop < max)"| Req`）。

## P2：设计改进空间

### 3. `subagent-driven-development` 的 fix→review 循环不引用外层 `max_loop`

**现象**：`skills/subagent-driven-development/SKILL.md` 定义了自己的执行流：`implementer → task reviewer → (FAIL) → fix subagent → task reviewer (复审)`。这个 fix→review 循环**没有迭代上限**，也没有引用 `rules/AGENTS.md` 中的 `max_loop` 机制。

当前设计的隐式假设是"subagent-driven-development 运行在主编排之内，外层 max_loop 会兜住"。但 `subagent-driven-development` 是一个 skill 文档——它被 coder/main agent 加载后执行，其内部 fix→review 循环是在**同一阶段**（实现）内部发生的，不会触发外层 Test→Debug→Code 回路的计数器。

**建议修复**：在 `subagent-driven-development/SKILL.md` 的 fix→review 流程中显式声明："同一 task 的 fix→re-review 循环不得超过 N 次（建议 2），超限标该 task 为 BLOCKED，汇入主编排的升级路径。" 这与 debugger 的"同一方法失败两次换方向"铁律对齐。

**影响范围**：`skills/subagent-driven-development/SKILL.md`。

---

### 4. 合约测试未覆盖 `Consist→Code` 回路与 `requirement_mismatch` 回路

**现象**：`__test__/workflow-contract.test.ts` 的"编排红线文本"部分验证了：
- Consist 时序正确（`Consist -->|符合| Test` 存在，旧边不存在）
- `reviewer ≠ coder` 文本存在
- `MISSING blocked` 文本存在
- 禁止未读输出声称通过文本存在

但**未验证**：
- `Consist -->|不符| Code` 边是否有熔断标注（或文本中是否提及 Consist 回路的 max_loop）
- `Review -->|"requirement_mismatch FAIL"| Req` 路径是否有计数/熔断文本
- "三条回路"或类似表述存在于核心门禁

这意味着如果后续重构意外删除了 Consist→Code 的熔断机制，合约测试不会报警。

**建议修复**：在 `__test__/workflow-contract.test.ts` 的"编排红线文本"部分增加断言：
1. `rules/AGENTS.md` 包含对 Consist→Code 回路有界性的文字（如 `Consist` 回路或三条回路的表述）。
2. `rules/AGENTS.md` 包含 `requirement_mismatch` 路径的回路约束（如关键词 `mismatch_loop` 或将其纳入 `max_loop` 描述）。

**影响范围**：`__test__/workflow-contract.test.ts`

### 5. `recall-memory` 的 boundary 最低召回机制是完全静默的 opt-in

**现象**：`recall-memory` 规定"每次召回至少含一条相关的 constraint/boundary 记忆"以防止安全边界侵蚀，但紧接着说"本项目无 boundary 记忆时跳过，不硬凑"。

这意味着：一个从未显式写过 `constraint`/`boundary` 类记忆的项目，永远不会享受这一保护机制。更重要的是，**没有任何提示告诉用户或 agent 该项目缺少 boundary 记忆**——机制静默跳过，不发出 warning、不在 recall 输出中标注"当前项目无 boundary 记忆，安全边界侵蚀风险未受保护"。

对照 `rules/AGENTS.md` 的"安全边界侵蚀"归因（reflect 的第五种根因），如果 recall 没有机会提供 boundary 上下文，reflect 诊断时也无法将其与"缺少 boundary 记忆"关联。

**学术对照**：SAGE 的 checker/guardrails 层是强制的——即使没有用户定义的规则，也有默认 safety guardrails 在运行。MemGPT/Letta 的 memory init 阶段会创建 system-level 默认 blocks。

**建议修复**（轻量，不破坏"不硬凑"原则）：
1. 当 recall 发现当前项目无任何 boundary/constraint 记忆时，在召回输出末尾附一行提示（如 `[info] 当前项目未定义 boundary 记忆，安全边界侵蚀保护未激活`）。
2. 或在 `init-project`/`remember` 的初始化指引中建议用户写入至少一条项目级 boundary 记忆（如"本项目不得直接操作生产数据库"之类的基线约束）。
3. 不改"跳过"行为本身——只增加可观测性。

**影响范围**：`skills/recall-memory/SKILL.md`、可选影响 `skills/init-project/SKILL.md`。

## P3：可观测性改进（记录备查）

### 6. 流水线执行缺少聚合 trace 格式

当前每个阶段产出证据 schema（阶段名、状态、命令、输出），但没有一个聚合格式把一次完整的流水线执行串起来——回路实际进了几次、每阶段耗时/token、最终路径是什么（走了哪些分支）。

这不影响正确性，但影响后续的 self-evolution 数据质量：`session-capture` 采集的是原始会话文本，难以从中准确重建"这次 Consist→Code 回路进了 2 次、第 1 次因为漏覆盖验收用例 TC-03 被打回"这样的结构化轨迹。

**建议**（远期）：定义一个可选的 pipeline execution trace schema（JSON 或 YAML），在阶段转移时追加记录，使 distill-candidates 和 reflect 可以直接消费结构化轨迹而非从自然语言文本推断。与 `issue/自我进化.md` Phase 5（执行轨迹分析）协同。
