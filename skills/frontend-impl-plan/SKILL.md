# Frontend Impl Plan（前端实现计划 / 任务书）

补齐 need → plan → test → code 链路中的「前端 plan」环节：在 PRD 和测试设计就绪后、正式写前端代码前，按业务域产出可评估、可执行的前端实现任务书，让开发者先看清「前端打算怎么做」，再驱动前端代码生成。

本 skill 只负责前端侧。后端数据模型、接口实现、服务分层属于 `backend-impl-plan`，因为前后端的上下文来源、关注点与编码范式完全不同，混在一份 task 里会稀释各自的可评估性。

## 触发条件

- PRD（`docs/prds/` 或指定 PRD）与测试设计已就绪，需要在写前端代码前先出前端实现方案时使用。
- 用户要求生成前端实现计划、前端任务书、页面/组件落地方案、前端开发任务拆解时使用。
- 前端代码生成前需要一份可评估的中间产物（含组件用法、布局、状态管理、API 调用、前端测试）时使用。

## 不适合场景

- 只需直接改少量前端代码、无需先出实现方案时不使用。
- 需要后端实现方案（数据模型、接口实现、服务分层）时用 `backend-impl-plan`。
- PRD 关键事实缺失、未确认（大量 `MISSING`）时，不臆造实现细节；先回到澄清门禁补齐需求。
- 纯需求/纯测试/纯组件契约文档的产出，分别用 `prd-docs`、`test-docs`、`components-docs`。

## 输入

- 需求：`docs/prds/<业务域>.md`（背景、流程、字段口径、验收标准、状态规则）。
- 测试：`docs/test/<业务域>.md` 或对应测试用例（用例矩阵、回归范围）。
- 组件：`docs/components/`（外部组件库消费约束，如 Element Plus 用法）、`docs/out-components/`（本项目自有组件契约）。
- 接口契约（只读消费）：`docs/api/`、`docs/out-api/`（如存在）——前端按契约调用，不在此设计后端接口。

## 前置门禁

- 本环节是实现编码前的最后一道设计门禁，前置依赖需求、API/组件契约、测试设计三者就绪：开始前必须确认对应业务域的 `docs/prds/<模块>.md` 与 `docs/test/<模块>.md` 存在且非草案、关键事实非 `MISSING`；涉及接口/组件时确认 `docs/api/`、`docs/components/`、`docs/out-components/` 对应契约就绪。
- 上游缺失或仍为草案/大量 `MISSING` 时，报告 `MISSING blocked`（说明缺失的上游产物）并停止，不得臆造需求、用例或契约继续出实现计划。
- 可运行 `node <AIRules>/scripts/verify-stage-gate.mjs <project-root> frontend-plan <模块>` 做确定性前置校验；校验失败按 `MISSING blocked` 处理，不得绕过。

## 输出边界

- 默认只写 `docs/plan/frontend/<需求模块>.md` 和 `docs/plan/frontend/index.md`（前端自有索引）；用户显式指定其它位置时按指定位置写，并在文档开头说明实际位置与未同步索引的事实。
- 不写共享的 `docs/plan/index.md`：该文件若由前后端两个 skill 并发写会相互覆盖（已在纯净测试中复现）。本 skill 只维护自己目录下的 `docs/plan/frontend/index.md`；后端索引归 `backend-impl-plan` 写 `docs/plan/backend/index.md`，两者互不写对方目录，从源头消除并发写冲突。需要项目级总览时由非并发环节单独维护一份静态 `docs/plan/index.md` 指向两个子索引，本 skill 不触碰该文件。
- 不直接生成业务代码；本 skill 只产出前端实现方案，代码由后续代码生成环节按 task 执行。
- 不设计后端接口、不定义数据模型；只按已有 API 契约描述「前端如何调用」。发现契约缺失时标 `MISSING`，不自行约定后端接口。
- 不修改 PRD、测试、组件契约的事实口径；发现与上游冲突时标记 `MISSING` 并列出冲突，不静默改写。
- 不得把密钥、token 等凭证明文写入；以配置项名称引用。

## 输出位置

- 任务书：`docs/plan/frontend/<需求模块>.md`，一个需求模块一份；多模块时先在 `docs/plan/frontend/index.md` 出前端任务总览（脑图 + task 导航）。
- 必须按需求模块拆分为多个文件，每模块一份；严禁把多个模块的 task 正文混写进同一文件，也严禁把所有模块汇总成单份长文档。

## 拆分粒度（关键）

- 拆分单位是「需求模块 / 功能模块」，不是粗粒度的产品域。判定粒度时跟随上游已有的最细拆分：优先对齐 PRD 业务流程与页面划分，其次对齐 `docs/test/` 用例分组与 `docs/api/` / `docs/out-api/` 接口模块。
- 上游若已把一个产品域拆成多个功能模块（如「基础主数据 / 供应商发货点 / 店仓关系 / 品仓 / 仓仓线路 / 供货管理 / 供货路由」），前端任务书必须同样拆成对应的多份，而不是合并成一份产品域大文档——合并会稀释每个模块的可评估性。
- 一个需求模块对应一份任务书；模块边界以「能独立评审一块前端实现方案」为度。若上游确实只有单一模块的确认事实，则只产出该一份，并在 index 标注其余模块为 `MISSING`（上游未就绪）。

## 多域并行委派（该代理就代理）

- 当本次计划覆盖 2+ 相互独立的需求模块、且各模块写入 `docs/plan/frontend/<模块>.md` 互不重叠时，默认每个模块派一个 fresh 子代理产出该模块前端任务书，主代理只做拆分、整合与复核，避免多模块上下文互相污染。
- 委派为各子代理精确构造自包含上下文：对应模块的 PRD、测试设计、组件契约（`docs/components/`、`docs/out-components/`）、API 契约路径与本 skill 的产物结构要求；子代理不继承主会话历史。
- `docs/plan/frontend/index.md`（前端任务总览）由主代理在收齐各模块产物后单独维护，不交给并发子代理写，从源头消除索引并发写冲突。
- 单一模块、或模块间存在强共享前置（如统一设计令牌、跨页面状态约定需先定稿）时不并行，由主代理串行产出或先定稿共享前置再派子代理，并在交付中说明。
- 子代理回传是自述；主代理必须按本 skill 的产物结构与可追溯要求复核每份任务书，确认 `MISSING` 标记完整后才算就绪。

## 计划粒度（关键）

- 本 skill 产出的是「前端实现思路 / 方案」，供人评估「前端打算怎么做、对不对」，不是逐步施工脚本。
- 写到「需求来自哪里、调用哪些接口、使用或封装哪些组件、页面怎么布局、组件怎么拆、状态怎么管、前端测试覆盖哪些用例」这一层的具体思路即可；能让评审判断方案正确性就够。
- 禁止套用通用 `writing-plans`/superpowers 计划格式：不写 `- [ ]` 勾选步骤清单、不写逐 Step 的 RED-GREEN-REFACTOR、不写每步的具体命令/commit、不展开成上千行施工手册。
- 禁止输出到 `docs/superpowers/plans/`；该目录是通用计划格式领地，与本 skill 的「方案级、按域拆分」产物不同。
- 每份任务书保持紧凑（聚焦思路），用 Mermaid 图 + 表格表达方案，而非长流程正文。

## 写作规则

- 变更分级（L0/L1/L2）与澄清门禁的定义见「变更分级与澄清门禁」一节：下游已安装项目在根 `AGENTS.md` 注入块，AIRules 仓库本身在 `rules/AGENTS.md`，就近读取，找不到时按 L2 从严处理。
- 生成 task 前必须先读取对应业务域的 PRD、测试、组件契约；事实以这些上游文档为准，缺失内容标记 `MISSING`，不从代码或想象补业务规则。
- 命中澄清门禁时（涉及前端架构边界、跨页面状态、关键交互流程等关键事实缺失或歧义），先输出《前端实现澄清问题清单》，未确认内容保留 `MISSING`，不臆造方案。
- 每个业务域 task 内部按「实现大纲图（图在前）+ 需求来源 + 使用/封装组件 + 页面布局 + 组件树 + 状态管理 + 调用接口（API 调用） + 测试落地 + 风险待确认」组织。
- 需求来源必须显式列出 PRD 路径/章节、验收标准、测试用例号或用户确认记录；缺少可核对来源的实现项标 `MISSING`。
- 使用/封装组件必须区分外部组件库（`docs/components/`）、本项目自有组件（`docs/out-components/`）和本次计划新增封装，标注类型（使用/封装）、来源与约束。
- 调用接口只描述前端视角：调用哪个接口、方法、契约来源、入参、返回、错误处理；接口本身的设计归 `backend-impl-plan`，此处缺失契约时标 `MISSING`。
- task 必须可追溯：每条实现项标注其来源 PRD 章节、验收标准或测试用例编号，不凭空新增需求。
- 生成实现任务拆解前，先调用 `knowledge-search` 在 `airules.knowledge.json` 登记来源中定位组件契约（`docs/components/`/`docs/out-components/`）、用例（`docs/test/`）、需求（`docs/prds/`）；无登记来源支撑的实现项与组件用法不得进入计划，标 `MISSING`，不得凭组件库通用知识或代码命名补全。
- 任务书是评估与执行材料；用户基于它评估确认后，再进入前端代码生成。

## 配图规则

- 图用 Mermaid 代码块（` ```mermaid `），放在每份 task 最前面作为实现大纲，可在语雀、GitHub、VSCode 直接渲染。
- 选图由内容驱动：
  - 前端任务脑图（`mindmap`）：必出，呈现该业务域前端任务拆解。
  - 页面布局图（`flowchart` 或 `graph`）：有页面时出，表达区域划分与组件位置。
  - 组件树（`flowchart`）：组件层级与数据流。
  - 调用时序（`sequenceDiagram`）：前端调后端 API、跨组件交互必出（前端视角）。
  - 状态机（`stateDiagram-v2`）：存在前端交互状态流转时出。
- 无法确认的节点、接口或字段显式标 `MISSING`；不伪造确定结论。

（拆解单位是「可独立评审/可独立验收的一块前端实现」，不展开到逐行代码或 commit；依赖排序遵循前端内在顺序：类型/契约 → 复用组件 → 页面与组件树 → 状态 → API 调用 → 测试；「可并行」只标无文件/状态耦合的任务，有共享状态或同一组件改动的任务标串行；每个任务必须有独立验收并指向用例号，无对应用例标 MISSING）

- **任务ID**：稳定标识，形如 `FT-<模块>-<序号>`（如 `FT-发货点-002`），跨版本不复用，供并行 coder 子代理与 `consistency-check` 按 ID 精确派发与追溯。
- **目标文件路径**：该任务预计新增/修改的主要文件路径（如 `src/views/shipping/ShippingDialog.vue`）；尚不确定时标 `MISSING`，不臆造路径。
- **`[P]` 并行标记**：「可并行」列为「是」即等价于可标 `[P]`，取自该列「无文件/状态耦合」的既有语义，不另立判定口径。
