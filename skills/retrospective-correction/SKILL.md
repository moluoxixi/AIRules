# Retrospective Correction

## 触发条件

- 用户指出"实现和我要求的不一致""你理解错了""这不是我要的""偏了""规则没按"等偏差。
- 用户要求分析为什么偏差发生，或判断是 AI 执行错误、skills 缺口、rules 缺口还是需求不明确。
- 已完成的代码、文档、测试、计划或规则生成结果需要先修正方向，再决定是否更新 AIRules。

## 不适合场景

- 用户只是提出新的需求、补充信息或正常变更方向，并未指出既有结果偏离要求时不要使用。
- 偏差只涉及文字措辞、格式微调或用户已明确给出直接修改指令时，可按轻微偏差直接修复，不启动重大偏差流程。
- 需要从零设计新规则或新 skill，而不是修正既有偏差时，应先走对应设计或文档流程。

## 经验复用（启动前必做）

- 在开始任何重大任务前，应先检索 `docs/retrospective-corrections/` 是否有相关历史纠偏记录，把其中的「预防规则」作为本次执行的硬约束。
- 若目录不存在或无相关记录，视为无历史约束，按正常流程推进；不得因缺记录而阻断。

## 分级处理

### 轻微偏差

满足全部条件时，可直接修复并在最终回复中简短说明偏差与验证结果：

- 用户反馈指向明确，期望结果没有歧义。
- 修改范围小，不涉及架构、需求口径、公共协议、rules/skills 或跨模块行为。
- 不需要判断长期根因，也不需要沉淀流程改造。
- 可以用现有测试、构建、文档检查或用户指定标准验证。

### 重大偏差

符合任一条件时，必须先输出《改动计划清单》，等待用户确认后再修复和归因，并在修复验证后强制写入纠偏记录：

- 偏差涉及用户需求理解、验收标准、架构边界、公共协议、数据口径或安全边界。
- 修复会修改 rules、skills、初始化流程、默认分发配置或多处模块。
- 用户要求分析"为什么会偏""是谁的问题""规则要不要改"。
- 同类偏差重复出现，可能是 `SKILL_GAP`、`RULE_GAP` 或系统性流程缺口。

## 共同规则

- 先读取用户原始要求、最新反馈、当前实现、已使用的 rules/skills、相关测试和验证输出。
- 不得在标准未确认前做最终归因；不得用"规则不清楚"替 AI 执行错误开脱。
- 若判断需要修改 skills 或 rules，重大偏差必须先提出更新建议；未经用户确认不得直接改。
- 只有重大偏差需要生成独立纠偏记录；轻微偏差在最终回复中说明即可。
- 原因分析必须明确判断主因是 `AI_EXECUTION_ERROR`、`SKILL_GAP`、`RULE_GAP`、`REQUIREMENT_AMBIGUITY`、`CONTEXT_LOSS` 还是 `TOOL_OR_ENVIRONMENT`，并说明为什么不是其它分类。

## 流程

1. **检索历史**：开始前检索 `docs/retrospective-corrections/`，将相关记录的预防规则纳入本次约束。
2. **分级判断**：判定是轻微偏差还是重大偏差，并说明依据。
3. **轻微偏差路径**：读取证据，直接修复，运行必要验证，最终回复说明偏差、修复和验证结果。
4. **重大偏差路径**：用用户语言复述偏差点和期望结果，列出证据，输出《改动计划清单》等待确认。
5. **标准确认**：用户确认计划后，将计划中的期望结果转成明确验收标准。
6. **原因归因草案**：基于证据形成待验证分类，不猜测、不甩锅。
7. **执行修复**：按确认后的计划修改，并运行必要验证。
8. **写入纠偏记录（重大偏差强制）**：修复并验证后，按下方格式将根因、纠偏内容和预防规则写入新记录文件。
9. **最终回复**：重大偏差链接纠偏记录；轻微偏差只需摘要说明修复和验证结果。

## 纠偏记录输出（重大偏差强制）

- 默认路径：`docs/retrospective-corrections/<YYYY-MM-DD>-<kebab-title>.md`。
- 重大偏差修复后必须写入纠偏记录，这是把本次经验转为下次约束的强制步骤，不得跳过。
- 若项目没有 `docs/`，创建 `docs/retrospective-corrections/`；若用户指定路径，使用用户指定路径。
- 记录必须是本次修复新建文件，不得覆盖旧记录；同名冲突时改用更具体文件名。
- 若文件系统不可写，必须在最终回复标记 `FAIL retrospective document` 并输出完整记录内容；不得伪造成已写入。
- 记录必须在修复和验证之后生成；不得在修复前用未验证结论定稿。
- 「预防规则」必须是可执行、可在下次任务直接遵守的具体约束，一行一条；不得写成空泛感想。
- 根因需对照《原因归因分类》给出一个主因；存在多个因素时在根因中列为次因。

## 纠偏记录格式

```md
# <偏差标题>

## 根因
<根因分析，含主因分类和说明>

## 纠偏内容
<做了什么修正，含验证结果>

## 预防规则
- <规则1：条件 + 应做/禁止，可下次直接执行>
- <规则2>
```

## 改动计划清单格式

```md
# 改动计划清单

## 偏差点

## 期望标准

## 拟修改范围

| 项 | 文件/模块 | 修改内容 | 验证方式 | 风险 |
|---|---|---|---|---|

## 是否可能需要更新 rules/skills

## 等待确认
```

## 原因归因分类

| 分类 | 含义 |
|---|---|
| `AI_EXECUTION_ERROR` | 现有要求、rules 或 skills 已清楚表达，但 AI 没有遵守或执行遗漏。 |
| `SKILL_GAP` | 应触发的 skill 缺少必要流程、检查点、反例或输出格式。 |
| `RULE_GAP` | 项目 rules 没有覆盖该约束，或表达模糊、冲突、不可执行。 |
| `REQUIREMENT_AMBIGUITY` | 用户要求存在多个合理解释，且未提供足够验收标准。 |
| `CONTEXT_LOSS` | AI 未读取、遗漏或误用已有上下文、文档、代码或前序结论。 |
| `TOOL_OR_ENVIRONMENT` | 工具、依赖、平台、权限、缓存或外部状态导致结果偏差。 |

## 示例

以下内容是示例模板，仅供参考，不得作为真实业务事实自动应用。

```md
# init-project 误注入 base 占位

## 根因
主因 `RULE_GAP`：现有 rules 未区分新建与已有 `AGENTS.md`，脚本无论文件是否存在都注入。次因：无。

## 纠偏内容
修改脚本，已有非空 `AGENTS.md` 时跳过注入。`npx vitest run tests/init-project-scripts.test.ts` PASS。

## 预防规则
- 处理 AGENTS.md 注入前先判断文件是否已存在且非空，已有则跳过。
- init-project skill 中写明新建与已有文件的差异化处理逻辑。
```
