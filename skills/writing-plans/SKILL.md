# 实现计划

把需求事实源拆成可执行、可追溯的实现任务，每项任务都能回溯到需求与对外契约。跨前后端适用，按任务实际触及的栈填写对应字段。计划面向"对本代码库零上下文的实现者"撰写：写清要动哪些文件、各文件职责、如何验证。

## 触发条件

- 需求事实源已就绪、即将进入实现编码
- 需要把需求拆解为可追溯到验收标准的实现任务

## 不适合场景

- 需求仍为草案或关键事实 `MISSING` → 先回到需求分析
- 单行/单点小改且无契约影响 → 主代理直接实现，不需要正式计划
- 测试用例设计 → 由 `test-design` 承担，本 skill 只引用其产出

## 任务切分与质量要求

- **文件结构先行**：定义任务前，先列出将创建/修改的文件及各自单一职责，把分解决策锁定下来；改动应内聚，变更同进退的文件放在一起。
- **每个任务落档为独立 md（强制，跨栈）**：无论前后端，**每个 task 必须落成一个独立的 md 文件**（多文件），一任务一文件；**禁止把多个任务合并进单一 plan 文件**。切分单位按栈确定——前端 = 页面，后端 = 内聚交付单元（一个能力 / 一组端点 / 一个领域模块，即"自带测试闭环、值得一次独立评审"的最小交付）。
- **前端按页面拆分（强制）**：前端任务的顶层切分单位是**页面**（不是业务模块），一页一个 task md 文件。跨页面共享的组件/逻辑单独成 task 文件或在组件复用分析中登记，不塞进某个页面任务里。
- **任务足够小**：一个任务是"自带测试闭环、值得一次独立评审"的最小单元；把配置、脚手架、文档步骤折叠进它服务的任务里，只在评审者能独立通过/驳回相邻任务时才切分。
- **步骤清晰**：每个任务以一个可独立验证的交付物结束；步骤描述要具体到可执行，避免 "TBD/TODO/适当处理/类似上一个" 等占位写法。
- **类型一致**：后续任务引用的类型、签名、属性名必须与前序任务定义一致。

## 计划必须包含的可追溯字段

每个实现任务必须写明以下字段——依据任务触及的栈，该栈标注的字段为必填，未标注栈的字段可省略：

- **需求来源**：对应需求事实源/验收标准的哪一条
- **接口设计**：新增/修改的接口签名、入参出参、错误约定（后端）
- **调用接口**：调用了哪些后端/外部接口（前端）
- **数据模型**：涉及的实体、字段、存储结构（后端）
- **代码分层与职责**：改动落在哪一层、各层职责（后端）
- **事务与一致性**：事务边界、并发、幂等约束（后端，涉及时）
- **字段级配置**：本页面涉及的查询字段、列表列、详情表单字段，逐字段列出（前端，页面任务必填）
- **页面布局**：区域划分（如筛选区/列表区/操作区）、关键交互区、路由结构，粒度到区域/层级即可（前端，页面任务必填）
- **组件复用分析**：跨模块可复用的既有组件（复用哪个）与需额外封装的新组件（为何封装、供哪些页面共用），分两类列出（前端）
- **类型（使用/封装）**：涉及的类型定义与来源（前端）
- **性能边界**：可度量的性能约束，如首屏/接口耗时阈值、列表虚拟化触发行数、查询无 N+1、分页必选、并发/超时上限（跨栈，涉及时必填，必须写成可判定阈值而非"要快"）
- **契约来源**：依据的 API/组件/数据契约出处；项目文档契约可引用 `.airules/knowledge/` 下的文件路径

## 自检

计划写完后，以新视角对照需求事实源核对：

1. **需求覆盖**：逐条扫需求/验收标准，能否指到对应任务？列出缺口并补任务。
2. **占位扫描**：搜 "TBD/TODO/待补/适当处理" 等红旗，逐个补实。
3. **产物形态可判定性**：布局、性能边界等形态字段是否写成可核对的条件（区域/层级、量化阈值）？含糊表述（"要好看/要快"）降级为噪声，就地改成可判定条件或删除。
4. **类型一致**：后续任务用到的签名、属性名是否与前序定义吻合。

发现问题就地修复，无需重审。

## 两路任务落点

计划完成后，任务 Markdown 落盘位置按路径决定：

- **普通编码路径**：每个 task 独立落 `.airules/tasks/<task-name>.md`，一任务一文件。
- **规格契约路径（spec-workflow）**：`.airules/changes/<change-id>/tasks.md` 作为该 change 的任务索引与勾选清单（`- [ ] N.M 任务`），同时在 `.airules/tasks/` 落详细任务文件；`tasks.md` 勾选列表中若已有对应 `.airules/tasks/<task-name>.md`，必须在该行附注引用路径，避免两处定义。
- 不论哪条路径，**禁止把多个可独立实现/验证/评审的任务塞进单一文件**；单一 plan 文件视为不合规。

## 单任务 Markdown 最小内容（强制模板）

每个落档的任务 Markdown 必须包含以下字段（无关字段可标 `N/A` 并注明原因，但不得省略字段本身）：

```markdown
# <任务标题>

## 目标
<一句话说明本任务交付什么，可独立实现/测试/评审>

## 需求来源 / 契约来源
<对应需求事实源或 spec 的哪一条，或 spec-workflow change-id + 条目编号>

## 涉及文件与职责
| 文件路径 | 职责说明 |
|---|---|
| `<path>` | <职责> |

## 实现步骤
1. <具体可执行步骤>
2. ...

## 测试设计 / 验收用例映射
<从 test-design 的验收清单引用 AC-id，或内联简要测试点>
- AC-1: <...>
- AC-2: <...>

## 需要编写或更新的测试
- `<test-file>`: <测试哪些场景>

## 验证命令
```bash
<实际可运行的 build/test/lint 命令>
```

## 状态
| 环节 | 状态 | 备注 |
|---|---|---|
| code | `PENDING` / `PASS` / `FAIL` / `N/A` | |
| test | `PENDING` / `PASS` / `FAIL` / `N/A` | |
| consistency-review | `PENDING` / `PASS` / `FAIL` / `N/A` | |
| code-review | `PENDING` / `PASS` / `FAIL` / `N/A` | |
| verification | `PENDING` / `PASS` / `FAIL` / `N/A` | |

## 阻塞项
<若无则写"无">

## N/A 说明
<若有任何环节标 N/A，在此写明原因与替代验证方式>
```

## N/A 判定

并非每个任务都必须有 code 或 test：

- **可标 `N/A` 的情形**：纯文档编写、纯规则文本修改、纯格式调整、纯调研、纯配置声明（无行为变更），可将 `code` 或 `test` 标为 `N/A`。
- **标 `N/A` 的要求**：必须在"N/A 说明"字段写明原因与替代验证方式，例如 diff 结构检查、脚本快照校验、文档一致性对比、规则 lint 等客观信号。
- **不得用 `N/A` 回避的情形**：有行为变更（接口、状态机、用户可观察功能）、有数据逻辑变更、有接口新增/修改——这些必须有测试，不得以"内容是文字"为由标 `N/A`。

## 输出边界

- 只产出实现计划与任务拆解，不编写生产代码。
- 范围必须冻结：计划定稿后进入实现，范围变更需回到需求分析。
- 计划与验收用例清单（`test-design` 产出）共同作为实现阶段的输入。
- 计划定稿后归档按"两路任务落点"落盘，作为可追溯事实源留存。
- **产物形态（强制，跨栈）**：每个 task 落成一个独立 md 文件（前端 `<页面名>.md`，后端 `<能力/模块名>.md`），内容满足"单任务 Markdown 最小内容"模板；禁止把多个任务合并成单一 plan 文件，单一 plan 文件视为不合规。
- 字段含义以本 skill 为准；示例任务仅供格式参考，不得当作真实需求落地。
