# 软件开发流程规范 (Software Development Workflow)

## 用途与边界

本规范是开发任务的核心流程引擎，提供可复用的执行顺序与验证标准。

- 本文件决定“怎么做流程”和“怎么交付”；而具体的“代码怎么写”，请通过工具链、本地检索或项目文件主动读取并严格遵守对应的 `SKILL.md`（如 `frontend-code-standard`、`node-code-standard`、`nestjs-code-standard`、`java-code-standard` 等）。
- 本文件不替代 `AGENTS.md`、用户指令或 CI 规则；当上层规则更严格时，必须遵守上层规则。

## 一、流程骨架 (Execution Flow)

每次开发任务必须按以下顺序执行。前置确认可以基于用户请求和仓库事实完成；只有目标、验收标准或风险无法可靠推断时，才需要停下来询问用户。

1. **识别上下文**：读取项目技术栈、相关文件、当前 Git 状态。若存在 `docs/AI项目知识/项目概览.md`，优先将其作为入口进行读取。
2. **确认目标**：明确任务目标、验收标准、非目标与潜在风险。
3. **设计边界**：规划将要影响的文件范围，拒绝蔓延式的随意修改。
4. **实施变更**：优先沿用项目既有模式进行代码变更。
5. **执行验证**：根据下方的“场景分级”与“质量门”，执行针对变更范围的精准验证。
6. **交付报告**：严格按照底部的“强制交付模板”汇报结果。

## 二、场景分级 (Scenario Grading)

不要把所有任务套进重度流程，根据任务风险匹配适当的动作：

| 级别 | 典型任务 | 推荐动作 |
|---|---|---|
| **L0** | 咨询、审查、方案讨论、只读排查 | 不修改代码，仅报告观察结果。 |
| **L1** | 修改文档、README、配置或策略规则 | 执行轻量验证（如 `git diff --check`、目标文件 lint）。 |
| **L2** | 小范围、低风险的代码局部调整 | 执行目标文件的静态检查（Lint/Typecheck）与直接相关的单测。 |
| **L3** | 功能新增、Bug 修复、运行时行为变化 | 执行静态检查、相关测试，按影响面补充 Coverage 或构建验证。 |
| **L4** | 多模块重构、高风险核心链路变更 | 执行完整质量门：Lint、类型检查、测试、构建及必要的手动/浏览器验证。 |

## 三、项目知识接入规则 (Project Knowledge Rules)

- **前置读取**：任务开始前，若存在 `docs/AI项目知识/` 目录，按需读取索引文件获取上下文。若该目录不存在，将项目知识状态标记为 `MISSING` 后跳过，严禁擅自猜测或主动创建知识库。
- **后置刷新**：开发任务完成后，**绝对禁止**自动写入或刷新 `docs/AI项目知识/`。只有在用户显式发送“请更新项目知识库”指令时，才允许修改该目录。

## 四、质量门验证纪律 (Quality Gates)

执行测试或收集覆盖率时，必须遵守以下红线：

- **精准狙击**：工具支持时，必须显式指定被修改的具体文件或直接相关测试文件（例如 `npx vitest run tests/skill-validation.test.ts`），**严禁盲目运行全量测试套件消耗时间与算力**。若工具不支持文件级过滤，运行项目能表达的最小相关范围，并在交付报告中说明原因。L4、发布前检查、共享契约变更或跨模块风险可以扩大到完整质量门，但必须说明触发原因。
- **杜绝伪造**：如果项目缺少测试框架或对应脚本，直接标记为 `MISSING`，绝对禁止伪造测试通过的输出。

验证状态字典：

- `PASS`：命令已运行并成功通过。
- `FAIL`：命令已运行但失败（必须提供修复建议或错误日志）。
- `MISSING`：该验证维度必要，但项目缺少相关脚本或依赖工具。
- `NOT RUN`：该验证维度必要，但因客观原因未运行（需说明原因）。
- `N/A`：该验证维度与本次任务无关。

## 五、任务拆分策略 (Task Splitting Strategy)

当用户需求包含多个独立领域、大型重构或多项功能混杂时：

- **禁止伪造并行**：严禁在输出中假装唤醒“子代理”或“多线程并行执行”。
- **确认优先**：当拆分会形成多个交付批次、优先级不明或存在目标取舍时，必须先输出**任务拆分计划清单**，并明确停下来询问用户：“*请确认是否按此顺序执行，或指定优先执行哪一项？*”
- **逐一推进**：获得确认后，按顺序逐个完成子任务并独立验证，禁止将未完成的中间状态堆砌在一起。

若用户已经明确要求端到端完成，且拆分只是内部执行策略、不改变交付范围，则可直接按依赖顺序推进。

## 六、强制交付模板 (Mandatory Report Template)

任务完成且代码或文档写入后，**必须**严格按照以下 Markdown 格式输出最终报告。`Status` 必须选择 `成功`、`部分完成` 或 `失败` 之一；质量门条目按实际结果列出，不相关示例行应删除。

```markdown
### 任务结论 (Status: 成功)
- **改动范围**：简述触及的核心模块或文件。

### 质量门验证 (Quality Gates)
- [PASS] `执行的具体命令` : 简要结果说明。
- [MISSING] `验证维度或命令` : 缺少脚本、配置、依赖或测试入口。
- [NOT RUN] `验证维度或命令` : 未运行原因。

### 遗留风险与下一步 (Risks & Next Steps)
- 无。
```

只读任务或未修改代码时，可以使用更短报告，但必须说明未修改代码以及质量检查为何为 `N/A` 或 `NOT RUN`。
