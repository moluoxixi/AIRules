# Consistency Check（跨产物一致性门禁）

实现编码前的最后一道防漏门：横切检查 PRD ↔ 测试设计 ↔ 实现计划 ↔ 已有代码四者是否对齐、有无覆盖缺口与孤儿项。purity-check 查 skill 自身是否自足、文档后置校验查单份产物是否漏标 `MISSING`，唯独缺这一层「多份产物之间是否互相对得上」的横向校验——本 skill 补这个断点。

## 触发条件

- 由开发链路编排显式点名：需求、测试设计、实现计划三者就绪后、进入实现编码前，作为 analyze 环节运行。
- 用户要求核对「需求/用例/计划是否对齐、有没有漏测漏实现」时使用。
- 实现计划改动后、重新进入编码前，需要确认改动未制造覆盖缺口时使用。

本 skill 由编排或用户按名加载，省略 `description`，不作为主代理自动捞起的 skill，避免普通对话误触发。

## 不适合场景

- 上游任一产物缺失或仍为草案（大量 `MISSING`）：本 skill 不臆造缺失事实补齐，直接报告 `MISSING blocked` 指明缺失产物并停止，回到对应上游环节。
- 单产物自足性校验（是否漏标 `MISSING`、结构是否缺项）：归文档后置可控性校验，不在本 skill 范围。
- skill 自身可控性校验：归 purity-check，不在本 skill 范围。
- 运行测试、跑覆盖率、构建：归测试验证环节（`verification-before-completion`），本 skill 只做静态对齐核对，不执行代码。

## 输入

- 需求：`docs/prds/<模块>.md`（验收标准、用户流程、字段口径、状态规则）。
- 测试设计：`docs/test/<模块>.md`（用例矩阵，用例ID 形如 `TC-<模块>-<序号>`）。
- 视觉设计输入（前端模块且已产出时）：`docs/design/<模块>.md`（布局、设计 token、组件状态四态、响应式断点、可访问性意图）。仅当被核对模块为前端 UI 模块且 `docs/design/<模块>.md` 存在时纳入；纯后端或无视觉态模块标 `N/A`。
- 实现计划：`docs/plan/frontend/<模块>.md` 与/或 `docs/plan/backend/<模块>.md`（实现任务拆解表，任务ID 形如 `FT-`/`BT-<模块>-<序号>`，每条带独立验收指向用例号）。
- 已有代码（如相关模块已存在）：作为「计划任务是否已落地 / 是否有计划外改动」的对照，仅作核对，不在本环节修改。测试代码作为「用例是否真正落到可执行断言」的对照——用例ID（`TC-<模块>-<序号>`）应能在测试文件注释中反查到（见 `code-core.md` 的用例ID 回溯约定）。
- 跨模块 E2E 旅程（如本模块参与某条跨模块旅程）：`docs/test/e2e/<旅程名>.md` 及 `docs/test/index.md` 的旅程清单，旅程用例ID 形如 `E2E-<旅程名>-<序号>`。仅当被核对模块出现在某旅程「涉及模块」中时纳入，单模块核对不强制。

## 前置门禁

- 本环节前置依赖需求、测试设计、实现计划三者就绪：开始前必须确认 `docs/prds/<模块>.md`、`docs/test/<模块>.md` 及对应 `docs/plan/{frontend,backend}/<模块>.md` 存在且非草案、关键事实非 `MISSING`。
- 上游缺失或仍为草案/大量 `MISSING` 时，报告 `MISSING blocked`（说明缺失的上游产物）并停止，不得臆造上游事实继续核对。
- 可运行 `node <AIRules>/scripts/verify-stage-gate.mjs <project-root> consistency <模块>` 做确定性前置校验；校验失败按 `MISSING blocked` 处理，不得绕过。

## 输出边界

- 默认只写一致性核对报告到 `docs/consistency/<模块>.md`；用户显式指定其它位置时按指定位置写，并在文档开头说明实际位置。
- 不修改 PRD、测试设计、实现计划、业务代码、测试代码：本 skill 只产出核对结论，发现的缺口回填由对应上游环节执行。
- 不臆造缺失事实：核对中发现的未对齐项标 `FAIL`/`MISSING`，不替上游补内容。
- 不得把密钥、token、连接串等凭证明文写入报告；以配置项名称引用。

## 多向核对（关键）

前 4 向是每次核对都必走的基本盘；第 5 向仅在被核对模块参与某条跨模块 E2E 旅程时增列，第 6 向仅在被核对模块为前端 UI 模块且 `docs/design/<模块>.md` 存在时增列，否则各标 `N/A`。每个方向逐项走查，每项给 `PASS`/`FAIL`/`MISSING`/`N/A` 之一，禁止留空：

1. **需求 → 用例**：每条 PRD 验收标准是否都有对应测试用例覆盖？无对应用例的需求项标 `FAIL`（漏测）。
2. **用例 → 计划任务**：每条测试用例ID 是否都被至少一个实现任务的「独立验收」勾到？无任务承接的用例标 `FAIL`（漏实现）。
3. **计划任务 → 需求/用例**：每条实现任务是否都可追溯到某条需求或用例？追溯不到的任务标 `FAIL`（孤儿任务/范围蔓延）。
4. **计划 ↔ 已有代码**（相关模块已存在时）：计划任务声称要改的目标文件是否与实际代码结构对得上？已有代码是否存在计划未覆盖的相关改动？对不上标 `MISSING`（需澄清）或 `FAIL`（计划与现状冲突）。
5. **跨模块旅程 → 模块用例/计划**（被核对模块参与某条跨模块 E2E 旅程时）：旅程用例（`E2E-<旅程名>-<序号>`）在本模块的每个步骤，是否都回指到了本模块已存在的 `TC-<模块>-<序号>` 与承接任务？旅程清单声称本模块参与、但模块测试设计/计划里找不到对应衔接用例或任务的，标 `FAIL`（跨模块衔接漏测/漏实现）；旅程涉及的他模块上游未就绪导致衔接事实无法确认的，标 `MISSING`。被核对模块不参与任何跨模块旅程时，本方向标 `N/A`。
6. **视觉状态 → 用例 → 任务**（前端 UI 模块且 `docs/design/<模块>.md` 存在时）：`docs/design/<模块>.md` 中定义的每个组件视觉状态（加载中/空态/错误态/成功态等）是否都有对应测试用例（`TC-<模块>-<序号>`）覆盖、且该用例被某实现任务承接？设计已定义但测试设计无对应用例的状态标 `FAIL`（视觉态漏测，回 `test-docs`）；有用例但无任务承接的标 `FAIL`（视觉态漏实现，回 `frontend-impl-plan`）；设计输入本身缺该状态定义的标 `MISSING`（回 `design-docs`）。模块无视觉态（纯后端/纯数据）时本方向标 `N/A`。

另有一项**用例 → 测试代码**反向核对，并入第 4 向「计划 ↔ 已有代码」一起走查（仅在测试代码已存在时）：测试设计的每条用例ID 是否能在对应测试文件的注释中反查到（`// TC-<模块>-<序号>`，见 `code-core.md` 约定）？有用例但测试代码中查不到对应标注的标 `FAIL`（用例未落到可执行断言或未登记）；测试代码尚未编写（仍在编码前）时本反向核对标 `N/A`，不阻断编码前的一致性门禁。

核对依据必须来自上游产物本身；上游未写明、需反查代码才能确定的事实标 `MISSING`，不用代码反推业务口径。

## 文档结构

```md
# <模块>跨产物一致性核对报告

## 核对范围

- PRD：docs/prds/<模块>.md
- 测试设计：docs/test/<模块>.md
- 实现计划：docs/plan/<栈>/<模块>.md
- 已有代码：（涉及的模块/目录，无则写 N/A）

## 需求 → 用例覆盖

| 需求项（PRD 章节/验收标准） | 对应用例ID | 状态 |
|---|---|---|

## 用例 → 计划任务覆盖

| 用例ID | 承接任务ID | 状态 |
|---|---|---|

## 计划任务 → 需求/用例追溯

| 任务ID | 来源需求/用例 | 状态 |
|---|---|---|

## 计划 ↔ 代码核对

| 任务ID | 目标文件 | 与现状一致性 | 状态 |
|---|---|---|---|

## 用例 → 测试代码反查（测试代码已存在时；否则 N/A）

| 用例ID | 测试文件中是否查到 `// TC-` 标注 | 状态 |
|---|---|---|

## 跨模块旅程衔接核对（本模块参与跨模块旅程时；否则 N/A）

| 旅程用例ID | 本模块步骤 | 回指模块用例ID | 承接任务ID | 状态 |
|---|---|---|---|---|

## 视觉状态 → 用例 → 任务覆盖（前端 UI 模块且 docs/design/ 已产出时；否则 N/A）

| 视觉状态 | 来源（docs/design/<模块>.md） | 对应用例ID | 承接任务ID | 状态 |
|---|---|---|---|---|

## 缺口汇总

- 漏测（需求无用例）：...
- 漏实现（用例无任务）：...
- 孤儿任务（任务无来源）：...
- 计划与代码冲突：...
- 用例未落到测试代码（测试代码已存在但查不到 `// TC-` 标注）：...（测试代码未写则 N/A）
- 跨模块衔接漏测/漏实现（旅程步骤在本模块无对应用例/任务）：...（不参与旅程则 N/A）
- 视觉态漏测/漏实现（设计定义的状态无用例或无任务承接）：...（无视觉态则 N/A）
- MISSING（需上游澄清）：...

## 结论

- 总体：PASS / FAIL / MISSING blocked
- FAIL/MISSING 项必须回填对应上游产物后复核，不得在本报告内自行补齐上游事实。
```

## 结论与处置

- 全部方向 `PASS`（含跨模块旅程方向与视觉状态方向，本模块不参与旅程或无视觉态时对应方向为 `N/A` 不影响总体）→ 总体 `PASS`，可进入实现编码。
- 任一方向存在 `FAIL`（漏测/漏实现/孤儿/冲突/跨模块衔接漏测漏实现/视觉态漏测漏实现/用例未落测试代码）→ 总体 `FAIL`，列出缺口，回退到对应上游环节（漏测回 `test-docs`，漏实现/孤儿回对应 impl-plan，需求冲突回 `prd-docs`，跨模块衔接缺口回 `test-docs` 的旅程文档或对应 impl-plan，视觉态缺口回 `design-docs`/`test-docs`/`frontend-impl-plan`）回填后复核，不得带 `FAIL` 进入编码。
- 存在依赖上游澄清的 `MISSING` → 总体 `MISSING blocked`，走澄清门禁补齐事实后复核。
