# 完成前验证

声明完成前的证据门：先实际运行，再读取输出，最后按枚举状态收口。这是收益最高的门禁——LLM 会系统性高估自己的产物，运行结果是唯一可信的锚。没在当前这次动作里跑过验证命令，就不能声称它通过。

## 触发条件

- 准备声明任务完成、已修复、已通过，或表达"搞定 / 没问题"之类的满意度
- 高风险改动（删除、生产、安全、权限、跨模块）收口前
- 提交、推送、建 PR、转入下一任务之前
- 委派子代理后：子代理回报"成功"不等于成功，需独立核对 diff / 输出

## 不适合场景

- 仍在实现中途、尚未到收口节点
- 纯文档 / 注释 / 格式改动且无可运行验证项 → 标 `N/A` 并说明

## 验证流程

1. **识别**：列出本次改动应运行的验证项（build、test、lint、相关用例）。优先项目既有脚本与配置，问"哪条命令能证明这个声明"。
2. **运行**：实际执行完整命令，全新跑、不跳步、不假设、不外推。
3. **读取**：读真实输出，看退出码，数失败数量，确认通过 / 失败的具体内容。
4. **收口**：按枚举状态逐项记录。

## 状态枚举

只能用 `PASS`、`FAIL`、`MISSING`、`NOT RUN`、`N/A`：

- 脚本 / 配置 / 依赖 / 测试入口缺失 → `MISSING` 或 `NOT RUN` + 原因
- 不得把失败、缺失、不相关或未运行转写成通过

## 常见自欺（识破并拒绝）

| 借口 | 现实 |
|------|------|
| "应该能过了" | 跑一遍验证 |
| "我很有把握" | 把握 ≠ 证据 |
| "lint 过了" | lint 不等于编译 / 测试 |
| "子代理说成功了" | 独立核对 diff 与输出 |
| "局部查过就够了" | 局部证明不了整体 |
| "换个说法这条就不适用" | 看精神不看字面，绕开即违反 |

特别地：声称"回归测试有效"必须真正验证过红绿——改前失败、修后通过；只跑一次通过不算数。

## 输出边界

- 未实际运行并读取输出前，不得声明完成、已修复或已通过。
- 交付汇报精简收口：改了什么、验证命令与结果状态、未执行项及原因（没有则显式写"无"）。
- 覆盖率不足只能补有效测试或说明原因；不得降阈值、排除关键文件、删断言。
- 验证不留捷径：跑命令、读输出，然后才下结论。
