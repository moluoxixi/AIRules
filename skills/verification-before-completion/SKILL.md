# Verification Before Completion（完成前验证）

## 概述

没验证就声明完成，是不诚实，不是高效。

**核心原则：证据先于声明，永远如此。**

违反本规则的字面要求，就是违反它的本质。

## 铁律

```
没有新鲜的验证证据，不得做任何完成声明
```

如果你没有在本条消息里跑过验证命令，就不能声称它通过。

## 门禁函数

```
在声明任何状态或表达满意之前：

1. 识别：哪条命令能证明这个声明？
2. 运行：执行完整命令（全新、完整地跑一遍）
3. 读取：读完整输出，检查退出码，数失败数量
4. 验证：输出是否确认了声明？
   - 否：用证据陈述真实状态
   - 是：带着证据陈述声明
5. 然后才：做出声明

跳过任何一步 = 撒谎，不是验证
```

## 触发条件

**任何以下情况之前都适用：**

- 任何形式的成功/完成声明，及其同义改写与暗示。
- 任何对工作状态的肯定表述、任何表达满意。
- 提交、建 PR、完成 task、进入下一个 task。
- 委派子代理后采信其回传结论之前。

## 不适合场景

- 纯讨论、方案权衡、尚未产生可验证产物的阶段。
- 用户明确表示只要草稿、不要求验证时（仍须在交付中说明未验证）。

## 应用边界与子代理委派（该走子代理就走）

- **回归量大或跨多模块**：派验证子代理跑测试/构建/lint 并收集证据，回传 `PASS`/`FAIL` + 证据句柄（命令、输出摘要、退出码），主代理据此复核，不让海量验证输出占满主上下文。
- **单条命令、输出短**：主代理直接跑、直接读，不必委派。
- **子代理回传 ≠ 已验证**：子代理报告"成功"只是自述。主代理必须独立核对可验证句柄（VCS diff、命令输出、文件内容）后才能向用户声明成功。信任子代理的成功报告而不复核，是本规则明确禁止的。

## 常见失败：声明所需的证据

| 声明 | 需要的证据 | 不充分的依据 |
|---|---|---|
| 测试通过 | 测试命令输出：0 失败 | 上一次运行、"应该能过" |
| Lint 干净 | Lint 输出：0 错误 | 局部检查、外推 |
| 构建成功 | 构建命令：退出码 0 | "lint 过了""日志看着没问题" |
| Bug 已修 | 测原始症状：通过 | 改了代码、想当然认为修好了 |
| 回归测试有效 | 红绿循环已验证 | 测试只过了一次 |
| 子代理完成 | VCS diff 显示改动 | 子代理报告"成功" |
| 需求已满足 | 逐条核对清单 | 测试通过 |

## 危险信号——停下

- 用"应该""大概""似乎"。
- 验证前就表达满意（"很好！""完美！""搞定！"等）。
- 没验证就要提交/推送/建 PR。
- 信任子代理的成功报告。
- 依赖局部验证外推整体。
- 想着"就这一次"。
- 累了、想赶紧收工。
- 任何在没跑验证的情况下暗示成功的措辞。

## 借口与现实

| 借口 | 现实 |
|---|---|
| "现在应该好了" | 去跑验证 |
| "我很有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "lint 过了" | lint ≠ 编译器 |
| "子代理说成功了" | 独立复核 |
| "我累了" | 疲惫不是借口 |
| "局部检查够了" | 局部什么都证明不了 |
| "换个说法规则就不适用了" | 本质重于字面 |

## 关键模式

**测试：**
```
✅ [跑测试命令] [看到 34/34 通过] "全部测试通过"
❌ "现在应该能过""看起来对"
```

**回归测试（TDD 红绿）：**
```
✅ 写 → 跑(过) → 回退修复 → 跑(必须失败) → 恢复 → 跑(过)
❌ "我写了回归测试"（没做红绿验证）
```

**构建：**
```
✅ [跑构建] [看到退出码 0] "构建通过"
❌ "lint 过了"（lint 不检查编译）
```

**需求：**
```
✅ 重读计划 → 列清单 → 逐条核对 → 报告差距或完成
❌ "测试过了，阶段完成"
```

**子代理委派：**
```
✅ 子代理报告成功 → 查 VCS diff → 核对改动 → 报告真实状态
❌ 直接信任子代理报告
```

## 与项目检查状态对齐

验证结果统一用 `PASS`、`FAIL`、`MISSING`、`NOT RUN`、`N/A` 表达，不得把失败、缺失、不相关或未运行转写成通过。交付汇报必须给出实际运行的命令、结果状态、未执行项与原因（与项目「交付验证」「开发链路控制」一致）。

## 底线

不给验证留任何捷径。跑命令，读输出，然后才声明结果。这一条不可商量。
