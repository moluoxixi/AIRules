# 需求分析

把任务诉求转成下游计划/实现可直接消费的需求事实源。自适应输入：用户可能提供 PRD，也可能只有一句话诉求。

## 触发条件

- 编码任务进入流水线、尚无明确需求事实源
- 用户给了 PRD 但存在缺口或歧义，需要归一化为下游事实源
- 用户只给了模糊诉求，需要澄清边界后再进入计划

## 不适合场景

- 需求事实源已就绪且无歧义 → 直接进入计划阶段
- 纯 bug 修复且现象明确 → 走调试修复，不需要重做需求分析
- 架构/选型讨论 → 不属于本 skill 范围

## 方法

1. **评估输入**：判断是否已有 PRD 或等价需求文档。
   - 有：读取并核对是否覆盖目标、范围、角色、关键流程、验收标准；缺口逐项标 `MISSING`。
   - 无：用苏格拉底式问题澄清目标、用户、核心流程、边界、验收标准。
2. **歧义处理**：关键事实缺失或多解时，输出澄清问题清单等待用户确认；不得用推断、默认值或代码反推替代用户确认。
3. **产出需求事实源**：澄清闭环后，归一化为结构化需求事实源，包含验收标准雏形供 `test-design` 消费。

## 输出边界

- 产出需求事实源（含验收标准雏形）；是否写盘按项目既有 docs 约定，默认作为下游阶段的输入事实源。
- 澄清未闭环前不得定稿、不得声明需求就绪、不得进入计划阶段。
- 不替用户做产品决策；不把示例诉求当作真实需求自动落地。
