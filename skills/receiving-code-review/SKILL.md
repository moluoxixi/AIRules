# Receiving Code Review（接受代码评审反馈）

## 概述

代码评审需要的是技术评估，不是情绪表演。

**核心原则：落实前先核实。假设前先发问。技术正确优先于社交舒适。**

## 触发条件

- 收到来自评审员（人或子代理）的代码评审反馈，准备处理时。
- 反馈不清晰、或技术上看起来站不住脚，需要判断是否照做时。

## 不适合场景

- 还没收到任何评审反馈时。
- 用户已直接给出明确修改指令、无歧义时，按指令改即可。

## 响应模式

```
收到代码评审反馈时：

1. 读完：完整读完反馈，先不反应
2. 理解：用自己的话复述要求（或发问）
3. 核实：对照代码库现实检查
4. 评估：对本代码库而言技术上是否成立？
5. 回应：技术性确认，或带技术理由的回推
6. 落实：一次改一项，每项都验证
```

## 禁止的回应

**绝不：**
- "你说得完全对！"（表演式附和）
- "好观点！""反馈太棒了！"（情绪表演）
- "我马上改"（核实之前）

**而要：**
- 复述技术要求。
- 提澄清问题。
- 若反馈有误，用技术理由回推。
- 直接开始干（行动胜于表态）。

## 处理不清晰的反馈

反馈含糊时，不要猜测意图就动手。先复述你的理解并请求确认；或对照代码指出歧义点，请评审员明确。宁可多问一句，不要照着错误理解改一通。

## 处理技术上存疑的反馈

- 先对照代码库核实反馈是否对**本**代码库成立——别处的最佳实践未必适用这里。
- 若核实后确认反馈有误：用技术理由回推，拿代码/测试/契约证据说明为什么当前实现是对的，不为社交舒适而盲从。
- 若核实后确认反馈正确：直接落实，不必表演式致谢。

## 落实纪律

- 一次只改一项，每项改完即验证（对齐 `verification-before-completion`：证据先于声明）。
- 区分严重度：阻断性问题（`FAIL`）立即修；重要问题在推进前修；次要问题记录后续处理。
- 全部 `FAIL`/`MISSING` 项修复后回传评审员复审，直到全维度 `PASS`。

## 危险信号

- 还没核实就说"马上改"。
- 用附和代替技术回应。
- 因为评审员"听起来很自信"就盲从。
- 一次性堆多项改动、不逐项验证。
