# 系统化调试

由 `debugger` 按名加载的方法论。随手乱改浪费时间还会制造新 bug；先复现并定位根因，再提出修复建议，不在定位阶段改生产代码。未定位根因前不提修复。

## 触发条件

- 由 `debugger` 加载，处理测试失败、生产 bug、非预期行为、性能 / 构建 / 集成问题
- 根因不明、需要先查清再修
- 越是在时间压力下、越是"一个小修复就好"看起来很诱人时，越要走流程——系统化比反复试错更快

## 不适合场景

- 主代理在普通对话里不主动加载本 skill（故省略 description）
- 单点已定位的小 bug → 主代理直接修，不派 debugger
- 需求 / 计划设计 → 不在本 skill 范围

## 四阶段（先定位，后修复）

每一阶段完成后才进入下一阶段。

### 1. 复现

- 仔细读错误信息、完整堆栈、行号 / 文件 / 错误码，它们往往直接指向答案。
- 构造稳定复现路径，确认失败现象与触发条件；不能稳定复现就继续收集数据，不要猜。
- 查最近改动：git diff、近期提交、新依赖、配置或环境差异。

### 2. 缩小

- 多组件系统（CI→build→签名、API→service→DB）在边界处加诊断输出，先跑一次看清"在哪一层断"，再深入那一层。
- 用二分、日志、最小复现逐步缩小到具体代码 / 数据。
- 错误深在调用栈里时，从坏值出发反向追溯到它的来源——在源头修，不在症状处修。
- 找同仓里相似的可用代码作对照，逐条列出可用与故障之间的差异，别假设"这点不可能有影响"。

### 3. 根因

- 形成单一假设："我认为根因是 X，因为 Y"，写下来，具体而非含糊。
- 解释为什么会失败——是机制，不是症状。区分根因与表象。
- 不懂就说"我不理解 X"，去查，别假装懂。

### 4. 建议

- 给出建议修复点与回归测试设计（先能复现 bug 的失败测试），回传给 coder 执行。
- 一次只动一个变量，不捆绑"顺手"改动或重构。

铁律：同一思路失败两次后停下来质疑假设，换一条根本不同的路径，而不是反复打补丁。若每次修复都在不同地方暴露新的共享状态 / 耦合，那不是假设错了，是架构错了——升级讨论，不要继续打补丁。

## 输出边界

- 只读诊断，可落盘 `docs/diagnosis/<bug>.md`，不改生产代码——修复由 coder 按回传执行。
- 回传必须包含根因 + 证据 + 建议修复点 + 回归测试设计。
- 不得把"暂时不复现"当作已修复；现象未稳定复现时标 `MISSING`。
- 调查若确证问题确属环境 / 时序 / 外部因素，记录调查过程并建议相应处理（重试、超时、监控）——但绝大多数"查不到根因"其实是调查不彻底。
