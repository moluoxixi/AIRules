# 系统化调试

由 `debugger` 按名加载的方法论。先复现并定位根因，再提出修复建议，不在定位阶段改生产代码。

## 触发条件

- 由 `debugger` 加载，处理测试失败、生产 bug、非预期行为、性能/构建/集成问题
- 根因不明、需要先查清再修

## 不适合场景

- 主代理在普通对话里不主动加载本 skill（故省略 description）
- 单点已定位的小 bug → 主代理直接修，不派 debugger
- 需求/计划设计 → 不在本 skill 范围

## 四阶段（先定位，后修复）

1. **复现**：构造稳定复现路径，确认失败现象与触发条件。
2. **缩小**：用二分、日志、最小复现逐步缩小范围，定位到具体代码/数据。
3. **根因**：解释为什么会失败——不是症状，是机制。区分根因与表象。
4. **建议**：给出建议修复点与回归测试设计，回传给 coder 执行。

铁律：未定位根因前不提修复；同一思路失败两次后停下来质疑假设，换根本不同的路径，而非反复打补丁。

## 输出边界

- 只读诊断，可落盘 `docs/diagnosis/<bug>.md`，不改生产代码——修复由 coder 按回传执行。
- 回传必须包含根因 + 证据 + 建议修复点 + 回归测试设计。
- 不得把"暂时不复现"当作已修复；现象未稳定复现时标 `MISSING`。
