# Systematic Debugging（系统化调试）

## 概述

随机试错会浪费时间并制造新 bug，快速打补丁只会掩盖底层问题。

**核心原则：动手修复前必须先定位根因。只修症状即视为失败。**

违反流程的字面要求，就是违反调试的本质。

## 铁律

```
未完成根因调查，不得提出任何修复
```

没走完第 1 阶段（根因调查），就没有资格提出修复方案。

## 触发条件

任何技术问题都适用：测试失败、生产 bug、非预期行为、性能问题、构建失败、集成问题。

**尤其在以下情况不得跳过：**

- 时间紧迫（越是紧急越容易靠猜）。
- "就改一个地方试试"看起来很显然。
- 已经试过多次修复仍未解决。
- 上一个修复没生效。
- 自己并未真正理解问题。

**不要因为"问题看起来简单"就跳过：简单 bug 也有根因，流程对简单 bug 同样很快。**

## 不适合场景

- 根因已明确定位、单点小改即可的修复，可直接修，不必走完整四阶段；但仍须满足验证环节的证据要求。
- 纯需求/设计澄清、与运行时行为无关的纯文档改动。

## 输出边界与子代理委派（该走子代理就走）

调试常产生大量日志、堆栈和复现输出，是子代理隔离上下文的典型场景：

- **多个相互独立的失败**（不同测试文件、不同子系统、不同 bug）：每个独立失败域派一个调查子代理并行调查，主代理只接收回传的根因结论，不让海量调查输出污染主上下文。
- **单点已定位的小 bug**：主代理直接调查修复，不必委派。
- 委派调查子代理时，指令必须自包含：提供失败现象、复现步骤、相关文件路径、已知约束，并要求回传"根因 + 证据 + 建议修复点"，而不是直接改代码（生产代码修改由主代理复核，或由高质量 coding 子代理在主代理协调下进行）。
- 子代理回传的根因是自述证据，不是已验证结论；主代理须用可验证句柄（命令输出、diff、日志）复核后才采信。

## 四个阶段

每个阶段必须完成后才能进入下一个。

### 第 1 阶段：根因调查

动手修复前：

1. **仔细读错误信息**——不要跳过错误或警告，它们常常直接给出答案。完整读堆栈，记下行号、文件路径、错误码。
2. **稳定复现**——能否可靠触发？确切步骤是什么？是否每次都发生？无法复现就继续收集数据，不要猜。
3. **检查近期改动**——什么改动可能引发它？看 git diff、近期提交、新依赖、配置变更、环境差异。
4. **多组件系统先加诊断埋点定位失败边界**——当系统跨多个组件（CI → 构建 → 签名，API → 服务 → 数据库）时，先在每个组件边界记录入参、出参、环境/配置传递与各层状态，跑一次收集证据，看清在哪一层断裂，再深入那个具体组件，而不是一上来就猜。
5. **回溯数据流**——当错误深在调用栈中：坏值从哪里产生？谁用坏值调用了它？一路往上追到源头，在源头修，不在症状处修。

### 第 2 阶段：模式分析

修复前先找出模式：

1. **找可用的对照实现**——在同一代码库里找类似的、能正常工作的代码。
2. **完整对照参考实现**——若在套用某个模式，完整读参考实现的每一行，不要略读。
3. **列出差异**——可用版本与故障版本之间，每一处差异都列出来，哪怕看起来微不足道，不要假设"这不可能有影响"。
4. **理解依赖**——它还需要哪些组件、配置、环境？做了哪些假设？

### 第 3 阶段：假设与验证

科学方法：

1. **形成单一假设**——明确写下"我认为 X 是根因，因为 Y"，要具体不要含糊。
2. **最小化测试**——做能验证假设的最小改动，一次只动一个变量，不要同时修多处。
3. **验证后再继续**——生效了进第 4 阶段；没生效就形成新假设，**不要在旧修复上叠加新修复**。
4. **不懂就说不懂**——说"我不理解 X"，不要假装懂，去查、去问。

### 第 4 阶段：实现修复

修根因，不修症状：

1. **先建失败用例**——最简复现，能自动化就自动化，没有框架就写一次性脚本；修复前必须先有这个用例。需要写规范的失败测试时，配合 `test-driven-development` 的 RED-GREEN 流程。
2. **实现单一修复**——只针对已定位的根因，一次一处改动，不顺手做"既然来了"的改进，不夹带重构。
3. **验证修复**——用例现在通过了吗？有没有弄坏其它测试？问题真的解决了吗？
4. **修复无效时停下**——数一下：试了几次？少于 3 次回第 1 阶段带着新信息重新分析；**达到 3 次及以上，停下质疑架构**，不要在没有架构讨论的情况下尝试第 4 次修复。
5. **3+ 次修复失败 = 质疑架构**——若每次修复都在不同地方暴露新的共享状态/耦合/问题、修复需要"大规模重构"、每个修复在别处制造新症状，这不是失败的假设，而是错误的架构。停下，和用户讨论"是否该重构架构而非继续修症状"，再决定下一步。

## 危险信号——立即停下回到第 1 阶段

如果发现自己在想：

- "先快速修一下，回头再查"
- "就改 X 看看行不行"
- "一次多改几处，跑测试看看"
- "跳过测试，我手动验证一下"
- "八成是 X，我直接修"
- "虽然没完全搞懂，但这么改可能行"
- "参考实现说要 X，但我换个方式适配"
- 还没追数据流就开始提解决方案
- "再试最后一次修复"（已经试过 2 次以上）
- 每个修复都在不同地方暴露新问题

**以上全部意味着：停下，回到第 1 阶段。** 已失败 3+ 次则质疑架构。

## 常见借口与现实

| 借口 | 现实 |
|---|---|
| "问题简单，不用走流程" | 简单问题也有根因，流程对简单 bug 很快 |
| "紧急，没时间走流程" | 系统化调试比猜测试错更快 |
| "先试这个，再去调查" | 第一个修复定了基调，从一开始就做对 |
| "确认修好了再补测试" | 没测试的修复站不住，先有测试才能证明 |
| "一次多修几处省时间" | 无法隔离是哪处生效，还会制造新 bug |
| "参考太长，我适配一下模式" | 一知半解必然引入 bug，完整读完 |
| "我看到问题了，直接修" | 看到症状 ≠ 理解根因 |
| "再试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题，质疑模式而非再修一次 |

## 与其它环节衔接

- 偏差是因为实现偏离了需求/计划/规则，而非纯技术故障时，用 `retrospective-correction` 按偏差分级处理。
- 修复完成后进入测试验证环节，按 `verification-before-completion` 跑真实命令、用证据下结论，不得凭"应该好了"声明完成。
- 写失败用例和回归测试时配合 `test-driven-development` 的 RED-GREEN-REFACTOR。

## 快速参考

| 阶段 | 关键动作 | 完成标准 |
|---|---|---|
| 1. 根因 | 读错误、复现、查改动、多组件加埋点、回溯数据流 | 弄清"是什么"和"为什么" |
| 2. 模式 | 找对照实现、完整对比、列差异 | 找出差异点 |
| 3. 假设 | 形成单一假设、最小测试 | 假设被确认或形成新假设 |
| 4. 实现 | 建失败用例、单一修复、验证 | bug 解决、测试通过 |

## 当调查显示"没有根因"

若系统化调查确实表明问题是环境性、时序性或外部依赖导致：你已走完流程，记录调查内容，实现恰当的处理（重试、超时、明确错误信息），并加监控/日志便于后续排查。但 95% 的"没有根因"其实是调查不彻底。
