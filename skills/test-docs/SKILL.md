# Test Docs

## 触发条件

- 用户要求生成、更新或标准化测试策略、用例矩阵、联调验证、回归范围或测试数据准备文档时使用。
- 用户要求在写正式测试设计前先出测试脑图、用例分组图等评估前置大纲，方便快速理解和评估测试范围时使用。
- 开发评审前需要把测试设计和验证范围落到 `docs/test/` 时使用。

## 不适合场景

- 用户只要求直接写测试代码，且已有明确测试模式和验收标准时，不必先写测试文档。
- 缺少 PRD、API、缺陷复现或用户确认时，不要猜测测试预期。

## 输出边界

- 只写 `docs/test/`（含跨模块旅程子目录 `docs/test/e2e/`）、`docs/test/index.md` 和 `docs/map.md`。
- 不修改测试代码、业务实现、Mock 服务或 CI 配置；需要改代码时另行确认。

## 输出位置

- 模块测试文档：`docs/test/<需求模块>.md`，一个需求模块一个文件。
- 跨模块 E2E 旅程文档：`docs/test/e2e/<旅程名>.md`，一条跨模块旅程一个文件（仅当旅程横跨 ≥2 个需求模块时单列，见「跨模块 E2E 旅程文档」节）。
- 索引路径：`docs/test/index.md`
- 地图路径：`docs/map.md`

## 拆分粒度（关键）

- 拆分单位是「需求模块 / 功能模块」，不是粗粒度的产品域或项目名。必须按模块拆成多份，严禁把整个项目的用例混写进单份大文档。
- 判定粒度时跟随上游已有的最细拆分：优先对齐 `docs/prds/` 已拆出的需求模块（每个 PRD 模块对应一份测试文档），其次对齐 `docs/api/` / `docs/out-api/` 接口模块。
- 上游若已把项目拆成多个需求模块（如「仓库管理 / 区域管理 / 供应商发货点管理 / 店仓关系 / 品仓管理 / 仓仓线路管理 / 供应商供货管理 / 多级供货网络路由」等），测试文档必须同样拆成对应多份，而不是合并成一份产品域/项目级大文档——合并会稀释每个模块的可评估性。
- 模块边界以「能独立评审一块测试设计」为度；若上游确实只有单一模块的确认事实，才只产出一份，并在 index 说明其余为 `MISSING`（上游未就绪）。

## 跨模块 E2E 旅程文档（关键）

模块测试文档里的 E2E 用例只覆盖「单模块内」的关键路径；横跨 ≥2 个需求模块、由一条完整用户旅程串起来的端到端验证（如「下单 → 库存扣减 → 发货 → 回款」跨订单/库存/物流/财务多模块），单模块文档承接不了，必须单列为跨模块 E2E 旅程文档。设计意图：把跨模块旅程的覆盖范围显式枚举成可评审清单，避免「每个模块各自测了、模块衔接处却没人测」的缝隙，也让评审者能一眼看全跨模块 E2E 的计划与范围。

- **何时单列**：一条用户旅程横跨 ≥2 个需求模块时，在 `docs/test/e2e/<旅程名>.md` 单列；旅程完全落在单一模块内时，留在该模块文档的用例矩阵（层级标 E2E），不重复单列。
- **旅程清单先行**：写具体旅程文档前，先在 `docs/test/index.md` 列出本项目已识别的全部跨模块旅程（旅程名 + 涉及模块 + 状态），上游未就绪的旅程标 `MISSING`。清单是评审「跨模块 E2E 范围是否枚举完整」的依据，漏列等同漏测。
- **旅程用例ID**：形如 `E2E-<旅程名>-<序号>`，与模块用例ID（`TC-<模块>-<序号>`）正交、各自独立命名空间；旅程用例的每个步骤必须回指它消费的模块用例ID，建立「旅程 → 模块用例」的双向追溯。
- **不复制模块用例**：旅程文档只描述「跨模块衔接与编排」（模块间数据交接、状态在模块边界的流转、跨模块失败回滚），单模块内部的交互/校验细节仍归模块文档，旅程文档按 TC-ID 引用而非重写。
- **前置依赖**：旅程涉及的每个模块的 `docs/prds/<模块>.md` 与 `docs/test/<模块>.md` 都须就绪；任一模块上游缺失，旅程文档对应步骤标 `MISSING blocked`，不臆造跨模块衔接事实。
- **旅程地图**：旅程文档第一部分用 Mermaid 画跨模块旅程图（`flowchart` 或 `sequenceDiagram`，标注每段落在哪个模块、衔接处的数据/状态交接点），未确认的衔接点显式标 `MISSING`/`TBD`。

## 前置门禁

- 本环节是实现编码前的测试设计门禁，前置依赖需求与 API/组件契约：开始前必须确认对应业务域的 `docs/prds/<模块>.md` 存在且非草案、关键事实非 `MISSING`；涉及接口/组件时确认 `docs/api/`、`docs/out-api/`、`docs/components/` 对应契约就绪。
- 上游缺失或仍为草案/大量 `MISSING` 时，报告 `MISSING blocked`（说明缺失的上游产物）并停止，不得臆造需求或接口预期继续写测试设计。
- 可运行 `node <AIRules>/scripts/verify-stage-gate.mjs <project-root> test-design <模块>` 做确定性前置校验；校验失败按 `MISSING blocked` 处理，不得绕过。

## 写作规则

- 先读取 `docs/map.md`、`docs/test/index.md`、相关 PRD、API 协议、架构文档和已有测试文档。
- 测试文档必须服务开发评审；实现前需要评审时，只输出测试设计，不直接生成测试代码。
- 变更分级（L0/L1/L2）与澄清门禁的统一定义见项目 `AGENTS.md` 的「变更分级与澄清门禁」一节；本 skill 的 L0/L2 判定以该定义为准。
- 命中澄清门禁时（属于 L2，或测试目标、业务预期、权限/状态规则、Mock/fixture 策略、联调边界、覆盖率边界或回归范围缺少明确来源或存在歧义），必须先输出《测试澄清问题清单》或《测试设计报告》，用苏格拉底式问题逐项暴露验证目标、风险假设、输入输出、边界条件、依赖数据和失败判定；未确认内容必须标记为 `MISSING`，澄清未闭环前不得定稿。
- 用例必须覆盖正常路径、边界条件、权限/状态、错误路径和回归范围。
- 异常/边界用例必须按枚举法逐类走查，不得凭感觉发散；每类至少给出「已覆盖 / N/A（说明理由）/ MISSING（缺上游事实）」三态之一，禁止留空：
  1. 输入校验：空值、超长、格式错误、特殊字符、最小/最大合法值。
  2. 边界条件：min、min-1、max、max+1、分页边界、超时阈值、限流阈值。
  3. 错误态：网络失败、资源不存在、权限拒绝、会话过期、5xx 降级。
  4. 并发：重复提交/双击、双人改同一资源、加载后数据被改（陈旧数据）。
  5. 集成失败：依赖服务不可用/返回错误/超时（标注超时值）。
- 每条异常用例的「预期」必须含用户可见恢复路径（看到什么、能否重试、数据是否保留），仅检测不恢复视为 `MISSING`。枚举法每类的合法值/阈值/超时值/权限规则/状态机，必须先经 `knowledge-search` 命中 `airules.knowledge.json` 的知识源（PRD/API 契约/领域规则）后填写，未命中标 `MISSING`，不得用经验值填阈值。
- 前端模块的测试设计必须覆盖前端交互测试，不止接口联调：组件交互（点击、输入、选择、拖拽）、表单校验（必填、格式、联动、提交禁用态）、状态流转（加载中/空态/错误态/成功态）、路由与权限可见性、关键用户操作路径与 E2E。前端交互用例在用例矩阵的「层级」列标注为组件/E2E，并对齐 `frontend-impl-plan` 将消费的用例编号。
- 前端交互用例落地方法：动态页面先 reconnaissance 后 action（导航 → 等渲染完成/关键 selector 出现 → 读 DOM 发现真实 selector → 再写断言，禁止在渲染完成前断言）；selector 优先级 role/text > 稳定 testid > CSS，禁止依赖易变样式类名；状态机四态（加载中/空态/错误态/成功态）各对应独立用例编号；E2E 脚本路径与用例编号双向登记，便于回归追溯。
- 跨模块端到端旅程（横跨 ≥2 个需求模块）按「跨模块 E2E 旅程文档」节单列到 `docs/test/e2e/<旅程名>.md`，并在 `docs/test/index.md` 维护旅程清单；单模块内的 E2E 留在模块文档，不重复单列。
- 新增或修改测试策略、测试分层、Mock/fixture 策略、E2E/联调范围、覆盖率边界、权限/状态机/数据一致性验证时，属于 L2，必须先完成澄清门禁并输出《测试设计报告》，等待开发者确认后才能定稿。
- 已有明确 PRD/API/缺陷复现步骤，且只补充既有模式下的单元、组件或回归用例时，属于 L0，可直接生成测试代码，并在交付中说明分级判定和跳过评审依据。
- 更新或新增文档后，同步更新 `docs/test/index.md` 和 `docs/map.md`；`docs/map.md` 必须维护需求模块到 PRD/API/组件/测试文档的导航关系。`docs/test/index.md` 除模块测试文档清单外，还须维护「跨模块 E2E 旅程清单」（旅程名 + 涉及模块 + 文档路径 + 状态），上游未就绪的旅程标 `MISSING`。

## 评估前置可视化

测试设计定稿前，必须先产出「测试脑图」：用大纲级图让产品、开发、测试快速理解验证范围全貌，在评审阶段提前暴露未覆盖路径、依赖断点和口径冲突，再写正式用例矩阵。

- 时序：每个需求模块测试文档内，图放第一部分（`## 测试脑图`），正式测试设计（测试目标、分层、用例矩阵等）放其后。
- 图必须用 Mermaid 代码块（` ```mermaid `），可在语雀、GitHub、VSCode 直接渲染，可进 git、AI 易生成、改动零成本；不得用截图或二进制图替代结构图。
- 选图由内容特征驱动，不是每种都画，避免噪音：
  - 测试脑图（`mindmap`）：必出，呈现测试目标 → 测试分层 → 核心场景分组 → 关键风险点的树状全貌。
  - 用例流程图（`flowchart`）：单条核心业务流程含多分支、多前置条件时出，展示用例覆盖的路径与判定点。
  - 状态覆盖图（`stateDiagram-v2`）：被测对象存在状态机（如单据状态、属性切换）且需验证状态流转时出，标注每个流转对应的用例。
- 画图时把未覆盖、待确认或依赖未定的节点显式标 `MISSING` 或用 `TBD` 标注；画图过程发现的缺口必须汇总进「风险与待确认」。
- 图是评审材料，不是定稿依据；评审确认验证范围后，才把对应用例写进用例矩阵。

## 示例

以下内容是示例模板，仅供参考，不得作为真实业务事实自动应用。

```md
# 采购订单测试文档

## 测试脑图

​```mermaid
mindmap
  root((采购订单测试))
    列表筛选
      按供应商
      空态/错误态
    详情展示
    状态规则
      关闭后禁审批
    风险
      关闭态可操作动作::MISSING
​```

## 测试目标

验证采购订单列表筛选、详情展示、审批状态和关闭限制符合 PRD 与接口契约。

## 测试分层

- 单元测试：筛选参数构造、状态展示映射。
- 组件测试：列表筛选表单、空态、错误态。
- 接口联调：`GET /api/purchase-orders` 查询参数与响应渲染。

## 用例矩阵

| 场景 | 前置条件 | 操作 | 预期 | 层级 | 状态 |
|---|---|---|---|---|---|
| 按供应商筛选 | 存在供应商 A/B 的订单 | 输入供应商 A 并查询 | 只展示供应商 A 的订单 | 组件/联调 | planned |
| 关闭订单限制 | 订单状态为 closed | 点击发起审批 | 操作不可用并展示原因 | 组件 | planned |

## 风险与待确认

- MISSING：后端是否返回关闭状态下的可操作动作列表。
```
