# 请求代码评审

由 `code-reviewer` / `frontend-reviewer` / `backend-reviewer` 等评审子代理按名加载的评审方法论。对实现编码后的最终 diff 做独立评审，不替代后置一致性评审。核心原则：尽早评审、频繁评审，趁问题级联前发现它。

## 触发条件

- 由代码评审子代理加载，对实现编码后的最终 diff 做独立评审
- 评审实例必须与编写该代码的实例不同（独立性是拆 reviewer 子代理的前提）
- 典型时机：完成一个任务后、完成主要功能后、合并前；卡壳或修完复杂 bug 时也值得一评

## 不适合场景

- 主代理在普通对话里不主动加载本 skill（故省略 description）
- 需求一致性核对 → 由 `consistency-check` 承担
- 评审者自己改代码 → 评审只读，修复回到 coder

## 派发要点

评审子代理只拿"评估所需的精确上下文"，不灌主会话历史，以保持聚焦并节省上下文：

- **传 diff 范围**：给出待评审的 diff（或 BASE/HEAD 提交范围），让评审者看改了什么。
- **传需求/计划**：附上这段改动应满足的需求事实源或计划条目，作为正确性判据。
- **传任务摘要**：一句话说明这段改动构建了什么。
- **不传**：编码过程的思路、试错历史、无关会话上下文。

## 评审维度

- **正确性**：逻辑是否实现预期、边界与异常是否处理
- **可维护性**：命名、结构、重复、与项目既有风格一致性
- **安全**：输入校验、注入、权限、敏感信息泄露
- **健壮性**：错误处理、失败路径、并发与资源释放
- **测试**：测试是否覆盖关键路径与边界，断言是否有效
- **栈相关**：后端关注分层/事务/一致性/幂等；前端关注组件契约/状态/空错态/可访问性

## 输出边界

- 只读评审，按 `Critical` / `Improvement` / `Nitpick` 分级给出结论，不直接改代码。
- 结论必须基于实际 diff 与可运行证据，不得伪装 PASS、不得放过 `Critical`。
- `Critical` 必须修复后才继续；`Improvement` 进入下一步前处理；`Nitpick` 可记录后续。
- 评审结论由主代理复核后决定是否回 coder 修复；评审者若有误，coder 可带技术理由反驳。
