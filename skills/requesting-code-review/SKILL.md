# Requesting Code Review（请求代码评审）

## 概述

派一个评审员子代理，在问题级联扩散之前抓住它们。评审员拿到的是主代理为评审精确构造的上下文，而**不是**主会话历史——这让评审员聚焦于工作产物本身，而不是你的思考过程，也为主代理保留继续工作的上下文。

**核心原则：评审趁早，评审常态化。**

## 触发条件

**强制：**
- 实现编码一完成（提交 PR 前）就立即评审——把评审节点提前到编码完成节点，不拖到提交时。
- 子代理驱动开发中，每个 task 完成后。
- 完成重要功能后、合入 main 前。

**有价值但非强制：**
- 卡住时（换个视角）。
- 重构前（先建立基线）。
- 修完复杂 bug 后。

## 不适合场景

- 还在方案讨论、未产生实际代码改动时。
- 纯文档产物——文档走「文档可控性后置校验」，不走代码评审。

## 边界：评审员子代理的隔离要求（强制）

- 评审员子代理与编写该代码的子代理**必须是不同实例**，主代理不得用同一上下文自评自己刚写的代码。隔离上下文既避免对自己代码的偏袒，也防止评审产生的大量 diff 污染主上下文。
- 改动**跨前后端**时，按技术栈拆成前端评审、后端评审两个独立子代理**并行**执行，各自只评所属栈，不混评。
- 评审结论统一用 `PASS`、`FAIL`、`MISSING` 表达。`FAIL`/`MISSING` 项回传主代理修复后再复审；只有全部维度 `PASS`，才允许提交本地 PR，不得让问题项静默通过。

## 如何请求评审

**1. 取改动范围（git diff 区间）：**
```bash
BASE_SHA=$(git rev-parse HEAD~1)   # 或 origin/main、或本批改动起点
HEAD_SHA=$(git rev-parse HEAD)
git diff --stat "$BASE_SHA" "$HEAD_SHA"
```
未提交的工作区改动可用 `git diff` / `git status` 圈定范围。

**2. 派评审员子代理（用平台的子代理委派能力）：**

子代理指令必须自包含，至少提供：
- **改动说明**：本次实现了什么、为什么这么改（关联到需求/缺陷）。
- **应满足的要求**：对应的实现计划、PRD、测试用例（路径或要点）。
- **改动范围**：`BASE_SHA`/`HEAD_SHA` 或具体文件清单；跨前后端时按栈分别给出。
- **期望回传**：按下列维度给 `PASS`/`FAIL`/`MISSING` 结论 + 具体问题与定位。

**3. 评审维度：**

通用（前后端共同）：正确性（业务逻辑、边界条件、并发/竞态、空值与异常路径是否真正成立）、安全（注入、鉴权、密钥泄露、越权）、性能（算法与查询复杂度、热点路径、循环内 IO、资源占用、重复计算）、规则符合性（边界校验在入口、内部无冗余防御、无错误绕行/lint 绕行）、与实现计划和测试用例的一致性、测试充分性（静态检查测试是否覆盖关键路径与异常分支；覆盖率数字以测试验证环节实测为准）、错误处理、命名与可维护性。

前端附加：门面/统一入口与目录边界（无 Deep Import、职责目录有 `index.ts`）、组件契约（Props/Emits/Expose/类型收敛）、状态与响应式正确性、交互与可访问性、空态/错误态/加载态、性能（重渲染、包体积、懒加载、大列表虚拟化）、前端交互测试是否覆盖关键路径与边界。

后端附加：分层与模块边界、接口契约与错误码一致性、数据一致性与事务边界、并发与幂等、权限/状态机校验、输入边界校验与参数化查询（防注入）、性能（N+1、索引命中、慢查询、连接/资源释放、缓存击穿）、日志与可观测性。

**4. 按反馈处理：** 收到评审结论后按 `receiving-code-review` 的方式处理——技术化核对，不表演式附和，不盲目照搬。

## 危险信号

**绝不：**
- 因为"简单"就跳过评审。
- 忽略 `FAIL` 项就提交。
- 带着未修的 `MISSING` 项继续推进。
- 跟正确的技术反馈硬抬杠。

**若评审员判断有误：**用技术理由回推，拿代码/测试证明它能成立，或请求澄清——而不是为了过关而争辩。

## 与项目链路对齐

本环节对应开发链路的「代码评审」，前置依赖「实现编码」，下游接「测试验证」与「提交 PR」。评审全 `PASS` 且测试验证通过后，才按 `github-pr-workflow` / `pr-creator` 推新分支建本地 PR（不直推 main）。
