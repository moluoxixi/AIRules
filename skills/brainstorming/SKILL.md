# 需求分析

把任务诉求转成下游计划/实现可直接消费的需求事实源。自适应输入：用户可能提供 PRD，也可能只有一句话诉求。先理解项目上下文，再按缺口补齐，产出需求事实源（含验收标准雏形供 test-design 消费）。

## 触发条件

- 编码任务进入流水线、尚无明确需求事实源
- 用户给了 PRD 但存在缺口或歧义，需要归一化为下游事实源
- 用户只给了模糊诉求，需要澄清边界后再进入计划

## 不适合场景

- 需求事实源已就绪且无歧义 → 直接进入计划阶段
- 纯 bug 修复且现象明确 → 走调试修复，不重做需求分析
- 架构/选型讨论 → 不属于本 skill 范围

## 阻断门禁（与强制阻断的核心区别）

- 歧义或关键事实缺失（`MISSING`）、存在多个合理解释（多解）时才澄清并阻断；不得一遇模糊就升级阻断。
- L0/L1（既有口径/边界内补充或修改）可直接执行，无需先出设计待批。
- L2（触及需求/架构/公共协议/权限/状态机/数据一致性/安全边界/跨模块行为）或仍有 `MISSING`/多解时，必须输出澄清问题清单或设计报告并等待用户确认。
- 先尝试读代码、知识源（项目存在 `.airules/knowledge/` 时先读 `index.md`，命中相关条目才深读）、文档补齐事实，再决定是否阻断。

## 方法

1. **评估输入**：判断是否已有 PRD 或等价需求文档。
   - 有：读取并核对是否覆盖目标、范围、角色、关键流程、验收标准；缺口逐项标 `MISSING`。
   - 无：做轻量澄清，用苏格拉底式问题暴露目标、用户、核心流程、边界、验收标准。
2. **逐个澄清**：一次一个问题，能用多选就用多选；只在缺口确实影响判定时才问，不为简单诉求强凑设计流程。
3. **探索方案（按需）**：诉求涉及多种可行路径时，提 2-3 个方案并给出推荐与理由；简单诉求可跳过。
4. **歧义处理**：关键事实缺失或多解时，输出澄清问题清单等待用户确认；不得用推断、默认值或代码反推替代用户确认。
5. **拆分超大诉求**：若诉求横跨多个独立子系统，先帮用户拆成子项目，再就第一个子项目走需求分析。
6. **产出需求事实源**：澄清闭环后，归一化为结构化需求事实源，包含验收标准雏形供 `test-design` 消费。

## 需求文档落档

需求分析阶段不得只在对话里形成结论——需求事实源必须写盘，作为下游计划/实现/评审的事实依据。

**落档路径（强制）**：

- 普通路径：`.airules/requirements/<feature-or-change>.md`
- spec 路径：`.airules/requirements/<change-id>.md`，在 `## 契约影响摘要` 节写明变更类型（新增/修改/废弃）与涉及契约路径；无需单独 `proposal.md`

**需求文档最小内容（强制模板）**：

```markdown
# <需求标题>

## 需求 ID
<REQ-xxx，全局唯一>

## 背景与目标
<为什么做，解决什么问题>

## 用户故事 / 业务场景
<用户或系统角色的核心操作路径>

## 范围
- 范围内：<明确包含的内容>
- 范围外：<明确排除的内容>

## 功能需求
<逐条列出，可判定>

## 非功能需求
<性能、安全、可用性、兼容性等，须写成可判定阈值，不得只写"要快/要稳">

## 外部可观察行为变化
<新增/修改/废弃的对外行为，若无则写"无">

## 契约影响摘要
<!-- 仅 spec 路径时填写；普通路径写"N/A（不触发 spec-workflow）" -->
- 变更类型: 新增 / 修改 / 废弃
- 涉及契约: <capability 路径，如 .airules/specs/auth/spec.md>
- change-id: <与 .airules/changes/<change-id>/ 目录对应>

## 接口 / 数据 / 权限 / 状态机 / 兼容性影响
<涉及的公共 API、数据模型、权限规则、状态转换、破坏性变更；若无则写"无">

## 验收标准雏形
<供 test-design 消费；列出可判定的通过条件>

## 未确认项
<状态标 MISSING 或 MISSING blocked；确认后更新>

## 下游追溯入口
- 任务 ID：（由 writing-plans 填写）
- 测试用例 ID：（由 test-design 填写）
```

落档路径随需求文档一起回传给主代理，供 planner / coder / consistency-reviewer 按 ID 追溯。

## 输出边界

- **需求文档落档（强制）**：澄清闭环后，需求事实源必须按上方"需求文档落档"规则写盘；不得只以对话文本交付。
- 澄清未闭环前不得定稿、不得声明需求就绪、不得进入计划阶段。
- 不替用户做产品决策；不把示例诉求当作真实需求自动落地。
- 下一步进入 `writing-plans` 生成实现计划，不在本阶段直接编码或调用实现类 skill。
- 需求事实源产出时，尾部附状态标记供下游机械判定：
  - `## 状态：ready` — 关键事实已全部确认，可进入计划
  - `## 状态：blocked` — 仍有未闭环澄清项（列表附后）
