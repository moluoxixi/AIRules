# Backend Impl Plan（后端实现计划 / 任务书）

补齐 need → plan → test → code 链路中的「后端 plan」环节：在 PRD 和测试设计就绪后、正式写后端代码前，按业务域产出可评估、可执行的后端实现任务书，让开发者先看清「后端打算怎么做」，再驱动后端代码生成。

本 skill 只负责后端侧。前端组件复用、页面布局、状态管理、API 调用属于 `frontend-impl-plan`，因为前后端的上下文来源、关注点与编码范式完全不同，混在一份 task 里会稀释各自的可评估性。

## 触发条件

- PRD（`docs/prds/` 或指定 PRD）与测试设计已就绪，需要在写后端代码前先出后端实现方案时使用。
- 用户要求生成后端实现计划、后端任务书、接口/数据模型设计、服务端开发任务拆解时使用。
- 后端代码生成前需要一份可评估的中间产物（含数据模型、接口设计、分层、后端测试）时使用。

## 不适合场景

- 只需直接改少量后端代码、无需先出实现方案时不使用。
- 需要前端实现方案（组件、页面、状态、API 调用）时用 `frontend-impl-plan`。
- PRD 关键事实缺失、未确认（大量 `MISSING`）时，不臆造实现细节；先回到澄清门禁补齐需求。
- 纯需求/纯测试/纯接口契约文档的产出，分别用 `prd-docs`、`test-docs`、`api-docs`。

## 输入

- 需求：`docs/prds/<业务域>.md`（背景、流程、字段口径、验收标准、状态规则）。
- 测试：`docs/test/<业务域>.md` 或对应测试用例（用例矩阵、回归范围）。
- 接口契约：`docs/api/`（外部接口消费约束）、`docs/out-api/`（本项目自有接口契约，如存在）。
- 架构与数据：`docs/architecture/`（分层、模块边界、依赖方向、数据流、权限模型，如存在）。

## 前置门禁

- 本环节是实现编码前的最后一道设计门禁，前置依赖需求、API 契约、测试设计就绪：开始前必须确认对应业务域的 `docs/prds/<模块>.md` 与 `docs/test/<模块>.md` 存在且非草案、关键事实非 `MISSING`；涉及接口时确认 `docs/api/`、`docs/out-api/` 对应契约就绪，涉及数据/权限时确认 `docs/architecture/` 相关事实就绪。
- 上游缺失或仍为草案/大量 `MISSING` 时，报告 `MISSING blocked`（说明缺失的上游产物）并停止，不得臆造需求、用例或契约继续出实现计划。
- 可运行 `node <AIRules>/scripts/verify-stage-gate.mjs <project-root> backend-plan <模块>` 做确定性前置校验；校验失败按 `MISSING blocked` 处理，不得绕过。

## 输出边界

- 默认只写 `docs/plan/backend/<需求模块>.md` 和 `docs/plan/backend/index.md`（后端自有索引）；用户显式指定其它位置时按指定位置写，并在文档开头说明实际位置与未同步索引的事实。
- 不写共享的 `docs/plan/index.md`：该文件若由前后端两个 skill 并发写会相互覆盖（已在纯净测试中复现）。本 skill 只维护自己目录下的 `docs/plan/backend/index.md`；前端索引归 `frontend-impl-plan` 写 `docs/plan/frontend/index.md`，两者互不写对方目录，从源头消除并发写冲突。需要项目级总览时由非并发环节单独维护一份静态 `docs/plan/index.md` 指向两个子索引，本 skill 不触碰该文件。
- 不直接生成业务代码；本 skill 只产出后端实现方案，代码由后续代码生成环节按 task 执行。
- 不设计前端页面/组件；接口设计要给出供前端消费的契约，但前端如何调用归 `frontend-impl-plan`。
- 不修改 PRD、测试、接口契约的事实口径；发现与上游冲突时标记 `MISSING` 并列出冲突，不静默改写。
- 不得把密钥、token、连接串等凭证明文写入；以配置项名称引用。

## 输出位置

- 任务书：`docs/plan/backend/<需求模块>.md`，一个需求模块一份；多模块时先在 `docs/plan/backend/index.md` 出后端任务总览（脑图 + task 导航）。
- 必须按需求模块拆分为多个文件，每模块一份；严禁把多个模块的 task 正文混写进同一文件，也严禁把所有模块汇总成单份长文档。

## 拆分粒度（关键）

- 拆分单位是「需求模块 / 功能模块」，不是粗粒度的产品域。判定粒度时跟随上游已有的最细拆分：优先对齐 PRD 业务流程划分，其次对齐 `docs/out-api/` / `docs/api/` 已拆出的接口模块，再次对齐 `docs/test/` 用例分组。
- 上游若已把一个产品域拆成多个接口模块（如「基础主数据 / 供应商发货点 / 店仓关系 / 品仓 / 仓仓线路 / 供货管理 / 供货路由」），后端任务书必须同样拆成对应的多份，而不是合并成一份产品域大文档——合并会稀释每个模块的可评估性。
- 一个需求模块对应一份任务书；模块边界以「能独立评审一块后端实现方案」为度。若上游确实只有单一模块的确认事实，则只产出该一份，并在 index 标注其余模块为 `MISSING`（上游未就绪）。

## 多域并行委派（该代理就代理）

- 当本次计划覆盖 2+ 相互独立的需求模块、且各模块写入 `docs/plan/backend/<模块>.md` 互不重叠时，默认每个模块派一个 fresh 子代理产出该模块后端任务书，主代理只做拆分、整合与复核，避免多模块上下文互相污染。
- 委派为各子代理精确构造自包含上下文：对应模块的 PRD、测试设计、接口契约（`docs/api/`、`docs/out-api/`）、架构基线（`docs/architecture/`）与本 skill 的产物结构要求；子代理不继承主会话历史。
- `docs/plan/backend/index.md`（后端任务总览）由主代理在收齐各模块产物后单独维护，不交给并发子代理写，从源头消除索引并发写冲突。
- 单一模块、或模块间存在强共享前置（如统一错误码体系、跨模块数据模型/迁移需先定稿）时不并行，由主代理串行产出或先定稿共享前置再派子代理，并在交付中说明。
- 子代理回传是自述；主代理必须按本 skill 的产物结构与可追溯要求复核每份任务书，确认 `MISSING` 标记完整后才算就绪。

## 计划粒度（关键）

- 本 skill 产出的是「后端实现思路 / 方案」，供人评估「后端打算怎么做、对不对」，不是逐步施工脚本。
- 写到「数据模型怎样、接口怎么设计、代码怎么分层、事务/一致性怎么保证、后端测试覆盖哪些用例」这一层的具体思路即可；能让评审判断方案正确性就够。
- 禁止套用通用 `writing-plans`/superpowers 计划格式：不写 `- [ ]` 勾选步骤清单、不写逐 Step 的 RED-GREEN-REFACTOR、不写每步的具体命令/commit、不展开成上千行施工手册。
- 禁止输出到 `docs/superpowers/plans/`；该目录是通用计划格式领地，与本 skill 的「方案级、按域拆分」产物不同。
- 每份任务书保持紧凑（聚焦思路），用 Mermaid 图 + 表格表达方案，而非长流程正文。

## 写作规则

- 变更分级（L0/L1/L2）与澄清门禁的定义见「变更分级与确认门禁」「澄清门禁」两节：下游已安装项目在根 `AGENTS.md` 注入块，AIRules 仓库本身在 `rules/AGENTS.md`，就近读取，找不到时按 L2 从严处理。
- 生成 task 前必须先读取对应业务域的 PRD、测试、接口契约；事实以这些上游文档为准，缺失内容标记 `MISSING`，不从代码或想象补业务规则。
- 命中澄清门禁时（涉及架构边界、公共协议、数据模型、权限/状态机、数据一致性、跨系统集成等关键事实缺失或歧义），先输出《后端实现澄清问题清单》，未确认内容保留 `MISSING`，不臆造方案。
- 每个业务域 task 内部按「实现大纲图（图在前）+ 需求背景 + 数据模型 + 接口设计 + 代码分层与职责 + 事务与一致性 + 测试落地 + 风险待确认」组织。
- 接口设计必须覆盖：方法、路径、DTO、校验、错误码；与已有 `docs/api/` / `docs/out-api/` 契约保持一致，冲突或缺失标 `MISSING`。
- 数据模型必须覆盖：实体、关键字段、关系、约束；状态字段配合状态机说明流转。
- task 必须可追溯：每条实现项标注其来源 PRD 章节、验收标准或测试用例编号，不凭空新增需求。
- 生成接口设计与任务拆解前，先调用 `knowledge-search` 在 `airules.knowledge.json` 登记来源中定位架构（`docs/architecture/`）、契约（`docs/api/`/`docs/out-api/`）、用例（`docs/test/`）、需求（`docs/prds/`）；无登记来源支撑的实现项与接口字段不得进入计划，标 `MISSING`，不从代码命名或目录暗示猜架构。
- 任务书是评估与执行材料；用户基于它评估确认后，再进入后端代码生成。

## 配图规则

- 图用 Mermaid 代码块（` ```mermaid `），放在每份 task 最前面作为实现大纲，可在语雀、GitHub、VSCode 直接渲染。
- 选图由内容驱动：
  - 后端任务脑图（`mindmap`）：必出，呈现该业务域后端任务拆解。
  - 数据模型（`erDiagram`）：有数据实体时必出，表达表/字段/关系。
  - 调用时序（`sequenceDiagram`）：跨服务/跨系统交互、关键事务流程必出（服务端视角）。
  - 状态机（`stateDiagram-v2`）：存在状态流转时出。
  - 分层/依赖图（`flowchart`）：表达 controller/service/repository 等分层与依赖方向。
- 无法确认的节点、接口或字段显式标 `MISSING`；不伪造确定结论。
