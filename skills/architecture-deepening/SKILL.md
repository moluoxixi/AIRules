# Architecture Deepening

发现架构摩擦，提出**深化机会（deepening opportunities）**——把浅模块改造成深模块的重构。目标是可测试性与 AI 可导航性。

本 skill 借鉴并改编自《A Philosophy of Software Design》(Ousterhout) 的“深模块”理念与 Michael Feathers 的 seam 概念。完整术语见 [references/language.md](references/language.md)，深化与测试策略见 [references/deepening.md](references/deepening.md)。

## 触发条件

- 用户要改进架构、找重构机会、合并紧耦合模块、让代码更易测试或更易被 AI 导航。
- 用户说“这块太碎了”“到处跳来跳去才看懂一个概念”“想重构但不知道从哪下手”。
- 在架构设计或调试中发现某片代码摩擦明显，需要系统性评估是否值得深化。

## 不适合场景

- 只是要写一个新功能或修一个具体 bug，不涉及结构性重构时，走实现计划或调试类 skill，不要用本 skill。
- 用户只要求格式整理、改名、删注释等表层清理时，不属于深化范畴。
- 缺少对目标代码的访问或领域上下文，无法做真实评估时，先补齐知识源（见项目知识源读取规范），不要凭空臆测架构问题。

## 术语（必须统一使用）

每条建议都用下列术语，不要漂移成“组件/服务/API/边界”。完整定义见 [references/language.md](references/language.md)。

- **模块（Module）**：任何有接口和实现的东西（函数、类、包、跨层切片）。
- **接口（Interface）**：调用方为正确使用模块必须知道的一切——类型签名，外加不变量、顺序约束、错误模式、必需配置、性能特征。
- **实现（Implementation）**：模块内部的代码。
- **深度（Depth）**：接口处的杠杆——小接口背后藏大量行为为**深**；接口复杂度接近实现复杂度为**浅**。
- **缝（Seam）**：接口所在之处，能在不就地改代码的前提下替换行为。（用“缝”，不用“边界”。）
- **适配器（Adapter）**：在缝处满足某接口的具体实现。
- **杠杆（Leverage）**：调用方从深度中获得的收益。
- **局部性（Locality）**：维护者从深度中获得的收益——变更、bug、知识集中在一处。

核心判据：

- **删除测试（Deletion test）**：设想删掉该模块。若复杂度随之消失，它只是个透传层；若复杂度在 N 个调用方处重现，它在挣钱（值得保留）。
- **接口即测试面。**
- **一个适配器是假想的缝，两个适配器才是真实的缝。**

本 skill 受项目领域模型约束：先读领域术语和相关 ADR，领域语言给好的缝命名，ADR 记录的决策不要重新翻案。

## 流程

### 1. 探索

先读项目领域术语表和将要触及区域的 ADR（按项目知识源读取规范）。

涉及大量文件检索与代码走读时，委派 Explore 类子代理隔离上下文（见 AGENTS.md 子代理委派规范），主代理只接收回传的摩擦点清单。不要套死启发式，按真实摩擦记录：

- 理解一个概念是否需要在多个小模块间反复跳转？
- 哪里的模块是**浅**的——接口几乎和实现一样复杂？
- 哪里为了可测试性抽出了纯函数，但真正的 bug 藏在调用方式里（没有**局部性**）？
- 哪里紧耦合模块跨缝泄漏？
- 哪些部分没测试，或通过当前接口很难测？

对每个疑似浅模块跑**删除测试**：删掉它会集中复杂度，还是只是搬走？“会集中”才是你要的信号。

### 2. 以候选清单呈现

下列卡片字段为输出结构占位说明，需用户确认后才进入实际重构；为每个深化候选产出一张卡片（用领域术语描述业务，用本 skill 术语描述架构）：

- **涉及文件**：哪些文件/模块。
- **问题**：当前架构为什么造成摩擦。
- **方案**：要改成什么样（平实描述）。
- **收益**：用局部性和杠杆解释，以及测试会如何改善。
- **改造前 / 改造后**：用文字或简图对比浅与深。
- **推荐强度**：`强烈推荐` / `值得探索` / `推测性` 三选一。

最后给一个 **首选推荐** 小节：你会先做哪个、为什么。

> 上面的卡片字段是输出结构模板（占位说明），不是真实候选；填写时用真实代码事实替换，缺失证据的字段标 `MISSING`，不得编造架构问题凑数。

**ADR 冲突**：若某候选与现有 ADR 冲突，仅当摩擦真实到值得重开 ADR 时才提出，并在卡片里明确标注（如告警：“与 ADR-0007 冲突——但值得重开，因为……”）。不要罗列 ADR 禁止的每一种理论重构。

此阶段**不要**直接给接口设计。文件/清单产出后，问用户：“想深入看哪一个？”

### 3. 深化（用户选定后）

用户选定候选后，按 [references/deepening.md](references/deepening.md) 的依赖分类决定如何跨缝测试：

- **进程内**：纯计算/内存状态，直接合并模块、通过新接口测试，无需适配器。
- **本地可替身**：有本地测试替身（PGLite 替 Postgres、内存文件系统），用替身在测试套件里跑。
- **远程但自有（端口与适配器）**：在缝处定义端口，逻辑归深模块，传输作为适配器注入；测试用内存适配器，生产用 HTTP/gRPC/队列适配器。
- **真外部（Mock）**：第三方服务以注入端口形式接入，测试提供 mock 适配器。

缝纪律：一个适配器是假想缝，两个适配器才是真实缝；不要为单适配器引入端口（那只是间接层）。

测试策略：替换而非叠加——深化后在新接口处写测试，删掉旧的浅模块单测；测试断言可观察结果而非内部状态，能在内部重构后存活。

## 输出边界

- 探索阶段产出的候选清单与卡片是**分析产物**，不直接改代码；进入实际重构前需经实现计划环节并由用户确认（重构通常命中 L2，先走变更分级与澄清门禁）。
- 不在仓库工作区落盘临时报告；若需落盘分析结果，写到 `docs/` 对应分类或临时目录，并在交付中说明。
- 缺失代码访问或领域上下文的字段标 `MISSING`，不得用代码反推业务事实，也不得编造摩擦点。
- 不重新翻案已有 ADR 记录的决策，除非摩擦真实到值得显式重开并标注。

## 失败处理

- 无法读取领域术语或 ADR 时，报告 `MISSING knowledge source` 并说明缺失项，不绕过知识源治理继续臆断。
- 删除测试无法判定（依赖太复杂看不清）时，把该候选标 `推测性` 并说明不确定来源，不夸大为强推荐。
