# 深化（Deepening）

如何在给定依赖的前提下，安全地深化一簇浅模块。沿用 [language.md](language.md) 的词汇——**模块**、**接口**、**缝**、**适配器**。

> 本文件改编自《A Philosophy of Software Design》与端口-适配器（Ports & Adapters）模式，作为本 skill 的方法参考资料，不是当前项目的业务事实。

## 依赖分类

评估一个深化候选时，先给它的依赖分类。类别决定深化后的模块如何跨缝测试。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。永远可深化——合并模块，直接通过新接口测试，无需适配器。

### 2. 本地可替身（Local-substitutable）

有本地测试替身的依赖（PGLite 替 Postgres、内存文件系统）。替身存在即可深化。深化后的模块在测试套件里用替身运行。缝是内部的；模块外部接口处不暴露端口。

### 3. 远程但自有（端口与适配器 / Ports & Adapters）

跨网络边界的自有服务（微服务、内部 API）。在缝处定义**端口**（接口）。深模块持有逻辑，传输作为**适配器**注入。测试用内存适配器，生产用 HTTP/gRPC/队列适配器。

推荐表述：*“在缝处定义端口，为生产实现 HTTP 适配器、为测试实现内存适配器，使逻辑集中在一个深模块里，即便它跨网络部署。”*

### 4. 真外部（Mock）

你不控制的第三方服务（Stripe、Twilio 等）。深化后的模块以注入端口形式接收外部依赖；测试提供 mock 适配器。

## 缝纪律

- **一个适配器是假想缝，两个适配器才是真实缝。** 除非至少两个适配器有理由存在（通常是生产 + 测试），否则不要引入端口。单适配器的缝只是间接层。
- **内部缝 vs 外部缝。** 深模块既可有内部缝（私有于实现、供自身测试用），也有接口处的外部缝。不要只因测试用到就把内部缝暴露到接口上。

## 测试策略：替换，不要叠加

- 一旦深化模块接口处有了测试，浅模块上的旧单测就成了废料——删掉它们。
- 在深化模块的接口处写新测试。**接口即测试面。**
- 测试断言通过接口可观察的结果，而非内部状态。
- 测试应能在内部重构后存活——它们描述行为，不描述实现。若实现一变测试就得改，说明它测过了接口。
