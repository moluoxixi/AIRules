# 架构语言（Language）

本 skill 每条建议共用的词汇。严格使用这些术语——不要替换成“组件/服务/API/边界”。语言一致是整个方法的核心。

> 本文件改编自《A Philosophy of Software Design》(Ousterhout) 与 Michael Feathers 的 seam 概念，作为本 skill 的术语参考资料，不是当前项目的业务事实。

## 术语

**模块（Module）**
任何有接口和实现的东西。刻意做到尺度无关——同样适用于函数、类、包、跨层切片。
_避免_：单元、组件、服务。

**接口（Interface）**
调用方为正确使用模块必须知道的一切。包含类型签名，但也包含不变量、顺序约束、错误模式、必需配置、性能特征。
_避免_：API、签名（太窄——只指类型层表面）。

**实现（Implementation）**
模块内部的代码。与**适配器**区分：一个东西可以是“小适配器 + 大实现”（Postgres 仓储），也可以是“大适配器 + 小实现”（内存假实现）。谈缝时用“适配器”，否则用“实现”。

**深度（Depth）**
接口处的杠杆——调用方（或测试）每学习一个单位的接口，能驱动多少行为。大量行为藏在小接口背后即**深**；接口几乎和实现一样复杂即**浅**。

**缝（Seam）**（源自 Michael Feathers）
能在不就地改代码的前提下替换行为的位置。模块接口所在的*位置*。把缝放在哪里是一个独立的设计决策，与缝后面放什么不同。
_避免_：边界（与 DDD 的限界上下文重载）。

**适配器（Adapter）**
在缝处满足某接口的具体实现。描述的是*角色*（填哪个槽），不是实质（里面是什么）。

**杠杆（Leverage）**
调用方从深度中获得的收益。每学习一个单位接口获得更多能力。一份实现在 N 个调用点和 M 个测试间回本。

**局部性（Locality）**
维护者从深度中获得的收益。变更、bug、知识、验证集中在一处而非散落到各调用方。改一处，处处改好。

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小的、可 mock、可替换的部件组成——它们只是不属于接口。模块可以有**内部缝**（私有于实现，供自身测试用），也有接口处的**外部缝**。
- **删除测试。** 设想删掉该模块。若复杂度消失，模块没藏东西（是透传层）；若复杂度在 N 个调用方处重现，模块在挣钱。
- **接口即测试面。** 调用方和测试穿过同一条缝。若想测试接口*之外*，模块形状大概不对。
- **一个适配器是假想缝，两个适配器才是真实缝。** 除非确有东西跨缝变化，不要引入缝。

## 关系

- 一个**模块**恰好有一个**接口**（呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，以其**接口**为标尺度量。
- **缝**是**模块**的**接口**所在之处。
- **适配器**坐落在**缝**处并满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 被否决的框定

- **深度 = 实现行数 / 接口行数比值**（Ousterhout 原始定义）：会奖励给实现注水。我们改用“深度即杠杆”。
- **“接口” = TypeScript 的 `interface` 关键字或类的公共方法**：太窄——这里的接口包含调用方必须知道的每个事实。
- **“边界”**：与 DDD 限界上下文重载。请说**缝**或**接口**。
