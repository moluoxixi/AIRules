# TDD（红绿重构）

核心逻辑的实现纪律：测试先行，给 agent 客观的、不可粉饰的停止信号。

## 触发条件

- 实现阶段、编写逻辑明确且边界可枚举的核心逻辑
- 验收用例清单已就绪，需要逐条落实为可运行测试

## 不适合场景

- 集成/UI/端到端等红绿成本高的场景 → 用事后测试 + 实际运行验证兜底
- 纯探索性 spike（明确会丢弃）→ 不强制
- 测试用例的设计 → 由 `test-design` 承担

## 红绿重构循环

1. **红**：按验收用例写一个测试，运行并确认它**因正确的原因失败**（功能未实现，而非测试写错）。
2. **绿**：写最小代码让测试通过，不提前实现未被测试覆盖的功能。
3. **重构**：在测试保持绿的前提下整理代码与测试。
4. 循环下一条用例。

铁律：没有先看到失败的测试，不写生产代码；不得写完代码后补一个"顺手就过"的测试。

## 输出边界

- 测试与代码成对产出；后端单测细则见 `unit-testing`，前端交互测试细则见 `interaction-testing`。
- 不得为了让测试通过而删断言、放宽断言或跳过用例。
- 红阶段必须真实运行并读取失败输出，不得假设测试会失败。
