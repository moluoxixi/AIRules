# Reflect（反思归因）

产物不符合预期或规范时，诊断**根因属于哪一类**，给出证据与指向具体文件/流程节点的修复建议，并把可复用教训路由到 `remember`。这是进化闭环的"诊断"端：不只是修当前产物，而是定位"为什么会写成这样"，让 skill / rule / 执行方式本身被纠正。

## 触发条件

- 用户说"这文档/产物不符合规范 / 为什么会这样 / 复盘一下 / reflect"，或对已交付产物表达不满、要求追因时按名调用。

## 不适合场景

- 单点笔误、已明确定位的小 bug → 直接修，不必走归因流程。
- 产物其实符合规范、只是用户偏好不同 → 那是需求澄清，不是根因归因。
- 证据不足以支撑归因（看不到产物、看不到所依据的 skill/rule、不知道用户的"规范"具体指什么）→ 标 `MISSING` 并先索取证据，不臆造根因。

## 归因维度

按 AIRules 资产层级定位根因（对齐 `CLAUDE.md`「规则资产层级判定」，**不跨层归因**）。一个问题可命中多类，逐条列证据：

| 根因类别 | 判据 | 典型证据 |
|---|---|---|
| **skill 缺陷** | 照着 skill 做也会错——触发条件/不适合场景/流程写得有歧义、缺失或自相矛盾 | 指出 skill 文件里那段含糊或缺失的指令 |
| **rule 缺陷** | baseline (`rules/AGENTS.md`) 或项目规则与期望冲突、或留白未覆盖该场景 | 指出规则文件里冲突/缺失的条款 |
| **书写偏移** | skill 和 rule 都正确，但执行时偏离了它们——没按流程走、漏了门禁、把示例当真实事实 | 对比"规则要求"与"实际产物"的偏差点 |
| **输入缺陷** | 根因在上游——需求/PRD 本身 `MISSING` 或歧义，规则资产无责 | 指出输入里缺失或多义的关键事实 |

## 流程

1. 收集证据：被认定有问题的产物、用户的具体不满点（"不符合规范"指哪条规范）、产出该产物时所依据的 skill / rule。
2. 判定资产层级：产物属于 repo-maintenance / global-baseline / project-init / generated-project 哪一层，归因只在该层及其依据的规则资产内进行。
3. 逐维度核对上表判据，命中即记录证据；证据不足的维度标 `MISSING`，不强行归类。
4. 输出归因报告 + 修复点 + 教训路由（见下）。

## 输出

```markdown
## 反思归因 — <产物/问题简述>

### 资产层级
<generated-project / project-init / global-baseline / repo-maintenance 之一>

### 根因
- [skill 缺陷 | rule 缺陷 | 书写偏移 | 输入缺陷]：<结论> — 证据：<指向具体文件:行 或 流程节点>
  （可多条；无命中的维度标 N/A，证据不足标 MISSING）

### 建议修复点
- <指向具体 skill/rule 文件或流程节点的可执行修复>

### 可复用教训
- <若有跨任务复用价值的事实/教训 → 路由 remember（用户当场确认即写）或 distill-candidates（提炼成记忆候选待审）落 .airules/memory/；
   若是"该怎么做"的程序性模式 → 路由 distill-candidates 提炼 skill 候选待审；
   一次性偶发 → 不沉淀>
```

## 纪律

- 只诊断、不臆造：每条归因必须有证据；证据不足标 `MISSING`，不猜根因。
- 不跨层归因：generated-project 的问题不归咎于 repo-maintenance 规则，反之亦然。
- 状态用 `PASS` / `FAIL` / `MISSING` / `NOT RUN` / `N/A`，不把"没查到"写成"没问题"。
- 教训只路由不直接固化：本 skill 不自行写记忆或 skill 候选，由 `remember`（显式即写）/ `distill-candidates`（提炼候选待审）落盘（保持单一职责与写入边界）。
