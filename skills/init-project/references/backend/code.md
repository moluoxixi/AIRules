# 后端工程架构与代码规范

在执行任何后端代码生成、重构或评审任务时，必须没有例外地遵守以下与语言/框架无关的物理架构与代码交付红线。具体语言或框架的附加约束见 `backend/node.md`、`backend/nestjs.md`、`backend/java.md`；消费外部 API/SDK 的防腐与文档约束见 `backend/api-consumer.md`；对外 API 契约文档约束见 `backend/out-api.md`。

## 0. 适用边界

- **项目事实优先**：先读取当前项目的语言版本、框架、构建配置、测试入口和既有分层/目录约定；不得为了套用本规范擅自升级依赖、改写项目架构或伪造验证入口。
- **语言规范叠加**：本规范是后端通用层；与语言/框架规范冲突时，先按项目既有事实，再按更具体的语言规范，不得用通用规范覆盖项目真实约定。

## 1. 分层架构与防腐红线

- `Domain` 承载核心业务规则，禁止依赖 HTTP/RPC 框架、ORM、外部 SDK、序列化库或任何技术细节。
- `Infrastructure` 负责封装数据库、外部服务与 SDK，禁止反向污染领域类型定义或把外部类型泄漏进 Domain。
- `Transport`（Controller/Route/Resolver/Handler）层仅处理参数提取、输入校验与协议映射，禁止直接编写业务逻辑或操作数据库。
- `Application`（UseCase/Service）层负责编排业务流程与界定事务边界，禁止透传 `req`、`res`、`reply`、`ctx` 等框架宿主对象。
- 业务 Helper 必须就近留在 Feature 模块内；禁止设立无业务语义的全局 `utils` 目录，全局共享目录仅限纯技术工具。
- 类与文件必须保持职责内聚，对外暴露集合或可变结构时优先返回不可变视图。

## 2. 契约边界与输入校验

- 外部输入输出边界（CLI 参数、HTTP/RPC 入参、消息载荷、环境变量、配置、外部接口响应、文件读取）必须在入口处做显式校验。
- 进入 Application/Domain 层后，禁止重复编写基础防御性代码；校验只在边界做一次。
- API 边界与用例交互必须使用显式 DTO/Command 类型；Domain Entity 与 UseCase Command 必须是纯业务语义类型，禁止复用 Transport 层推导出的传输类型。
- 列表/查询入参必须显式约束分页上限与排序字段白名单，禁止信任客户端传入的开放排序或无上限分页。
- 多租户或带权限作用域的数据，作用域标识（如 `tenantId`、`userId`）必须从服务端可信会话获取，禁止信任客户端载荷。
- 拼接数据库查询时强制使用参数化查询或绑定变量，禁止字符串拼接用户输入。

## 3. 事务与错误传播

- 禁止将底层数据库事务句柄（`EntityManager`、`QueryRunner`、`Knex.Transaction`、`Prisma.TransactionClient` 等）透传给 Domain 或 Application；事务上下文必须通过 UnitOfWork 或上下文隔离机制传递。
- 禁止将远程网络调用、RPC 或耗时外部 I/O 裹挟在数据库同步事务中；跨系统一致性使用 Transactional Outbox 或等价模式。
- 业务代码只抛出自定义领域/应用错误，并保留原始异常上下文（如 `cause`），禁止吞掉异常或丢失堆栈。
- 捕获异常只允许用于补充上下文或释放资源后重新抛出，禁止 catch 后返回伪装的成功状态或 `200`。
- 协议状态码/错误码转换统一交由全局错误处理器（Exception Filter、error middleware、ExceptionHandler 等）处理，禁止在业务层散落硬编码状态码。
- 错误必须显式暴露，禁止静默降级、绕行或把失败伪装成功。

## 4. 开发评审门槛

- 触发以下任一条件时，禁止直接生成生产代码或测试代码；必须先输出《后端实现与测试设计报告》，等待开发者确认后再进入生成阶段：
  - 新增、重构或修改对外 API/RPC 契约、错误码、公共 DTO/schema、领域模型或模块对外接口。
  - 涉及权限模型、鉴权流程、状态机流转、数据一致性、事务边界、并发/幂等或跨模块编排。
  - 涉及数据库 schema、迁移、索引策略、外部服务集成、消息/事件契约或缓存策略。
  - 需要决定测试分层、Mock/fixture 策略、集成测试范围、覆盖率边界或异常路径验证方式。
  - 修改分层边界、依赖方向、框架集成方式、构建配置或测试配置。
  - 需求存在多个合理实现方案、验收标准不明确、存在迁移成本，或可能影响安全、性能、数据安全和错误处理。
- 同时满足以下条件时，可跳过前置评审直接实现，并在交付说明中报告依据：在既有契约与分层模式内的局部新增或修改、无对外契约变化、无新增权限/状态机/事务边界、无数据库 schema 变更、测试策略可直接沿用现有模式、存在可精准执行的验证脚本。
- 《后端实现与测试设计报告》必须包含：项目事实证据、改动范围、接口/数据模型契约、分层与事务方案、实现方案、测试分层与用例清单、Mock/fixture 策略、风险点和验证命令。报告阶段只允许读取和分析，不得创建或修改生产代码与测试文件。

## 5. 强制测试交付要求

- 进入实现阶段后，修改 Transport、Application、Domain、Infrastructure、DTO/schema、错误映射、事务边界、权限校验或可复用工具逻辑时，必须同步交付有效测试代码。
- 测试目录优先沿用项目既有约定；缺少约定时，按所属语言规范的目录约定放置（见 `backend/node.md`、`backend/nestjs.md`、`backend/java.md`）。
- Domain、UseCase 和纯业务逻辑必须优先交付单元测试，验证业务契约、边界条件和异常路径，并隔离外部依赖。
- Transport、输入校验、错误处理和鉴权上下文必须交付接口或模块级测试，显式断言状态码/响应结构、校验失败、权限失败和错误映射。
- Repository、UnitOfWork、事务、数据库约束或外部 SDK 适配器必须交付集成测试；优先使用项目既有测试数据库、Testcontainers 或等价隔离环境。
- 禁止只保留“能启动”“能编译”“接口返回 200”等低价值烟雾测试；必须显式断言数据、错误、事务和持久化契约，不得删除断言或降低阈值凑覆盖率。
