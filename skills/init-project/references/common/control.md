# 变更分级与确认门禁

## 变更分级

- 任何生成、修改、删除动作开始前，必须先判定变更级别 L0、L1 或 L2，并在交付中说明判定依据；无法判定时按更高一级处理。
- L0：在既有口径、契约或模式内补充，不改变任何对外事实。包括补字段说明、示例、变更记录，或在既有测试模式下补用例。可直接执行，交付中说明改动与验证结果。
- L1：在既有边界内新增或修改，不触及对外口径、公共协议、模块边界、权限、状态机、数据一致性或安全边界。可直接执行，交付中附级别判定依据和验证结果。
- L2：触及需求口径、架构边界、公共协议、权限模型、状态机、数据一致性、安全边界、跨模块行为，或修改项目规则、AI skills、初始化流程、默认配置。必须先完成澄清门禁并输出对应报告或计划，等待用户确认后才能执行。
- 判定边界模糊、同一动作可能横跨多级，或缺少判定所需事实时，必须按 L2 处理，不得擅自降级。

## 澄清门禁

- 触发条件：命中 L2，或目标、角色、边界、流程、字段、状态、验收标准、冲突、风险中任一关键事实缺失（`MISSING`）或存在多个合理解释（歧义）。
- 触发后必须先输出《澄清问题清单》或对应设计报告，用苏格拉底式问题逐项暴露上述维度；未确认内容必须保留为 `MISSING`，不得用推断、默认值或代码反推替代。
- 澄清未闭环前不得定稿、不得写入正式产物、不得声明完成；只有用户确认或补齐事实后才能继续。
- 轻微、无歧义且用户已给出明确指令的 L0 改动不强制澄清，但仍需在交付中说明判定依据。

## 开发链路控制

按开发环节选择对应控制资产，每个环节的失败、缺失或未确认都必须显式暴露，不得跳过或伪装通过：

| 开发环节 | 控制资产 | 必需控制点 |
|---|---|---|
| 需求进入 | `prd-docs`、`knowledge-search` | 背景、范围、用户流程、字段口径、验收标准、缺失项状态 |
| 架构设计 | `architecture-docs` | 模块边界、依赖方向、数据流、权限模型、ADR |
| API/组件契约 | `api-docs`、`components-docs` | 请求响应、错误码、字段含义、联调状态、组件边界 |
| 实现编码 | 项目规则、TDD/调试类 skills | 边界校验在入口，内部不重复防御，错误显式暴露 |
| 调试修复 | `systematic-debugging`、`retrospective-correction` | 先定位根因再修复，偏差按级别处理 |
| 测试验证 | `test-docs`、`verification-before-completion` | 测试策略、用例矩阵、回归范围、真实命令输出 |
| 代码评审 | `code-reviewer`、`requesting-code-review` | 安全、质量、规则符合性、测试充分性 |

- 进入任一环节前先按「变更分级」判级，命中 L2 或关键事实缺失时先走「澄清门禁」。
- 文档类产出（需求、架构、API、组件、测试）在事实缺失时标记 `MISSING`，不得用代码反推业务事实。
- 实现、测试、评审的检查结果统一使用 `PASS`、`FAIL`、`MISSING`、`NOT RUN`、`N/A`，任一门禁失败不得声明可交付。
