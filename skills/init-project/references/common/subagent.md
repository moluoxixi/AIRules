# 子代理委派

## 委派判断

- 子代理的核心价值是隔离上下文：把会产生大量中间信息（多文件检索、长命令输出、调研与复现）的工作交给独立上下文的子代理执行，主代理只接收回传结论，避免主上下文被中间过程污染。
- 是否委派先判断规模：单一、范围明确且交接成本高于收益的小任务由主代理直接做；只有任务会产生大量主代理无需保留的中间信息，或包含多个可拆分工作域时才委派。
- 独立则并行：任务包含两个或更多相互独立的问题域、模块、测试失败、文件范围或研究方向，且写入范围不重叠、无先后依赖时，拆成可独立验证的子任务并行委派。
- 依赖则串行：任务存在先后依赖但仍冗长时，采用包工头模式——主代理先产出完整计划，再逐个委派、逐个验收，禁止对存在依赖或共享写入范围的任务并行委派。
- 紧耦合不拆：共享状态、同一文件强耦合或拆分成本高于收益时不委派子代理，由主代理直接执行，并在交付中说明不拆分的原因。

## 关键环节子代理调度索引（什么时候调用什么子代理）

开发链路的关键环节默认走子代理隔离上下文，主代理只做拆分、协调、整合与复核。若当前项目另有「任务分诊」定义，以项目定义为准；未定义时按最小口径判定：feature=新增对外行为，bugfix=复现并修复缺陷，refactor=对外行为等价的结构调整，chore=依赖/脚手架/配置/纯文档。下表给出每个环节的委派形态与判据；命中「主代理直接做」的小规模例外时，必须在交付中说明为何不委派。`skill` 决定知识内容和方法论，`subagent` 决定上下文隔离、并行和反自评边界；不得因为“角色特点不同”就自动拆 agent。表中的具名 agent 按当前 AIRules 第一方 `agents/` 映射；宿主不支持同名 agent 时，按同等职责与隔离边界选择可用子代理。

| 环节 | 默认委派形态 | 该走子代理的判据 | 主代理直接做的例外 |
|---|---|---|---|
| 多源只读调研 | 临时研究子代理（非固定 `agents/` 文件，可用宿主 explorer 能力）并行检索独立证据域，回传结论与证据句柄 | 需要并行检索 2+ 独立文档树、代码域、长日志或外部来源 | 单一文件、单条命令、交接成本高于收益 |
| 实现计划 | `frontend-planner` / `backend-planner`；多业务域并行时每个业务域一个子代理产出该域实现计划/任务书 | 计划覆盖 2+ 相互独立的业务域/模块，且写入目录不重叠 | 单一业务域、范围明确、交接成本高于收益 |
| 实现编码 | `frontend-coder` / `backend-coder`；按实现计划的 task 派 fresh coding 子代理，一个独立 task 一个子代理 | task 之间无先后依赖、写入范围不重叠，且会产生主代理无需保留的大量 diff | 单文件小改、紧耦合改动、需主代理连续掌控的探索性编码 |
| 调试修复（bugfix 前置） | `debugger` 复现并定位根因，回传根因结论 + 建议修复点 + 回归测试设计；多失败域时每域一个调查子代理 | bugfix 进入修复前根因未定位，或调查会产生大量日志/复现输出；多个相互独立的失败（不同测试文件/子系统/bug） | 单点明确的小 bug、根因已定位，主代理直接修 |
| 代码评审 | `frontend-reviewer` / `backend-reviewer`；编码完成即起独立评审员子代理，跨前后端按栈并行 | 任何进入提交前的实现编码改动（强制，见下「后置子代理评审与校验」） | 无例外：评审强制走独立子代理，主代理不得自评 |
| 测试验证 | 临时验证子代理（非固定 `agents/` 文件，加载 `verification-before-completion`）/ 对应栈子代理 | 验证命令输出量大、涉及多模块、或需要长时间运行 | 单条命令、输出短、主代理可直接读结果 |
| 文档可控性校验 | 临时 clean/headless validator（非固定 `agents/` 文件，仅输入规则 + 被校验产物） | 任何需校验自足性与 `MISSING` 标记完整性的文档产物（强制，见下「后置子代理评审与校验」） | 无例外：校验强制走干净隔离子代理 |
| 规则自足性校验 | 临时 clean/headless validator（非固定 `agents/` 文件，仅输入规则、目标产物和必要 rubric） | 修改 `rules/AGENTS.md`、`rules/sources/*.md`、根 `AGENTS.md`/`CLAUDE.md` 投影或 init-project reference 后，需要验证规则脱离主会话仍自足 | 无例外：无法提供干净隔离时标记 `MISSING` 或 `NOT RUN`，不得由主上下文自评为 `PASS` |
| 架构深化/重构 | `architecture-refactor`（仅已确认 DC-*）/ 研究子代理或 `architecture-deepening`（未确认目标）；必要时再派 coder 落地 | 用户已确认具体 DC-* 候选，且需要落地行为等价重构；未确认目标但需结构分析时先做研究或深化候选发现 | 仅发现机会、未确认推进、用户未确认具体 DC-* 或纯格式清理 |

委派这些环节时遵循以下方法论（吸收自成熟多代理实践）：

- **fresh 子代理 per task**：每个 task 派全新子代理，不继承主会话历史；主代理为它精确构造所需上下文（文件路径、契约、约束、期望回传），既让子代理聚焦不跑偏，也为主代理保留协调用的上下文。
- **自包含与复核**：每次委派必须给子代理自包含指令；所有回传都必须由主代理用路径、diff、命令输出、URL 或日志复核后才能对外声明。
- **不同实例与拆分理由**：reviewer 必须与 coder 是不同实例；拆出独立 agent 必须命中隔离、并行或独立性之一，不得只因角色特点不同就拆 agent。
- **headless / 干净隔离**：文档可控性、规则自足性、skill 纯净测试等校验必须使用干净隔离上下文；无法提供时标记 `MISSING` 或 `NOT RUN` 并说明原因，不得用非干净执行替代通过。干净隔离指无主会话历史、无宿主 AGENTS/baseline、无额外引导；可使用只读工具、文件系统快照和显式注入的必要规则/产物/rubric。
- **两段评审**：实现编码类 task 完成后，默认由同一 reviewer 报告分两段输出——先检查是否满足计划/用例，再检查代码质量；只有跨栈或独立性/上下文隔离收益明确时才拆多个 reviewer。任一阶段 `FAIL` / `MISSING` 都回到修复，不得静默放行。
- **连续执行不空转请示**：已有用户确认、门禁已闭环且存在可执行计划时，主代理逐个委派、逐个验收，不在 task 之间反复向用户确认"是否继续"。遇到 L2、`MISSING` / conflict、风险升级、关键歧义、用户要求确认或全部完成时必须停下。
- **计划任务书必须可被零上下文子代理执行**：实现计划的每个 task 要细到一个对本代码库零背景的工程师也能照做——明确改哪些文件、做什么、怎么验证；这是计划环节能安全并行委派的前提。

## 委派契约

- 子代理指令必须自包含：子代理不继承主会话历史，委派时必须显式提供文件路径、错误信息、约束边界和期望回传内容；指令越具体，子代理越不会偏离范围。
- 模型选择：负责生产代码生成、Bug 修复、重构、迁移或自动修改文件的子代理，必须使用当前可用的高质量 coding 模型；只读研究、日志收集、测试执行或失败复现类子任务可使用更低成本模型，但不得产出未经主代理复核的代码修改。
- 主代理保留协调职责：判断依赖关系、分配所有权、整合结果、处理冲突，并在最终交付前运行必要质量检查。
- 所有子代理回传均为自述，不是已验证事实；涉及文件改动、命令输出、远端副作用、`PASS`/`FAIL` 结论时，主代理必须用可验证句柄（路径、diff、命令输出、URL 或日志）复核后才能对外声明。
- debugger（调试修复前置）委派契约：bugfix 链委派 debugger 子代理时必须自包含——显式提供失败现象、复现步骤、相关文件路径与约束边界；debugger 只读诊断、回传「根因 + 证据 + 建议修复点 + 回归测试设计」，不直接改生产代码（修复由 coder 按回传执行），复杂/跨栈 bug 可落盘 `docs/diagnosis/<bug>.md` 交接；回传是自述，主代理须用可验证句柄（复现命令输出、定位到的代码位置）复核后才据此驱动修复。
- 「角色特点不同」与「需独立 agent」是两层判断，不可混淆：角色有不同关注点/输入/范式 → 决定是否需独立知识内容（skill），不直接决定 agent；是否拆出独立 agent 取决于容器级三理由命中其一——①隔离收益（产生大量主代理无需保留的中间 token）②可并行（不重叠文件树/文档树同时跑）③独立性要求（写的人必须≠评的人）。仅特点不同但无三理由之一时，用独立 skill 承载差异、共用 agent，不另起 agent。

## 后置子代理评审与校验（强制）

下列环节完成后，必须由独立上下文的子代理做后置处理，主代理不得用同一上下文自评定稿：

- 编码后代码评审（强制）：实现编码一完成（提交 PR 前），就必须起独立上下文的评审员子代理评估代码质量，把评审节点提前到编码完成节点，不拖到提交时才评。隔离上下文避免主代理对自己刚写的代码偏袒，也防止评审过程的大量 diff 污染主上下文。评审员子代理与编写该代码的子代理必须是不同实例，不得自评。改动跨前后端时，按技术栈拆成前端评审、后端评审两个独立子代理并行执行，各自只评审所属栈的改动，不混评。评审结论统一用 `PASS`、`FAIL`、`MISSING` 表达，`FAIL`/`MISSING` 项回传主代理修复后再复审；只有全部维度 `PASS` 后，才允许提交本地 PR，不得让问题项静默通过。
  - 通用评审维度（前后端共同）：正确性（业务逻辑、边界条件、并发/竞态、空值与异常路径是否真正成立）、安全（注入、鉴权、密钥泄露、越权）、性能（算法与查询复杂度、热点路径、循环内 IO、内存与资源占用、是否有不必要的重复计算）、规则符合性（边界校验在入口、内部无冗余防御、无错误绕行/lint 绕行）、与实现计划和测试用例的一致性、测试充分性（评审阶段先静态检查测试是否覆盖关键路径、边界与异常分支；覆盖率数字以下游测试验证环节实测为准，不在评审阶段臆断）、错误处理、命名与可维护性。
  - 前端评审维度：门面/统一入口与目录边界（无 Deep Import、职责目录有 `index.ts`）、组件契约（Props/Emits/Expose/类型收敛）、状态与响应式正确性、交互与可访问性、空态/错误态/加载态处理、性能（重渲染、包体积、懒加载、大列表虚拟化）、前端交互测试是否覆盖关键路径与边界。
  - 后端评审维度：分层与模块边界、接口契约与错误码一致性、数据一致性与事务边界、并发与幂等、权限/状态机校验、输入边界校验与参数化查询（防注入）、性能（N+1、索引命中、慢查询、连接/资源释放、缓存击穿）、日志与可观测性。

## 提交本地 PR

代码评审全部 `PASS` 且测试验证通过后，提交本地 PR（按 `git_safety` 推送到新分支，不直推 main）。PR 描述由主代理基于评审结论与验证结果编写，必须包含：

- 标题：祈使句、概括本次改动，控制在 70 字符内；细节放描述。
- 变更摘要：本次改动做了什么、为什么这么改（关联到需求/缺陷）。
- 关联上游：对应的 `docs/prds/<模块>`、`docs/test/<模块>`、实现计划文档或 issue 编号，便于追溯。
- 改动范围：涉及的模块/目录/关键文件，跨前后端时分栈列出。
- 测试情况：实际运行的命令、结果（`PASS`/`FAIL`）、覆盖率数字、未执行项与原因；不得伪造或省略失败项。
- 评审结论：前端/后端评审员子代理的结论（全部 `PASS`），以及修复并复审过的问题摘要。
- 风险与待确认：已知风险、被阻断的功能、标记为 `MISSING` 的未决项；没有则写"无"。
- 回滚方式：必要时如何回退本次改动。

PR 描述只陈述已验证的事实；未经命令输出或文件确认的结论不得写成已完成。
- 文档产物可控性后置校验：需求、测试设计、实现计划等文档产物生成后，做可控性校验时起干净隔离子代理，仅以「规则 + 被校验产物」为输入，不注入主会话历史和引导性提示，判断产物是否自足、触发条件是否清晰、是否漏标 `MISSING`、产物结构是否缺项。暴露的缺口必须回填到产物或上游 skill 后复测，不得用额外提示词在校验中补救掩盖缺陷。
- 前置测试用例编写：测试设计（`test-docs`）作为实现编码前的前置门禁，前端模块必须覆盖前端交互测试（组件交互、表单校验、状态流转、空态/错误态、关键用户操作路径与 E2E），不止接口联调；该前置产物经评估确认后才进入实现编码。
- 后置子代理只能补充上下文、暴露问题或回传等价失败语义，不得绕过、降级或伪装上游门禁的失败结果。
