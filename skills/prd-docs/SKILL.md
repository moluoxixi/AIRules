# PRD Docs

## 触发条件

- 用户要求生成、更新或标准化业务需求文档、业务流程、字段口径、验收标准或需求变更时使用。
- 用户要求在写正式 PRD 前先出需求脑图、流程泳道图等评估前置大纲，方便快速理解和评估需求时使用。
- PRD 需要与架构、API、组件或测试文档建立导航关系时使用。

## 不适合场景

- 只需要从代码推断实现细节，或用户没有确认业务规则时不要使用。
- 跨业务域拆分、合并或调整口径时，不要直接写定稿；先输出报告等待确认。

## 输出边界

- 默认只写 `docs/prds/`、`docs/prds/index.md` 和 `docs/map.md`。
- 当用户或任务显式指定其它输出文件或目录时，按指定位置写入；此时不强制同步 `docs/prds/index.md` 与 `docs/map.md`，但必须在文档开头说明实际输出位置与未同步索引/地图的事实，不得静默偏离默认边界。
- 不修改代码、接口协议、测试策略或其它正式文档的事实口径。
- 不得把原始资料中的密钥、token、appKey 等敏感凭证明文写入文档；发现时以配置项名称引用，并在「风险与待确认」标记 `MISSING` 凭证治理项。

## 输出位置

- 需求模块文档：`docs/prds/<需求模块>.md`，一个需求模块一个文件；每个文件内部按「评估前置大纲 + 正式 PRD」两部分组织。
- 项目总览（多模块时必出）：`docs/prds/index.md` 承载项目级需求脑图（呈现需求模块全景）和模块文档导航；不得把多个需求模块的正式 PRD 正文混写进同一文件。
- 地图路径：`docs/map.md`
- 图渲染产物（可选）：本地预览物，不写入正式文档目录，默认不提交。

## 拆分粒度（关键）

- 拆分单位是「需求模块 / 功能模块」，不是粗粒度的产品域或项目名。一个项目（如「仓网中心」）通常含多个并列需求模块，必须拆成多份，严禁把整个项目当成单个业务域合并成一份大文档。
- 判定粒度时跟随源料已有的最细需求划分：优先对齐原始需求里「需求列表 / 需求明细」的模块条目（每个三级标题或需求项一个模块），其次对齐业务流程的独立环节。被删除线（`~~...~~`）标记的废弃/暂缓需求不产出文档。
- 示例（仅占位，按真实源料替换）：若源料「需求明细」列出「仓库管理 / 区域管理 / 供应商发货点管理 / 店仓关系 / 品仓管理 / 仓仓线路管理 / 供应商供货管理 / 多级供货网络路由」等并列模块，则每个有效模块各出一份 `docs/prds/<模块>.md`，而非合并成一份「仓网中心.md」。
- 模块边界以「能独立评审一块需求」为度；若源料确实只有单一模块的确认事实，才只产出一份，并在 index 说明其余为 `MISSING`（源料未就绪）。

## 写作规则

- 先读取 `docs/map.md`、`docs/prds/index.md`、相关架构文档、API 文档和同需求模块已有文档；已有事实必须保留并合并。
- 只写已确认需求；缺失内容标记为 `MISSING`，不得从代码或接口猜业务规则。
- 变更分级（L0/L1/L2）与澄清门禁的统一定义见「变更分级与确认门禁」「澄清门禁」两节：下游已安装项目在根 `AGENTS.md` 注入块中，AIRules 仓库本身在 `rules/AGENTS.md`；按当前所在项目就近读取，两处任一存在即以其为准，找不到时按 L2 从严处理。
- 命中澄清门禁时（属于 L2，或目标、角色、边界、流程、字段、状态、验收、冲突、风险中任一关键事实缺失或存在歧义），必须先输出《需求澄清问题清单》或《需求拆分与口径报告》，用苏格拉底式问题逐项暴露上述维度；未确认内容必须保留为 `MISSING`，不得从代码或接口猜业务规则。
- 澄清未闭环时，允许并推荐同时产出「评估前置大纲 + 正式 PRD 草案」，但必须在文档标题或开头显式标注为草案/待确认版，并保留澄清清单；草案不得被当作定稿引用，待用户确认澄清项后再转正式定稿。
- 资料含多个需求模块时，必须先做需求模块拆分：在 `docs/prds/index.md` 输出需求模块清单和项目级需求脑图，再为每个有效模块单独生成 `docs/prds/<需求模块>.md`；严禁把多个需求模块的正式 PRD 正文混写进同一文件，也严禁把整个项目合并成一份大文档（拆分粒度见「拆分粒度（关键）」节）。
- 每个需求模块文档内部按「评估前置大纲 + 正式 PRD」两部分组织；跨模块关系用链接引用，不复制其它模块的正文。
- 「评估前置大纲 + 正式 PRD 草案」是单个需求模块文档内部的结构，不是把所有模块合成一篇的理由；澄清未闭环时每个模块文档各自标注草案/待确认版。
- 新增、合并、拆分需求模块，或调整业务流程、字段口径、验收标准、权限/状态机/数据一致性规则时，属于 L2，必须先完成澄清门禁并输出《需求拆分与口径报告》，等待开发者确认后才能定稿。
- 仅在既有需求模块内补充已确认字段、示例或变更记录时，属于 L0，可直接更新，并在交付中说明分级判定依据。
- 更新或新增文档后，同步更新 `docs/prds/index.md` 和 `docs/map.md`；`docs/map.md` 必须维护需求模块到 PRD/API/组件/测试文档的导航关系。

## 内容方法论（产物质量约束）

写正式 PRD 各章节时，按以下方法论提升内容质量；每条事实的来源都先经 `knowledge-search` 命中 `airules.knowledge.json` 登记来源后引用，命中不到一律标 `MISSING`，禁止凭产品常识或代码反推业务事实。

- 问题陈述（背景节强化）：先框定「用户细分 + 痛点 + 业务影响 + 为何现在做」，避免泛指「所有用户」；用户细分要具体到角色/场景（如「完成结算的移动端买家」）。痛点严重度/频率须有证据来源（用户研究、工单、行为数据），无证据标 `MISSING`，不得臆断。
- 成功指标（目标节强化）：目标必须可度量——每个指标给「当前基线 + 目标值 + 度量口径」，并与所解决的问题直接挂钩。基线或目标值缺失时标 `MISSING`，禁止编造数字。
- 用户故事（可选，按需求拆 backlog 时用）：用「作为<角色>，我想要<操作>，以便<收益>」格式，收益子句必填（解释为何重要、用于排优先级）；每条故事按 INVEST 自检（独立/可协商/有价值/可估算/小/可测试）。故事必须可追溯到本 PRD 已确认需求，不得新造需求。
- 验收标准（验收标准节强化）：用 Given/When/Then 可验证格式写（前置/操作/预期），每条可判定通过与否；只写可观测结果，禁止写实现细节（具体函数名、内部状态）。覆盖正常流 + 边界 + 错误态三类，缺失分类标 `MISSING`。
- 优先级（多需求模块/多功能并列时可选）：用 RICE / ICE / MoSCoW 等框架排序，框架按数据可得性筛选（RICE 需定量 reach/impact/effort，MoSCoW 用于二元承诺决策）。输入数据缺失时只产出「估算脚手架 + 标 `MISSING`」，绝不编造评分；多框架结论分歧处是最有价值的待澄清信号，须显式列出。

## 评估前置可视化

正式 PRD 定稿前，必须先产出「评估前置大纲」：用大纲级图让业务、产品、技术、测试快速理解需求全貌，在评估阶段提前暴露 TBD、断点和口径冲突，再写正式 PRD。

- 时序：每个需求模块文档内，图放第一部分，正式 PRD 放第二部分。
- 图必须用 Mermaid 代码块（` ```mermaid `），可在语雀、GitHub、VSCode 直接渲染，可进 git、AI 易生成、改动零成本；不得用截图或二进制图替代结构图。
- 选图由内容特征驱动，不是每种都画，避免噪音：
  - 需求脑图（`mindmap`）：必出，呈现业务模块树与子能力。
  - 业务流程泳道图（`sequenceDiagram`）：跨系统或跨角色的核心流程必出。
  - 状态图（`stateDiagram-v2`）：存在状态机（如单据状态、属性切换）时出。
  - 实体关系图（`erDiagram`）：核心实体 ≥ 3 且有明确关系时出。
  - 系统架构数据流图（`flowchart`）：涉及多系统集成、MQ、外部接口时出。
- 画图时把无法确认的节点、流程或字段显式标 `MISSING` 或用虚线/`TBD` 标注；画图过程发现的待确认项必须汇总进「评估提示」，再带入正式 PRD 的「风险与待确认」。
- 图是评估材料，不是定稿依据；用户基于图评估确认后，才写正式 PRD 对应章节。

### 渲染预览（可选）

需要把 Mermaid 渲染成图片供非技术干系人预览时，用项目已装的 `@mermaid-js/mermaid-cli`：

```bash
# 首次安装（puppeteer 自带 Chromium 下载失败时跳过，复用系统浏览器）
PUPPETEER_SKIP_DOWNLOAD=true npm install -D @mermaid-js/mermaid-cli
# 渲染：把 md 中每个 mermaid 块输出为 PNG
npx mmdc -i <文档>.md -o <输出>.png -p .mermaid-puppeteer.json -b white -s 2
```

- `.mermaid-puppeteer.json` 指向本机 Chrome/Edge 可执行路径，属机器相关配置，不入库（已在 `.gitignore`）。
- 渲染产物是本地预览物，默认不提交；命令失败时报告 `MISSING render`，不得伪造成已渲染。

## 文档结构

完整 PRD 分两部分：第一部分「评估前置大纲」承载图，第二部分是正式 PRD。

```md
# <需求模块>需求文档

## 第一部分：评估前置大纲

### 需求脑图

​```mermaid
mindmap
  root((<需求模块>))
    模块A
    模块B
​```

### 核心流程泳道图

​```mermaid
sequenceDiagram
    ...
​```

### 评估提示（画图暴露的待确认项）

- MISSING：缺失或待确认事实（示例占位，按真实情况替换）

## 第二部分：正式 PRD

### 背景

（含问题陈述：用户细分 / 痛点 + 证据来源 / 业务影响 / 为何现在做；无证据项标 MISSING）

### 目标

（含成功指标：每项给 指标 / 当前基线 / 目标值 / 度量口径；缺失标 MISSING）

### 范围

#### 包含

#### 不包含

### 用户与角色

### 业务流程

### 字段口径

| 字段 | 含义 | 来源 | 规则 |
|---|---|---|---|

### 状态与规则

### 验收标准

（用 Given/When/Then 写，覆盖正常流/边界/错误态；只写可观测结果，不写实现细节）

| 编号 | Given（前置） | When（操作） | Then（预期，可观测） | 分类 |
|---|---|---|---|---|

### 风险与待确认

### 变更记录
```

## 示例

以下内容是示例模板，仅供参考，不得作为真实业务事实自动应用。

```md
# 采购订单需求文档

## 背景

采购团队需要统一查看采购订单的创建、审批、入库与关闭状态。

## 目标

- 支持按供应商、订单状态、创建时间检索采购订单。
- 支持进入订单详情页查看明细、审批记录和入库记录。

## 字段口径

| 字段 | 含义 | 来源 | 规则 |
|---|---|---|---|
| 订单状态 | 采购订单当前生命周期 | 后端订单状态字段 | `draft` 草稿，`approved` 已审批，`closed` 已关闭 |

## 验收标准

- 输入供应商名称后，列表只展示匹配供应商的采购订单。
- 订单进入 `closed` 后，不允许继续发起审批。

## 风险与待确认

- MISSING：是否支持跨组织查看采购订单。
```
