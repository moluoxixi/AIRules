## 优化动作

### A. 优化 `issue/自我进化.md`（文档本身）

1. **去重**：把 vendor 红线 / 候选隔离 / scope / enforcement 边界各自收敛到唯一权威小节，其余处改为指针引用，不重述全文。
2. **新增「已约束 vs 待强制」对照小节**：把每条 P0/P1 标注当前状态——`prose 已约束、缺 fixture` / `prose 缺、需补写` / `设计缺、需新增`——让路线图精确指向真正缺口。
3. **补受众边界一句**：在 scope 小节声明：第一类全局 skill 的「写根 skills/ + 登记 constants/skills.ts」机制仅 AIRules 仓库内适用；分发到用户项目时，全局可复用洞见是「上游贡献候选」，不在用户仓库内写「全局」资产。
4. **引用小节**：保留全部引用；不改 ID。（仅在确有把握时给 2606.11435 标注「2026-06，较新」一类中性注记，避免读者误判。）
5. 不动文档主结论与分阶段路线骨架，只做密度与精确性优化。

### B. 执行第一阶段 prose 契约对齐（5 skill + baseline）

目标：让闭环所有参与者对 候选区 / 正式库 / scope / vendor / 全局-项目 memory 读取协议 说法一致。**只改 prose，不改安装行为、不改 schema、不加 fixture（那是 Phase 2-4）。**

1. **`rules/AGENTS.md`「记忆与持续进化闭环」小节**（权威源，被各宿主软链）：
   - 增「scope 判定」一句：候选转正前先判 scope（全局可分发 / 项目局部 / 项目 memory / 运行时全局 memory / 规则资产），并声明第一类的仓库内机制 vs 用户项目内「上游贡献候选」的受众边界。
   - 增「memory 读取与冲突优先级」一句：读取顺序 = 运行时全局 memory 轻索引 → 项目 `knowledge/memory/` → 命中深读；冲突优先级 = 代码/项目文档 > 项目 memory > 全局 memory。
   - 保持精简，每点 1–2 句，不破坏现有 8 条门禁与图。

2. **`skills/recall-memory/SKILL.md`**：在「流程」「读回纪律」补全局/项目两层读取协议 + 冲突优先级（项目 > 全局；代码/文档 > 任何 memory）。明确运行时全局 memory 由宿主承载、不在仓库内。

3. **`skills/remember/SKILL.md`**：在「写入边界」补 scope 判定一句——只写**项目** `knowledge/memory/`；用户偏好/跨项目习惯属运行时全局 memory，不写进项目仓库；保持既有 vendor 禁写。

4. **`skills/distill-candidates/SKILL.md`**：在「双路判据 / 写入边界」补 scope——候选默认项目局部；全局可复用者标注为「上游贡献候选」交人工决定，不在用户项目内自行升级为全局；保持既有 vendor 禁写与候选隔离。

5. **`skills/session-capture/SKILL.md`**：补一句与上述一致的 scope/vendor 口径对齐（已禁 vendor，补 scope 默认项目局部的措辞），保证五者说法一致。

6. **`skills/reflect/SKILL.md`**：其「资产层级」（repo-maintenance/project-init/...）与文档「5 类 scope」是两套维度；补一句说明二者关系（归因层级 ⊃ 写入 scope），避免读者混淆，不改其归因表。
