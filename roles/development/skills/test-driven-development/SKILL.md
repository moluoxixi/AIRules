# TDD（红绿重构）

核心逻辑的实现纪律：测试先行，给 agent 一个客观、不可粉饰的停止信号。没看着测试失败，就不知道它是否在测正确的东西。

## 触发条件

- 实现阶段、编写逻辑明确且边界可枚举的核心逻辑
- 验收用例清单已就绪，需要逐条落实为可运行测试
- 修 bug：先写一个能复现该 bug 的失败测试，再按红绿循环修复

## 不适合场景

- 集成 / UI / 端到端等红绿成本高的场景 → 改用事后测试 + 实际运行验证兜底（本项目豁免，不强制红绿先行）
- 纯探索性 spike（明确会丢弃）、生成代码、纯配置文件 → 不强制
- 测试用例的设计 → 由 `test-design` 承担

## 红绿重构循环

1. **红**：按一条验收用例写一个最小测试，运行并确认它**因正确的原因失败**——功能缺失，而不是测试写错、拼写错或导入报错。测试一上来就过，说明在测已有行为，要修测试。
2. **绿**：写最简代码让测试通过，不提前实现未被测试覆盖的功能（YAGNI）。只让当前测试转绿，并确认其它测试仍绿、输出干净无报错。
3. **重构**：在测试保持绿的前提下整理代码与测试——去重复、改命名、抽辅助函数，不新增行为。
4. 循环下一条用例。

铁律：没有先看到失败的测试，不写生产代码；不得写完代码后补一个"顺手就过"的测试。事后写的测试一上来就通过，证明不了任何东西——可能在测错对象、测实现而非行为、漏掉你当时没想到的边界。

## 红绿成本高时的兜底（本项目豁免）

集成、UI、端到端等场景红绿循环成本过高时，允许事后补测试，但必须：

- 实际运行测试并读取输出，确认它真的覆盖目标行为，而非空跑通过；
- 测试与代码成对交付，不得只交代码不交测试；
- 在交付汇报里说明该模块走的是事后测试兜底，而非红绿先行。

## 何时卡住

- 不知道怎么测 → 先写"期望中的 API"和断言，倒推实现。
- 测试太复杂 / 要 mock 一切 → 多半是设计耦合过重，先简化接口或引入依赖注入，而不是迁就测试。
- 测起来难 = 用起来难，这是设计在给信号，听它的。

## 输出边界

- 测试与代码成对产出；后端单测细则见 `unit-testing`，前端交互测试细则见 `interaction-testing`。
- 不得为了让测试通过而删断言、放宽断言或跳过用例。
- 红阶段必须真实运行并读取失败输出，不得假设测试会失败。
- 优先用真实代码，mock 仅在不可避免时使用——测 mock 不等于测代码。
