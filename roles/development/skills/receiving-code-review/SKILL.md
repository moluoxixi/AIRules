# 接收代码评审

收到代码评审意见后，先做技术核实再决定是否实现，不盲从、不表演式同意；评审有误就带技术理由 pushback。与 `requesting-code-review`（发起评审）配对使用。本 skill 由编排或用户按名调用，不在普通对话自动触发。

核心原则：实现前先核实，假设前先发问。技术正确优先于社交舒适。

## 触发条件

- 收到代码评审意见（来自用户或评审子代理），准备据此修改之前。
- 意见看起来不清晰、或技术上存疑时尤其适用。

## 不适合场景

- 还没有评审意见可处理。
- 纯走流程的格式/拼写批注，直接改即可，无需完整核实流程。

## 响应流程

收到评审意见时：

1. 读完整意见，先不反应。
2. 用自己的话复述要求（或直接发问）。
3. 对照代码库现实核实。
4. 评估：对**这个**代码库技术上成立吗？
5. 回应：技术性确认，或带理由的 pushback。
6. 实现：一次一项，逐项测试。

## 禁止的回应

不要写："你说得太对了""好主意""这就去实现"这类表演式同意，也不要在核实前就开干。
取而代之：复述技术要求 / 提澄清问题 / 有错就带技术理由反驳 / 或直接动手（行动胜于表态）。

接收正确意见时也不要写任何感谢或赞美，直接陈述改动：例如"已修复：[改了什么]""漏在 [位置]，已修"。代码本身证明你听进去了。

## 处理不清晰的意见

任一条目不清晰：停下，先就不清晰的条目澄清，不要先实现一部分。
原因：条目之间可能相关，部分理解会导致错误实现。
例：用户说"修 1-6"，你懂 1/2/3/6、不懂 4/5——正确做法是先说"1/2/3/6 已理解，4/5 需澄清后再动手"，而不是先做懂的、回头再问。

歧义才澄清；能靠读代码、文档补齐的事实先自己补，不要一遇模糊就升级阻断。

## 按来源处理

来自用户：可信，理解后即可实现；范围不清仍要问；不做表演式同意，直接动手或给技术确认。

来自外部评审者，实现前先核实：

1. 对**这个**代码库技术正确吗？
2. 会破坏既有功能吗？
3. 当前实现是否有其存在理由？
4. 在所有目标平台/版本上成立吗？
5. 评审者是否掌握完整上下文？

- 若意见看起来不对：带技术理由 pushback。
- 若难以核实：明说"没有 [X] 我无法核实，要我 [调查/问/继续]?"
- 若与用户先前的决策冲突：先停下与用户讨论。

外部反馈是"待评估的建议"，不是"必须执行的命令"。

## YAGNI 核查

评审者建议"做完整/做规范"时，先 grep 代码库看是否真有使用：未使用就提议移除（YAGNI），在用才规范实现。

## 实现顺序

多条意见：先澄清不清晰项，再按"阻塞项（破坏、安全）→ 简单修复（拼写、导入）→ 复杂修复（重构、逻辑）"实现，逐项单独测试，确认无回归。

## 何时 pushback

意见会破坏既有功能、评审者缺上下文、违反 YAGNI、对该技术栈不正确、存在遗留/兼容理由、与既定架构决策冲突时，应 pushback。
方式：用技术理由而非防御姿态，提具体问题，引用可运行的测试/代码，架构层面则拉上用户。
若 pushback 后发现自己错了：事实性陈述更正即可（"核实了 [X]，确实 [Y]，现在实现"），不长篇道歉、不为先前 pushback 辩护。

## 输出边界

- 本 skill 决定"是否/如何采纳评审意见"，不负责发起评审（见 `requesting-code-review`），也不替代评审子代理与编码实例的独立性。
- 评审结论必须基于实际代码与可运行证据核实；状态只用 `PASS` / `FAIL` / `MISSING` / `NOT RUN` / `N/A`。
- 采纳的意见逐条实现并测试后才算闭环；未核实就照搬、或把存疑当通过，均不允许。
