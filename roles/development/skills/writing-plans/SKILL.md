# 实现计划

把需求事实源拆成可执行、可追溯的实现任务，每项任务都能回溯到需求与对外契约。跨前后端适用，按任务实际触及的栈填写对应字段。计划面向"对本代码库零上下文的实现者"撰写：写清要动哪些文件、各文件职责、如何验证。

## 触发条件

- 需求事实源已就绪、即将进入实现编码
- 需要把需求拆解为可追溯到验收标准的实现任务

## 不适合场景

- 需求仍为草案或关键事实 `MISSING` → 先回到需求分析
- 单行/单点小改且无契约影响 → 主代理直接实现，不需要正式计划
- 测试用例设计 → 由 `test-design` 承担，本 skill 只引用其产出

## 任务切分与质量要求

- **文件结构先行**：定义任务前，先列出将创建/修改的文件及各自单一职责，把分解决策锁定下来；改动应内聚，变更同进退的文件放在一起。
- **每个任务落档为独立 md（强制，跨栈）**：无论前后端，**每个 task 落成一个独立的 md 文件**，一任务一文件；切分单位是**变更单元**——前端变更单元可以是页面、共享组件/hook/状态模块/请求封装/样式系统；后端变更单元是内聚交付单元（一个能力 / 一组端点 / 一个领域模块，即"自带测试闭环、值得一次独立评审"的最小交付）。**不合规判定**：多个可独立实现/测试/评审的任务被混进单一 plan 文件才视为不合规；需求只有一个任务时，单文件完全合规。
- **前端变更单元拆分（强制）**：前端变更单元可以是页面、共享组件/hook/状态模块/请求封装/样式系统，一个变更单元一个 task md 文件；跨页面共享的组件/逻辑单独成 task 文件，不塞进某个页面任务里。
- **任务足够小**：一个任务是"自带测试闭环、值得一次独立评审"的最小单元；把配置、脚手架、文档步骤折叠进它服务的任务里，只在评审者能独立通过/驳回相邻任务时才切分。
- **步骤清晰**：每个任务以一个可独立验证的交付物结束；步骤描述要具体到可执行，避免 "TBD/TODO/适当处理/类似上一个" 等占位写法。
- **类型一致**：后续任务引用的类型、签名、属性名必须与前序任务定义一致。

## 前后端计划参考规范

当任务触及前端（页面/组件）或后端（接口/服务/数据）时，必须加载对应参考文件补充专项字段；两者均触及时均加载：

- **前端变更单元**：加载 `writing-plans/references/frontend-plan.md`——变更单元为**页面**时，全部专项字段必填（布局图、接口契约核对表、字段级配置、交互状态流）；变更单元为**组件/hook/状态模块/请求封装/样式系统**时，路由与布局图标 `N/A`，但必须额外填写被哪些页面或能力消费、props/事件/状态/样式契约是否变化；**禁止 mock、猜字段、前端兜底来伪装接口已满足**。
- **后端任务**：加载 `writing-plans/references/backend-plan.md`——接口契约、数据模型、权限规则、事务边界、错误码、幂等/兼容性；**禁止只写"新增接口"或"实现服务逻辑"，契约内容不得留白**。

参考文件提供字段规范，不重复主文件的通用字段；专项必填字段以参考文件为准。

## 计划必须包含的可追溯字段

每个实现任务必须写明以下字段——依据任务触及的栈，该栈标注的字段为必填，未标注栈的字段可省略：

- **需求来源**：对应需求文档（`.airules/requirements/<feature>.md`）中的需求 ID；若走 spec 路径则写 change-id + 条目编号
- **接口设计**：新增/修改的接口签名、入参出参、错误约定（后端）
- **调用接口**：调用了哪些后端/外部接口（前端）
- **数据模型**：涉及的实体、字段、存储结构（后端）
- **代码分层与职责**：改动落在哪一层、各层职责（后端）
- **事务与一致性**：事务边界、并发、幂等约束（后端，涉及时）
- **字段级配置**：本页面涉及的查询字段、列表列、详情表单字段，逐字段列出（前端，页面任务必填）；需按标准表格结构产出：
  - **查询字段表**：| 字段名 | 标签 | 组件 | 组件来源 | 必填 | 默认值 | 数据源/枚举 | 交互类型 |
  - **列表列表**：| 字段名 | 标签 | 宽度 | 格式化 | 排序 |
  - **表单字段表**：| 字段名 | 标签 | 组件 | 组件来源 | 必填 | 校验规则 | 交互类型 |
- **页面布局**：区域划分（如筛选区/列表区/操作区）、关键交互区、路由结构，粒度到区域/层级即可（前端，页面任务必填）
- **组件复用分析**：跨模块可复用的既有组件（复用哪个）与需额外封装的新组件（为何封装、供哪些页面共用），分两类列出（前端）；需额外封装的新组件，必须在计划中输出最小 API 草案（Props 列表 + 关键 Emits），标注供哪些页面共用；触发 RULES_frontend.md §3 评审条件的组件必须附《前端实现与测试设计报告》
- **类型（使用/封装）**：涉及的类型定义与来源（前端）
- **性能边界**：可度量的性能约束，如首屏/接口耗时阈值、列表虚拟化触发行数、查询无 N+1、分页必选、并发/超时上限（跨栈，涉及时必填，必须写成可判定阈值而非"要快"）；前端页面任务中「性能边界」不得为空或仅写"无"——至少包含以下可判定项之一：
  - 列表虚拟化阈值（如 >100 行启用虚拟滚动）
  - 首屏加载预期（如 FCP < 2s）
  - 接口超时阈值（如单接口 < 5s，超时显示 toast）
  - 分页策略（必选分页 / pageSize 上限）
  - 外部 API 调用降级（如高德接口超时后提示手动输入）
- **契约来源**：依据的 API/组件/数据契约出处；项目文档契约可引用 `.airules/knowledge/` 下的文件路径

## 自检

计划写完后，以新视角对照需求事实源核对：

1. **需求覆盖**：逐条扫需求/验收标准，能否指到对应任务？列出缺口并补任务。
2. **占位扫描**：搜 "TBD/TODO/待补/适当处理" 等红旗，逐个补实。
3. **产物形态可判定性**：布局、性能边界等形态字段是否写成可核对的条件（区域/层级、量化阈值）？含糊表述（"要好看/要快"）降级为噪声，就地改成可判定条件或删除。
4. **类型一致**：后续任务用到的签名、属性名是否与前序定义吻合。
5. **接口字段审计**（前端任务必做）：逐字段核对——
   - 显示字段：接口响应是否包含？标 `COVERED` / `MISSING` / `FRONTEND_ONLY`（纯前端计算）
   - 提交字段：接口请求体是否接收？标 `COVERED` / `MISSING`
   - `MISSING` 字段须判定阻断级别：`BLOCKING`（阻断实现）或 `MOCKABLE`（可先 mock 推进）

发现问题就地修复，无需重审。

## 两路任务落点

计划完成后，任务 Markdown 落盘位置按路径决定：

- **普通编码路径**：每个 task 独立落 `.airules/tasks/<task-name>.md`，一任务一文件。
- **规格契约路径（spec-workflow）**：任务统一落 `.airules/tasks/<task-name>.md`，在"需求来源 / 契约来源"字段写明 `change-id` 做反向关联；不另建 `.airules/changes/<change-id>/tasks.md` 索引。
- 不论哪条路径，**多个可独立实现/验证/评审的任务不得塞进单一文件**；单任务需求只有一个 md 文件完全合规，不强制多文件。

## 单任务 Markdown 最小内容（强制模板）

每个落档的任务 Markdown 必须包含以下字段（无关字段可标 `N/A` 并注明原因，但不得省略字段本身）：

```markdown
# <任务标题>

## 目标
<一句话说明本任务交付什么，可独立实现/测试/评审>

## 需求来源 / 契约来源
<需求文档路径（`.airules/requirements/<feature>.md` 中的需求 ID），或 spec-workflow change-id + 条目编号>

## 涉及文件与职责
| 文件路径 | 职责说明 |
|---|---|
| `<path>` | <职责> |

## 字段交互关系（前端页面任务必填）
| 触发字段 | 事件 | 目标字段 | 交互类型 | 逻辑说明 | 来源 |
|---|---|---|---|---|---|

> 6 种标准类型：级联刷新、条件显隐、值联动计算、校验依赖、互斥/禁用、选择回填。
> 无联动时写「无」，不得省略此章节。

## N/A 判定

并非每个任务都必须有 code 或 test：

- **可标 `N/A` 的情形**：纯文档编写、纯规则文本修改、纯格式调整、纯调研、纯配置声明（无行为变更），可将 `code` 或 `test` 标为 `N/A`。
- **标 `N/A` 的要求**：必须在"N/A 说明"字段写明原因与替代验证方式，例如 diff 结构检查、脚本快照校验、文档一致性对比、规则 lint 等客观信号。
- **不得用 `N/A` 回避的情形**：有行为变更（接口、状态机、用户可观察功能）、有数据逻辑变更、有接口新增/修改——这些必须有测试，不得以"内容是文字"为由标 `N/A`。

## 输出边界

- 只产出实现计划与任务拆解，不编写生产代码。
- 范围必须冻结：计划定稿后进入实现，范围变更需回到需求分析。
- 计划与验收用例清单（`test-design` 产出）共同作为实现阶段的输入。
- 计划定稿后归档按"两路任务落点"落盘，作为可追溯事实源留存。
- **产物形态（强制，跨栈）**：每个 task 落成一个独立 md 文件（`<变更单元名>.md`；前端可以是 `<页面名>.md` / `<组件名>.md` / `<hook名>.md` 等，后端是 `<能力/模块名>.md`），内容满足"单任务 Markdown 最小内容"模板；**不合规判定**：多个可独立实现/测试/评审的任务被合并进单一文件才视为不合规，单任务需求产出单文件完全合规。
- 字段含义以本 skill 为准；示例任务仅供格式参考，不得当作真实需求落地。
