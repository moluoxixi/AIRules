# 执行实现计划

在隔离上下文里按已写好的实现计划逐任务执行，带 review 检查点，遇阻塞上报。计划来源是 `writing-plans` 的产出。本 skill 由编排或用户按名调用，不在普通对话自动触发。

## 触发条件

- 已有一份成形的实现计划（通常由 `writing-plans` 产出），需要在独立会话/上下文中落地执行。
- 任务之间相对独立、计划已把步骤拆成可逐条执行的小步。
- 如果宿主支持子代理且任务适合"每任务派新实现者 + 任务级评审"，优先用 `subagent-driven-development`；本 skill 适用于单会话顺序执行。

## 不适合场景

- 还没有计划：先用 `writing-plans` 产出计划，不要边想边写。
- 计划存在大量未决项或歧义：歧义才澄清，回到计划阶段补齐，不在执行中靠猜推进。
- 紧耦合、需要持续全局视野的改动：顺序执行即可，不必强行套用检查点流程。

## 执行流程

### 第 1 步：加载并审阅计划

1. 读取计划文件。
2. 批判性审阅，列出对计划的疑问或顾虑。
3. 有顾虑：执行前先与用户对齐（歧义才澄清；L0/L1 范围内的小调整可直接执行，不得一遇模糊就升级阻断）。
4. 无顾虑：为计划条目建任务清单，开始执行。

### 第 2 步：逐任务执行

对每个任务：

1. 标记进行中。
2. 严格按计划步骤执行（计划已是小步）。
3. 按计划指定运行验证。
4. 标记完成。

实现性改动后，按本仓门禁在编码后、测试验证前走 `consistency-reviewer` 核对最终 diff。

### 第 3 步：收尾

所有任务完成并验证通过后，进入开发分支收尾（见 `finishing-a-development-branch`）：验证测试 → 给出 merge/PR/保留/丢弃选项 → 执行所选项 → 清理。

## 何时停下求助

遇到以下情况立即停止执行、向用户求助，不要靠猜推进：

- 撞到阻塞（缺依赖、测试失败、指令不清）。
- 计划存在导致无法启动的关键缺口。
- 不理解某条指令。
- 验证反复失败（同一思路失败两次以上，先诊断根因再换思路，不做小修小补式循环）。

## 何时回到前面的步骤

回到第 1 步（审阅）当：

- 用户基于你的反馈更新了计划。
- 根本思路需要重新考虑。

不要硬闯阻塞——停下来对齐。

## 记住

- 先批判性审阅计划。
- 严格按计划步骤执行，不跳验证。
- 计划指明引用某 skill 时照做。
- 被阻塞就停，不要猜。
- 未经用户明确同意，不在 main/master 上直接开始实现。

## 输出边界

- 本 skill 负责"按计划执行 + 检查点"，不负责重写计划：发现计划需改，回到计划阶段由用户确认。
- 验证状态只用 `PASS` / `FAIL` / `MISSING` / `NOT RUN` / `N/A`，不得把失败、缺失或未运行写成通过。
- 收尾交付收口五项：变更范围/风险摘要、改动内容、验证、未执行项及原因、风险/MISSING/待确认项（没有则显式写"无"）。

## 配套 skill

- `using-git-worktrees`：确保隔离工作区（新建或确认已存在）。
- `writing-plans`：产出本 skill 执行的计划。
- `subagent-driven-development`：宿主支持子代理时的同会话替代编排。
- `finishing-a-development-branch`：所有任务完成后的收尾。
