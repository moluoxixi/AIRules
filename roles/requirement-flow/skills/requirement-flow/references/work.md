# 工作记录：恢复问题，而不是回放聊天

在跨会话、复杂变更、业务取舍或多人交接时读取。优先使用项目已有 issue、spec、PR 或任务文档；需要仓库内记录而没有约定时用 `docs/changes/<有意义的名称>.md`。从项目文档入口或对应业务页给出链接，记录再链接回业务现状。不要只依赖聊天、个人记忆服务或不可共享的绝对路径。

把业务入口写成普通 Markdown 链接，例如 `[库存申请](../business/inventory.md)`；[网页阅读器](reader.md)将既有记录展示为任务卡，并提供业务到任务及任务到业务的跳转。任务卡的文字、进度与验证边界仍来自这份记录，阅读器不另存状态。

## 记录到什么程度

只保留下一位无法低成本从代码恢复的信息。小任务可由已有 PR/提交说明承担；需要文档时下面内容可放在同一页，按需取舍：

```markdown
# 保存后回读库存数量

当前进度：已实现；本机回归通过；UAT 未测。
业务入口：[库存申请](../business/inventory.md)

## 目标与边界
现状及来源：……
本次要改变：……
仍须成立的规则、已承诺场景：……
不在本次范围/已延期：……（实际决定依据）

## 决定、影响和实现
关键决定、理由、来源/决定人，尚待回答的问题：……
受影响的业务规则、状态、接口、调用方和数据：……
实际修改与位置：……（与目标分开）

## 验证
场景 | 预期 | 实际结果与证据 | 条件与限制
……

## 继续
当前工作区/分支与未提交内容：……
仍缺的场景、阻塞原因与下一步命令/操作：……
```

预期在实现前可以修改，但保留重要范围取舍及依据；发现尚未确认的规则时先写假设或待决定，避免用代码行为冒充产品决定。承诺场景被取消/延期时注明谁在何处作出决定、原因与影响；它不计入验证通过。只做了部分实现或检查时保留相应状态，不用“已完成”笼统覆盖。

## 换会话或换人

接手者先读业务入口与这份记录，再对照实际检出、diff 和相关来源；历史“通过”要核对代码内容、预期、环境与数据仍适用。原证据记录照常保留，失效项标明需要复验。已经回答的问题按决定更新，避免把旧疑问当当前阻塞。

交接必须让人直接开始下一步：给出真实入口、输入条件、未覆盖范围与具体待办；缺权限/数据时说明应由谁提供。不要把“继续检查”当作下一步，也无需逐条保存每次工具调用。

## 可选的分工与显式步骤

单执行者直接推进。复杂依赖或实际模型表现需要更明确的提示时，可以在本记录中列少量有完成条件的步骤，并随发现调整；这不引入第二种数据格式或编排引擎。仅在已观察到帮助时使用，不能靠模型名称判断必须走哪条流程。

能独立交付且不会互相覆盖的部分可以并行。给执行者交接目标、授权、业务/接口约束、可写范围、输入版本、预期产出及验证方式。共享文件或状态由一个执行者整合。改动正在使用的输入前先协调停止/同步；文档状态变更不能取消真实运行进程。返回实际改动、证据和未解决问题，整合者复核最终组合后的结果。

独立审查用于高影响、难以自证或持续诊断无进展的部分。审查者看原始需求、实际 diff 和证据；由同一执行者更换署名不会产生独立性。没有可用审查者时保留局限，继续其他可做工作，不制造领取、身份或固定失败次数门槛。
