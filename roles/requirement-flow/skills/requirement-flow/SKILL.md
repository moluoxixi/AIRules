# 需求编排

首次启用项目，从 AIRules 分发的本 skill 运行 `python3 <技能目录>/flow.py --project <项目目录> init`。之后从项目根目录运行 `python3 .agents/skills/requirement-flow/flow.py` 加下列子命令。先用 `list` 找已有需求。新需求用 `new <ID> --request '原话'`，仅调研或出方案时加 `--outcome research`。项目对分支、权限、联调和发布的约定始终适用。

## 选择工作方法

用 `task <ID> next --actor <执行者>` 查看待办、依赖与当前版次，用 `task <ID> context <故事ID>` 核对选定功能。返回动作的 `skill` 指明适用方法；结合用户授权和已有材料打开对应专项。若返回 `review_skill`，先复核未覆盖的验收或交付问题。计划中的动作可用 `skill` 指定更合适的方法。

| 什么时候用 | 打开哪个 skill | 需要拿回什么 |
| --- | --- | --- |
| 对象、目标、状态边界或验收例子还不清楚 | [需求分析](../flow-requirements/SKILL.md) | 故事、场景、待决定事项及受影响范围 |
| 画面或行为依赖接口，字段含义、读写、分页或回显需要核对 | [接口契约](../flow-contracts/SKILL.md) | 操作到字段及结果的对应关系、来源、缺口 |
| 一个可执行的开发动作已经有范围、输入和完成条件 | [功能开发](../flow-implement/SKILL.md) | 实际代码和该功能的关键处理路径 |
| 行为需要证明、修复需要回归，或验收依据发生变化 | [功能验证](../flow-verify/SKILL.md) | 对应到场景的运行结果、观察记录和失败返工项 |
| 用户要求检查，或跨层改动、关键路径、已有证据之间需要独立复核 | [审查](../flow-review/SKILL.md) | 有位置和依据的发现、影响、处理结论 |

这些方法可以跳过、重复或组合。已确认字段可直接开发；需求审查可止于问题清单；一个故事等待业务决定时，可并行推进其他已就绪的故事。多执行者各用稳定名称，写同一需求时以最新 `revision` 为准。专项 skill 指导实际工作，每次领取仍由本入口依据动作与授权决定。

## 写回同一份需求记录

1. 对照动作范围与完成条件后，用 `task <ID> claim --actor <执行者> --rev <版次>` 领取或接手，可加 `--story <故事ID>` 聚焦同一功能。
2. 补计划、故事、契约或依赖时用 `task <ID> plan <补丁.json> --why '依据' --actor <执行者> --rev <版次>`。业务选项由实际决定人确认后再用 `decision` 记入。遇到版次冲突，重读上下文和本次差异再写入。
3. 调研和开发的 `finish` 写实际产出及可复核位置。验证用 `verify-run` 执行检查，或用 `verify-observe` 登记真实观察，并核对场景覆盖。取得合格证据后用同一执行者和新版次 `finish` 验证动作；失败按受影响分支返工。命令、证据类型、场景 ID 和补丁字段见[记录格式](references/model.md)。
4. 当前委托完成后，交付相关故事、已验证结果和待决问题。用 `task <ID> serve` 打开本机图页，`task <ID> --check` 检查图页和模型一致性。已结束的需求可用 `archive <ID>` 归档。有证据且可重复使用的做法可写入该需求的 `lessons`。
