# 需求编排

首次启用从分发目录运行 `python3 <技能目录>/flow.py --project <项目目录> init`。升级前关闭需求图服务，从新版目录执行 `upgrade` 后可用原端口重启。日常从项目根运行 `python3 .agents/skills/requirement-flow/flow.py`。执行前读 `AGENTS.md`，按 `.requirements/rules/index.md` 查本次业务规则。分支、联调、权限和发布仍按项目约定。

## 默认轻量交付

先用 `list` 找已有需求；用 `context` 读故事和 `workflow`，沿用其模式。范围明确的新交付用 `new <ID> --light --request '原话'`；仅调研用 `--outcome research`。需要恢复历史材料时按 `.requirements/history/index.md` 查标题，用 `context` 查看归档记录。

1. **建卡。** 用 `task <ID> cards` 写能独立验收的故事、来源和有稳定 ID 的场景。向负责人展示功能清单和待决定的分支。验法容易跑错、要交接或指定环境时登记 `checks`；[字段与示例](references/lightweight.md#1-登记可验收的故事)。
2. **实现并采证。** 用 `implement <故事ID>` 登记实际产出和代码依据。立即读回执 `delivery.check_suggestions`：对有权限、环境和明确方法的缺口继续处理。轻量验证直接用场景 ID 调用 `verify-run` 或 `verify-observe`，成功回执自动用于该场景，无需领取或再 `finish`。开始前核对命令、实际环境及业务断言；按[采证说明](references/lightweight.md#2-按故事登记实现按场景采证)执行。
3. **当前交付检查。** 宣布需求验收前，运行 `task <ID> delivery-check` 核对整项本期范围。能补的继续补，只复验失效或欠缺的场景；缺输入时报告实现状态、具体缺口和接手方。只在当前结果 `ready_to_deliver: true` 时报告验收完成；此后改码、改范围或换目标环境，再核对后再报告。

## 按需启用动作编排

范围争议、待确认契约、跨人分工或独立复核才增加对应动作；旧需求继续按原动作记录。并行前核对共享文件/接口和上下游约定。独立复核交接实际候选、断言和回执，不用子代理的完成描述替代证据。

用 `task <ID> next --actor <执行者>` 查看待办、依赖与当前版次，用 `task <ID> context <故事ID>` 核对选定功能。返回动作的 `skill` 指明适用方法；结合用户授权和已有材料打开对应专项。若返回 `review_skill`，先复核未覆盖的验收或交付问题。计划中的动作可用 `skill` 指定更合适的方法。

| 什么时候用 | 打开哪个 skill | 需要拿回什么 |
| --- | --- | --- |
| 对象、目标、状态边界或验收例子还不清楚 | [需求分析](../flow-requirements/SKILL.md) | 故事、场景、待决定事项及受影响范围 |
| 画面或行为依赖接口，字段含义、读写、分页或回显需要核对 | [接口契约](../flow-contracts/SKILL.md) | 操作到字段及结果的对应关系、来源、缺口 |
| 一个可执行的开发动作已经有范围、输入和完成条件 | [功能开发](../flow-implement/SKILL.md) | 实际代码和该功能的关键处理路径 |
| 行为需要证明、修复需要回归，或验收依据发生变化 | [功能验证](../flow-verify/SKILL.md) | 对应到场景的运行结果、观察记录和失败返工项 |
| 用户要求检查，或跨层改动、关键路径、已有证据之间需要独立复核 | [审查](../flow-review/SKILL.md) | 有位置和依据的发现、影响、处理结论 |

专项可跳过、重复或组合。仅审查可止于问题清单；一张卡等业务决定时继续其他就绪工作。分派前查完整故事和 `covers`，因为故事筛选不缩减共享动作的范围。

## 子代理交接

同一活动需求同一时段指定一个模型写入工作区，代码可按项目流程在不同 worktree 分工。换写入工作区前同步需求、证据并核对版次；共享签名密钥不提供跨树实时领取互斥。每位实际执行者使用稳定署名；独立审查由不同的真实执行者承担。

派发时交接需求、动作、故事和场景 ID、执行者、当前版次、授权范围、代码执行根、模型写入根、完整动作包及必要项目规则。失败诊断另交接可复现命令、数据和必要历史输入；私有材料按授权单独交接，公共摘要不要求公开原始日志。材料不足时返回待补事项。

修改进行中动作的输入前，先通知原执行者停止并确认不再产生副作用；输入失效只撤销旧结果的有效性，不会终止真实进程。看到 `previous_execution` 时确认原执行已停止，再复核或领取。回包写完成、失败、取消或权限阻塞，产出位置、场景和回执 ID、最新版次及未覆盖项。版次或采集冲突须核对实际执行结果，再重读重采；拒收的结果不算已登记证据。

创建需求时先看原话命中的 `related_lessons`。拆出故事后，在 `next`、`context` 或 `claim` 里查看该故事的推荐和 `adopted_lessons`。打开原场景和回执，判断做法是否适用。决定采用时，用 `lesson-adopt` 把来源版本、目标故事和本次理由写回需求，再落实到实现或断言。已有采用记录可用于交接；退役经验只供追溯。命令见[经验的采用和退役](references/model.md#可在项目内复用的经验)。跨层改动、重复失败或经验待审时，把原话、动作与场景 ID、回执和待判定的问题交给独立审查者。有子代理能力时可分派独立工作，由总入口汇总证据；单执行者可继续其他就绪工作，把独立审查留在队列中。

## 动作编排的写回

1. 用 `task <ID> claim --actor <执行者> --rev <版次>` 领取动作或继续自己的动作。换班时先用 `next` 核对持有人，再用 `task <ID> handoff <动作ID> --from <原执行者> --actor <接手人> --why '交接原因' --rev <版次>` 登记交接。
2. 补计划、故事、契约或依赖时用 `task <ID> plan <补丁.json> --why '依据' --actor <执行者> --rev <版次>`。业务选项由实际决定人确认后再用 `decision` 记入。遇到版次冲突，重读上下文和本次差异再写入。
3. 调研和开发的 `finish` 写实际产出及可复核位置。验证用 `verify-run` 执行检查，或用 `verify-observe` 登记真实观察，并核对场景覆盖。取得合格证据后用同一执行者和新版次 `finish` 验证动作；失败按受影响分支返工。命令、证据类型、场景 ID 和补丁字段见[记录格式](references/model.md)。
4. 失败时读 `verification_followups`，定位原因、按依赖返工并重测。同一场景、输入、命令和环境连续失败时，`claim` 安排 `flow-review` 诊断动作；交给实际独立的执行者领取，核对失败回执，并用 `finish` 记录结论和依据。其他就绪动作继续推进。诊断完成后再修复并采集新证据。有复用价值的结论用 `lesson-propose` 绑定原始回执，`lesson_reviews` 中的待审项交给另一位实际审查者。
5. 读 `finish` 返回的复验建议，再按前述 `delivery-check` 核对本期范围。用 `serve` 查看验收和依据，用 `archive <ID>` 归档已结束的需求。
