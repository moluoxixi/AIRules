# 需求推进

让工作量由要解决的问题决定。自行选择分析、实现和验证方法，在已有授权内持续推进；项目规则和用户指定的交付物仍适用。本技能无需项目初始化或服务。

## 从目标和当前事实开始

用户想了解业务时，从一个真实操作讲起，沿角色、对象和状态说明规则与例外，给出读者可以核对的来源。只问业务可以直接回答，需要给后来者留下入口时维护项目里的[业务说明](references/business.md)。

开发时定位用户预期的结果和相关实现。续做时从项目入口找到已有[工作记录](references/work.md)，对照实际检出、未提交修改和证据，确认哪些结论还成立。

开始时做一个简短影响判断：涉及谁、改变什么可见行为、哪些约束必须继续成立、怎样观察结果。判断可以在思考中完成。局部且明确的修改直接实现并做相关检查，无需先建卡、写计划或生成文档；“重构”“依赖升级”等名称也不能代替影响判断。

## 随发现调整

把新发现及时反映到实现与验法中，尤其是：

- **状态与业务规则**：操作前后状态、权限与数据归属、重复/并发操作、失败后的恢复及已有例外。
- **跨边界行为**：共享调用方、接口读写与回显、外部系统、迁移和不可逆影响。需求和接口都存在时，将用户操作、字段语义/类型/必填/枚举、请求、响应、页面结果逐项对照；缺口留在具体受影响分支。
- **预期或事实不清**：材料冲突、环境差异、断言只测到了表象、原有证据不再适用。

这些是扩大调查和验证范围的信号，不是必填清单。按需追到能说明影响的边界，用具体成功、拒绝、失败及恢复例子澄清关键规则。发现新约束后补充相关验法，再继续；不要让最初“很简单”的印象免除后续检查。

可逆的实现选择自行判断。涉及缺失的业务决定、收窄已承诺范围或现有授权不足时，只询问依赖该答案的部分，说明取舍和影响；其他工作继续。保存原承诺和实际决定依据，延期、撤出与通过分别表述。

有跨会话、多人协作、重大决定或难以从代码恢复的上下文时，用一份[工作记录](references/work.md)保留当前边界、依据和下一步。发现长期适用的业务规则时，更新项目原有[业务说明](references/business.md)中受影响的部分。已有文档能承载就复用，不建立平行账本。

## 用实际结果结束工作

选择能证明用户结果的验证，核对断言究竟观察了什么。成功提示不能证明持久化，mock 不能证明真实接口可用，命令退出 0 不能证明业务正确。需要保存运行证据、实测附件或复核旧结果时读[验证与证据](references/verification.md)。

交付前再次对照最终 diff 与用户目标：新发现的共享依赖和例外是否处理，相关约束是否仍成立，证据是否适用于当前代码、预期及环境。按影响补测；无关变化不强制重跑全部检查。重复失败却没有新信息时改变假设或诊断方法，需要第二视角时引入独立审查；由问题决定，不按固定失败次数停工。

只在已约定范围得到相应证据时称该范围已验证。实现完成、验证通过、部署生效分别报告；未测、失败、待决定或受阻项写明具体场景、原因和可执行下一步。调研/审查任务以问题、结论和来源收尾，不凭空增加开发或部署承诺。工具输出和任务记录都是证据的一部分，不能替代这个判断。

## 让下一位接得住

结束或中断前，更新已有记录中会误导接手者的内容。下一位应能从项目入口找到：业务现在如何运作、本次准备/已经改变什么、实际验证了什么、还差什么及下一步。小任务可由代码、提交/PR说明和简短交付说明满足；有持续上下文时保留[工作记录](references/work.md)，无需另写一份同义总结。

业务说明中的**现行规则**、变更记录中的**目标与决定**、验证记录中的**指定条件下的实测结果**各有依据。实现或本地验证成功不自动代表目标环境已生效；有确认来源和生效范围后，才更新相应现状。
