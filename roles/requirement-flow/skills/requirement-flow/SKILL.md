# 需求编排

首次启用从分发目录运行 `python3 <技能目录>/flow.py --project <项目目录> init`。升级前关闭需求图服务，从新版目录执行 `upgrade` 后可用原端口重启。日常从项目根运行 `python3 .agents/skills/requirement-flow/flow.py`。分支、联调、权限和发布按项目约定；回执带 `project_rules` 时，按它查本次业务规则。

## 默认轻量交付

纯问答和不改行为的修改（错别字、格式化、纯重构、依赖升级）直接处理，不建需求。其余先用 `list` 找已有需求，续做时用 `context` 读故事和 `workflow`。新交付用 `new <ID> --light --request '原话'`，仅调研用 `--outcome research`。不带 `--light` 建的是动作编排需求（回执 `workflow: orchestrated`），用于一开始就要多人分工的工作。恢复历史材料按 `.requirements/history/index.md` 查标题。

1. **建卡。** 用 `task <ID> cards` 写能独立验收的故事、来源和有稳定 ID 的场景。验法容易跑错、要交接或指定环境时登记 `checks`。向负责人展示功能清单和待决定的分支，展示后继续实现，不等待确认；待决定的分支只阻塞依赖它的故事。[字段与示例](references/lightweight.md#1-登记可验收的故事)
2. **实现并采证。** 用 `implement <故事ID>` 登记实际产出和代码依据，写入时 `--actor` 全程沿用同一署名。按回执 `delivery.check_suggestions` 处理缺口；轻量验证直接用场景 ID 调用 `verify-run` 或 `verify-observe`，成功回执当场计入验收，不需要领取或 `finish`。[采证说明](references/lightweight.md#2-按故事登记实现按场景采证)
3. **交付检查。** 采证回执自带交付报告，`ready_to_deliver: true` 时报告验收完成；续做、交接或改码后没有最新回执时运行 `task <ID> delivery-check`。能补的缺口继续补；缺输入时报告实现状态、具体缺口和接手方。此后改码、改范围或换目标环境，重新核对后再报告。

用户已授权的需求内，新建需求、建卡、登记实现、运行本机检查并采证可直接做。需要实际决定人或用户确认的：业务 `decision`、用 `retire_scenarios` 撤出已承诺的场景、`--share-output` 分发原始日志、真实环境采证、归档。

创建需求后看回执的 `related_lessons`：打开原场景和回执核对是否适用，决定采用时用 `lesson-adopt` 写回来源版本和理由，[命令](references/model.md#可在项目内复用的经验)。待审经验交给另一位审查者。

## 继续与停下

有授权内的下一步就继续：补实现、补证据、处理 `check_suggestions`。报告验收完成时写明通过/本期场景数，以及仍待决定或未覆盖的部分。

停下来问用户的情况：缺业务决定，缺真实环境或权限，要撤出已承诺的范围，或同一场景相同输入连续失败两次。最后一种须由原失败执行者以外的执行者诊断，单会话时交接给用户或另起独立子代理，其他场景照常推进。

## 按需加编排

范围争议、待确认契约、跨人分工或独立复核才增加对应动作，已通过的证据保留。用 `task <ID> next --actor <执行者>` 查看待办，用 `task <ID> context <故事ID>` 核对功能；领取、交接、写回和子代理派发见[动作编排](references/orchestration.md)。

| 什么时候用 | 打开哪个 skill | 需要拿回什么 |
| --- | --- | --- |
| 对象、目标、状态边界或验收例子还不清楚 | [需求分析](../flow-requirements/SKILL.md) | 故事、场景、待决定事项及受影响范围 |
| 画面或行为依赖接口，字段含义、读写、分页或回显需要核对 | [接口契约](../flow-contracts/SKILL.md) | 操作到字段及结果的对应关系、来源、缺口 |
| 一个可执行的开发动作已经有范围、输入和完成条件 | [功能开发](../flow-implement/SKILL.md) | 实际代码和该功能的关键处理路径 |
| 行为需要证明、修复需要回归，或验收依据发生变化 | [功能验证](../flow-verify/SKILL.md) | 对应到场景的运行结果、观察记录和失败返工项 |
| 用户要求检查，或跨层改动、关键路径、已有证据之间需要独立复核 | [审查](../flow-review/SKILL.md) | 有位置和依据的发现、影响、处理结论 |

专项可跳过、重复或组合。仅审查可止于问题清单；一张卡等业务决定时继续其他就绪工作。分派前查完整故事和 `covers`，因为故事筛选不缩减共享动作的范围。
