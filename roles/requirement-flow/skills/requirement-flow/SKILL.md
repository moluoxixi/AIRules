# 需求编排

项目启用方式是从 AIRules 安装的本 skill 运行 `python3 <技能目录>/flow.py --project <项目目录> init`。已启用的项目使用项目根目录下的 `.agents/skills/requirement-flow/flow.py`。以下命令中的 `flow.py` 都指这份文件。先用 `list` 查找当前需求，复用已有 ID。

## 从原话到功能图

1. 独立需求使用 `new <ID> --request '用户原话' --title '可辨认的名称'`。若委托只要求调研或出方案，创建时指定 `--outcome research`。范围取自本次委托。已有项目规则继续约束分支、代码、接口、权限和验证环境。
2. 按用户可独立验收的结果拆故事。记录谁操作、起始状态、成功结果与失败恢复。涉及接口时核对路径、字段来源、类型、必填、枚举、提交与回显。把缺口关联到具体故事、契约或业务决定。
3. 用 `task <ID> plan <补丁.json> --actor <执行者> --rev <版次> --why '依据'` 写入故事及相应动作。按需组合调研、开发、验证，显式声明依赖和由业务选项触发的分支。计划字段和验收证据类型见 [记录格式](references/model.md)。

## 推进与回写

- 用 `task <ID> next --actor <执行者>` 读下一项、前置证据、完成条件和待决事项。可加 `--story <故事ID>` 聚焦功能；`context <故事ID>` 可读该功能的完整关系。并行执行者使用各自稳定的名称。
- 在授权范围内用 `task <ID> claim --actor <执行者> --rev <版次>` 领取，可加相同的故事筛选。依照返回的动作实际读代码、开发或运行检查。遇到版次冲突时重新读取。恢复同一工作线时沿用执行者名。
- 技术缺口先查实际契约和代码。影响用户行为的分歧列出具体选项和后果，收到用户的选择后用 `decision <决定ID> <选项> --actor <决定人> --rev <版次> --why '依据'` 写回。其他已满足依赖的动作可继续。
- 使用 `finish <动作ID> --actor <执行者> --rev <版次> --output '实际产出' --evidence '可复核位置或命令结果'`。验证另传 `--level`、`--environment` 和 `--expected`。验收失败用 `fail`，附同样证据和 `--reopen <需返工的相关动作ID>`。这些子命令都通过 `task <ID>` 执行。

## 查阅和交付

用 `task <ID> serve` 取得本机图页 URL。图上可以筛选功能，沿关系查看接口、字段、关键处理和验收证据，并登记业务决定。离线页和机器记录在 `.requirements/active/<ID>/` 的 `handbook.html` 与 `model.json`。用 `task <ID> --check` 检查两份记录。交付时给出图页、已验证范围与仍待确认的事项。若产生可复用经验，连同适用条件和证据写入 `lessons`。使用 `archive <ID>` 保留已结束需求的完整记录。
