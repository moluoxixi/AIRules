# 独立审查

接到 `lesson_reviews` 中的候选时，用自己的执行者身份打开来源场景和实际回执，核对附件、断言、环境与经验适用边界。如果无法判断断言能否抓住原问题，在隔离环境还原错误行为并运行同一检查。用 `lesson-review` 写明批准或驳回的具体理由。提案作者只负责补充或修订，留给独立审查者决定。

连续失败生成的诊断是普通调研动作，`review_for` 标明原验证、场景和失败回执，`failed_evidence` 提供核验后的来源。实际独立的执行者用稳定署名领取，复现后通过 `finish --output '诊断结论' --evidence '复现与依据位置'` 留存结果。工具拒绝原失败执行者领取或结束该诊断；更换署名不构成独立审查。验证动作随后按依赖恢复，须取得新回执。

先明确审查范围。需求评审读取原话、原型、故事和决定；实现评审同时读取实际差异、接口、调用方和验证记录。优先检查对用户结果有重大影响的路径。专项审查可以独立给结论，不要求顺序走过其他技能。

1. 选择一个用户故事，从验收预期逆向追踪到验证证据、实际处理和依赖契约。也从变更入口正向追踪一次，寻找漏接的调用者、异常分支、权限、重复操作或旧数据问题。
2. 核对每条重要结论是否有对应场景、当前输入、实际环境与可复查依据。特别检查代码已改但测试仍断言旧行为、正常路径通过但异常恢复未覆盖、mock 通过被当作线上验证等情形。
3. 对每个可操作的发现列出影响与优先级、触发条件、预期与实际、证据位置，以及需改的最小范围。区分已复现的问题、仍欠验证的风险和需要业务决定的问题。审查通过也注明查看了哪些范围和仍未验证的部分。
4. 需求图项目以 `context` 读取相关故事，使用 `plan` 增补确有依据的遗漏、动作与依赖，在当前审查动作记录结论。需要重跑的场景交给 `flow-verify`；需要业务取舍的事项交给实际决定人。用户只要求审查时交付发现与结论。

项目内 `flow.py` 位于 `.agents/skills/requirement-flow/`；数据字段见[记录格式](../requirement-flow/references/model.md)。
