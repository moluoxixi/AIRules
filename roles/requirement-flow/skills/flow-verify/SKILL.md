# 功能验证

读取动作包中的相关经验，把适用的失败条件写进当前需求自己的验证。出现 `verification_followups` 时按场景追溯失败回执，针对原故障修复后重测；相同输入连续失败时，按诊断动作交给独立审查者检查测试前提和归属。

读取故事、场景 ID、验证动作的完整 `covers`、允许的证据方式和当前版次。故事筛选不会裁剪共享动作的覆盖范围：一个动作由一位持有人统一结束，全部覆盖场景有效通过后才计入验收。独立交付或不同执行者负责的检查分别建验证动作；同一持有人可以并行运行不同场景。先写出每个场景可由什么结果证明。从 `next` 或 `claim` 的最新动作包核对 `verification_project_root` 和 `code_paths`：范围须覆盖实际所验的实现、测试和配置，命令、观察与所记录输入须属于同一检出。截图、日志等运行产物放在该代码范围之外；默认范围及无 Git 项目的处理见记录格式。核对环境、数据及入口满足场景前提；真实环境还需核对实际部署版本并走该环境的业务链路。

1. 选择能区分预期行为和错误行为的检查。例如验证字段回显时，检查保存请求、成功响应和重新打开后的显示值。仅验证成功提示，无法证明保存后的回显。
2. 自动化适用时用 `task <需求ID> verify-run` 执行能断言业务预期的测试命令，并开启测试结果输出。退出 0 但输出为空或全为空白时，运行事实会保留，场景仍缺成功凭据。有输出时也要核对测试名称、断言、退出状态及真正覆盖的业务行为。选择命令前检查其环境和副作用，遵从项目授权。
3. 页面、设备或真实接口适合观察时实际操作，再用 `verify-observe` 记录前提、预期、观察结果、验证者和可复核依据。截图或响应记录应能识别该行为，剔除账号凭据等敏感数据。只为确实验证到的场景登记证据。
4. 逐项对照 `covers`，分别说明通过、失败、未验证的场景及原因。失败附最小重现和相关前置动作；修复后重跑受影响场景。已变化的契约、决定或实现应使用当前输入重新验收。满足场景验收后，用同一执行者和已刷新版次的 `finish` 结束验证，引用本次真实回执。报告结果时附真实输出或观察位置和环境。

使用项目内 `.agents/skills/requirement-flow/flow.py`。证据命令参数及验证完成条件以[记录格式](../requirement-flow/references/model.md)为准。独立验收时按同样方式报告实测范围、实际结果和依据。
